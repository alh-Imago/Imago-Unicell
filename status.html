CELL INTERNALS — BOTH STEPS CLOSED
#49/#51/#59 — comparator, pattern chain & dynamic routing latch

Silicon-confirmed, cleanly. cmd_latch widened to 128 bits. A 3-way unsigned comparator (lower / equal / higher) selects between three 6-bit routing patterns; the same static configuration, fired against three different data values, took three genuinely different routes on real Arria 10 silicon — matching what simulation predicted exactly. Along the way: a real top-level address-lane whitelist bug was found and fixed, and an earlier "back-to-back rearm hazard" finding was corrected — it turned out to be a measurement artifact in sticky debug-readback latches, not a real cell fault. Targeted CMD_SET_ROUTE_LATCH_AT / CMD_FREEZE_AT / CMD_RELEASE_AT were also built and silicon-tested, and a real broadcast-emission hazard (a command-emit cell's own composed data accidentally reconfiguring the whole array) was closed by making emission genuinely targeted at the array level.

CONFIRMED
NEXT — ACTIVE DESIGN
The command-cell RAM-read runtime mechanism

With the internals settled, the next step is the runtime loader: RAM holding an array of pending commands, the existing proven boot-time reader (loader_fsm_v3.v) re-triggered and re-purposed to walk it serially at runtime instead of once at boot. The reader itself is now modeled faithfully in the VM (a direct replay of its own proven testbench passes cleanly) as the foundation for this work. The open design question: the boot-time confirm mechanism (CMD_LOAD_DONE) is specific to configuration loads — a runtime data-injection step needs its own answer for how a step confirms completion before the reader advances.

Scale to full 16-zone / 400-cell card

The full-scale target once the RAM-read mechanism is implemented and tested.

PARKED — NOT BLOCKING
PCIe bring-up

Link is confirmed Gen2 x8, the command register enables memory decode, and BAR0's address matches Device Manager. The root cause behind the fabric ignoring commands over both JTAG and PCIe simultaneously was found and fixed: UART_RX had no pin assignment or pull-up in any .qsf file, so left floating it assembled spurious cpu_valid pulses that trampled the shared three-master arbiter. Fix: tie uart_rx to 1'b1 at the top level. A 25-iteration repeatability loop on the fixed design passed 25 of 25, fully deterministic.

Open issue: BAR0 data access still returns 0xFFFFFFFF despite every externally-checkable cause being ruled out. Deliberately revisited last, once everything above is done — it isn't blocking any of it. The leading suspicion is a host-side hardware limitation, not yet confirmed.

PARKED
FIG. 06B THE VM

Fully rebuilt to match the current silicon, exactly

A complete, six-phase rebuild of the Python simulation model — topology latch, methodology latch, routing latch and comparator, targeted opcodes, command-emit, and array-level semantics — built bottom-up and verified line-by-line against the actual current Verilog rather than reconstructed from memory. 240 tests, several of them direct replays of exact silicon-confirmed results, including a complete four-role command-loader pattern that passed clean on its first run. This gives both the person and their AI development partner a fast, exactly-faithful place to prototype fabric designs before any FPGA compile.

Two IEI Mustang-F100-A10 cards (Arria 10 GX660, 10AX066H2F34E2SG). JTAG IDCODE 0x02E250DD. Volatile SRAM configuration — reflashed after every power cycle.

REBUILT

VM

Fully rebuilt against the current silicon (128-bit cmd_latch, the full opcode vocabulary through command-emit, targeted addressing) — 240 passing tests. The compiler/controller/workbench layer above it is the next migration, not yet started; the legacy VM stays in place and fully functional until that happens.

RULE LEARNED THE HARD WAY

Always reboot after JTAG reprogramming, before any PCIe test

JTAG reprogramming wipes PCIe config space, including BAR0 — producing a symptom indistinguishable from a dead card if the reboot step is skipped. This is now a fixed procedural rule.
