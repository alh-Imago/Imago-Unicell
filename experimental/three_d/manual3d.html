Imago UniCell 3D Kit — manual

Version of 23 Oct 2026 (ledger #1310–#1314). This kit is separate from the main UniCell tools: its own composer, its own placer, its own file formats. It does not need, and is not connected to, the main Composer, the workbench or the front panel.

1. What this is, and what it is not

The kit explores one idea: what if a cell had six neighbours — north, south, east, west, up and down — so that a design can be built in layers, the way a stacked chip is? It lets you draw such a design, run it, place it automatically, and save it in a file format meant for six-face cells.

It is an exploration, not a product. Be clear about this before relying on anything here:

  • There is no 3D hardware, no 3D RTL and no card to run any of this on. Everything runs in software, in a small toy model of the six-face grid (experimental_3d_nor_v2.py): a cell passes a word on, or combines two words with a gate, one cell per tick.
  • The number of layers is free (a stack can be 2 or 20 high). The cells themselves have to carry all six faces.
  • The three file formats in this kit (design, netlist, ICM-3D) are read only by this kit. Nothing else — no assembler, no generator, no FPGA flow — reads them.
  • Timing in the toy (one tick per cell) is not hardware timing.

2. Quick start

You need Python 3.12 or newer (tested on 3.13; nothing outside the standard library). From the folder that holds this manual:

python3 run_composer.py

The 3D Composer opens in your browser at http://127.0.0.1:7422. (--port 7430 changes the port, --no-browser stops it opening a window, --example adder_auto starts with an example loaded.) Stop it with Ctrl+C.

First things to try, in the page:

  1. Open an example… → NOR adder, 44 cells, 3 layers.
  2. Drag the Depth slider: the layer you are on is shown in full, everything on other layers fades.
  3. Drag in the 3D view to rotate; press Top, Front, Side, 3/4.
  4. In the Run / step panel give A and B some numbers, choose watch E, press Start, then Run to end: E holds A + B.

To check the whole kit works: python3 run_tests.py (needs pytest: pip install pytest).

3. The ideas, in plain words

  • Six faces. Every cell has N, S, E, W, U, D. A cell sends a word out of the faces you switch on; a neighbour receives it through its opposite face.
  • Layers. Up/down moves to the next layer. Layer 0 is the bottom. The board is rows × columns × layers.
  • Two kinds of cell.
  • Relay — passes the word on, optionally shifted left or right by 0–31 bits. In ICM-3D terms a relay is a ram cell in flowing (pass-through) mode: one word in, one or more faces out (Alan, 23 Oct 2026; read from ram_cell_v4sa.v). The shift is the add-on.
  • Gate — waits for two words, then outputs AND, OR, XOR, NOR, NAND or XNOR of them. In ICM-3D a gate is a nano cell with the toy's topology code.
  • Joins. A "join" is just a face switched on towards a neighbour. Cells that are not neighbours are joined by a chain of relay cells laid between them.
  • Entries and exits. An entry is a cell that sends but receives nothing: you give it a word to start. An exit is a cell that receives but sends nothing: you read the answer there.
  • Ticks. In each tick every cell that has a word passes it on; it arrives next tick. A gate fires when its second word arrives. There is no flow control: one set of words at a time.
  • Nothing crosses by accident. A cell sends only through the faces switched on, so two wires can pass side by side or one over the other without touching. The only rule: two wires never share a cell.

4. The 3D Composer

The page

  • Floor plan (left): one layer, editable. The layers above (▲n) and below (▼n) are drawn faded behind it. A gold triangle on a tile means it sends up or down; a hollow gold triangle means it receives from there.
  • 3D view (right): the whole stack in perspective. The current layer's sheet is outlined in copper; its cells are drawn solid and labelled, other layers are faded.
  • Depth slider (and the ▼ ▲ buttons, or the [ and ] keys): chooses the current layer. The others menu sets how strongly other layers fade (hidden · very faint · faint · visible); layers further from the current one fade more. layer gap spreads the layers apart in the 3D view. show switches between plan + 3D, plan only and 3D only.
  • 3D view controls: drag to rotate; shift-drag or right-drag to pan; mouse wheel to zoom; 3/4 · Top · Front · Side presets; Spin turns it slowly. Click a cell to select it.

Tools

Tool What it does
Select click a cell to select it and edit it in the Selected panel
Place pick Relay or a gate in the palette, then click an empty square of the current layer
Join click a source cell, then a target cell. Neighbours get a face; otherwise a shortest chain of relay cells is laid through free squares. The box joins may route through other layers chooses whether the chain may leave the current layer

The Selected panel

Name, kind (relay/gate), gate type, shift bits and direction (relay only), and six face buttons N S E W U D — a face can be switched on only where a neighbouring cell exists. It also shows what the cell receives from, and a Delete cell button.

Board and layers

Set rows and cols; + layer top / + layer bottom add an empty layer (adding underneath moves everything up one, so neighbours stay neighbours); − top / − bottom remove an empty end layer. A change that would cut off a cell is refused. Undo (or Ctrl+Z) takes back the last edit.

Run / step

Give each entry a word (decimal or 0x hex), choose a watch cell, press Start. Step advances one tick, +10 ten, Run to end until nothing moves (a loop is cut off after 2000 ticks). Cells holding words are outlined green; cells that fired this tick copper; the watch cell shows its word and the tick it first appeared. Any edit stops the run. Check (when the design says what it should compute) runs 100 random tests: for the adder against real addition, for an auto-placed design against its netlist.

Problems panel

Warns about: a face that points at no cell; a gate without two inputs; a loop (a word would go round for ever); a cell not joined to anything. Click a line to jump to it.

5. The automatic placer

experimental/three_d/placer3d_v1.py takes a netlist and lays it out by itself.

python3 experimental/three_d/placer3d_v1.py --example adder --layers 3 --out adder.3d.json
python3 experimental/three_d/placer3d_v1.py --netlist my_net.json --layers 2 --seed 3 --out my.3d.json

Open the result with Open file… in the composer.

The netlist file

{"format": "imago-3d-netlist", "version": 1,
 "cells": [{"name": "A", "kind": "relay"},
           {"name": "G", "kind": "gate", "gate": "XOR"},
           {"name": "S", "kind": "relay", "shift": 4, "left": true}, ...],
 "nets": [["A", "G"], ["B", "G"], ["G", "S"]]}

A net ["A", "G"] means A's output goes to G. Rules the placer checks and states plainly if broken: no loops; a gate has exactly two inputs; a relay at most one; a cell's inputs plus outputs at most six (add a fan-out relay yourself); every cell joined to something; names unique.

How it works

  1. Spread the cells on a lattice by simulated annealing (short wires, and no cell walled in by cells it is not joined to).
  2. Route every net as a chain of relay cells, by negotiated congestion (nets may share squares at first; sharing gets dearer each round until none do).
  3. Close the gaps between rows, columns and layers while it still routes, and delete planes that hold only straight-through relays.
  4. Verify by running: every exit must give the same word as direct evaluation of the netlist, for 64 random input sets. A layout that fails is never returned.

Several layouts are found (keep) and the smallest is returned; different --seeds give different layouts.

What it achieves (measured)

For the NOR adder (35 netlist cells), 3 layers allowed: 80 cells in all from the default three layouts (seed 1), 72 if eight are tried, 62 with 4 layers allowed. The hand-placed adder is 44 cells in 22 ticks; the automatic ones settle in about 40 ticks. So the placer is correct but not compact — about 1.4 to 1.8 times the hand layout. With one layer the adder cannot be placed (wires must cross) and the placer says so.

6. ICM-3D v2 — the file format

A standalone file format for six-face designs in the flex family. Full specification: the next section of this manual (ICM-3D v2 specification). In short: one record per cell — its square, its core (ram pass-through or nano gate with a topology code), its shift add-on, and two 6-bit face masks (out_mask: faces it sends to; in_mask: faces it receives from; bit order N S E W U D). A reader recomputes every in_mask from the neighbours and refuses the file if it disagrees. JSON form (with names) and a compact binary with a checksum (the 44-cell adder is 367 bytes).

python3 experimental/three_d/icm3d_v2.py convert design.3d.json out.icm3d.json
python3 experimental/three_d/icm3d_v2.py convert design.3d.json out.icm3d
python3 experimental/three_d/icm3d_v2.py convert out.icm3d back.3d.json
python3 experimental/three_d/icm3d_v2.py show out.icm3d

icm3d_v1.py (the first version, with a toy relay) is kept as it was written; v1 and v2 files refuse each other.

8. Checks

python3 run_tests.py runs 55 tests: edit refusals and undo, routing, layer changes, file round trips and damaged files, the stepper against the toy model's own run, the adder against real addition (and the check failing when a gate is broken), the placer's refusals and its verification (also tested to bite: a changed gate and a cut wire are caught), ICM-3D consistency rules and damaged binaries, and the live server.

9. Limits — what is not done

  • No 3D hardware, RTL, assembler pass or card (section 1).
  • ICM-3D covers only nano gates and ram pass-throughs. The other cores (adder, mul, div, accumulator, comparator, latch, sequencer, branch, priority, cross, corner, merge, the other ram modes) have no record; their six-face widths are in the cell audit (last section). The sub family is not defined.
  • The ram record is not a full ram configuration (no preload word; fixed mode off). How one ram offers a word to several consumers is the flex glue's job, not a ram setting. A real ram holds a word for two cycles; the toy passes one cell per tick. The polarity of the add-on's direction bit against "shift left" was not checked.
  • The nano topology codes are copied from the toy model, not re-checked against the RTL here.
  • The placer handles feed-forward netlists only, does not insert fan-out relays, and is not minimal.
  • The composer's Join router is a plain shortest-path search; it can fail on a dense design. Placing is in the floor plan only. Touch pinch-zoom is untested.
  • In the downloaded kit, the cell-audit's numbers come from the full project (cell_face_budget_v1.py there); the script is not in the kit.

ICM-3D v2 — a file format for six-face (3D) designs, flex family

23 Oct 2026. v2 supersedes v1 (#1314): v1 had a toy relay pseudo-core; per Alan a relay is a ram cell in flowing (pass-through) mode, and v2 says so. icm3d_v1.py is kept as it was. Exploration only (see the scope note in README.md): there is no 3D RTL, no assembler pass and no card. The format is read and written only by icm3d_v2.py and the 3D Composer, and describes designs in the toy grid experimental_3d_nor_v2.py.

Why a separate format

ICM v3's core_config is a 42-bit union shared by all cores; with six faces five cores overflow it (branch needs 49, nano 47, ram 46, comparator 44, accumulator 43 — CELL_AUDIT_6_FACE.md, re-run cell_face_budget_v1.py). Rather than move fields inside the 80-bit SUPER_LATCH, ICM-3D is a new standalone format with its own per-core records (Alan's choice, 23 Oct 2026). ICM v3 is untouched, and an ICM v3 reader will refuse an ICM-3D file (different format, different magic).

Family chosen first: flex/sub (Alan, 23 Oct 2026). In that family a cell has generic lanes and the wiring is the netlist, so the format needs one thing per cell beyond the core: which of the six faces it sends to and receives from.

What a record says

field meaning
pos [row, col, layer] the grid square; layer 0 is the bottom, U goes to a higher layer
core nano (a gate) or ram (a pass-through, see below)
topology nano only: the toy's nano topology code — AND 0x007, OR 0x024, XOR 0x0BC, NOR 0x004, NAND 0x027, XNOR 0x03C (copied from the toy model; not re-checked against the RTL here)
shift, shift_left the shift add-on, 0–31 bits (on a ram pass-through only; a gate has none in this model)
out_mask 6 bits, faces the cell sends to: bit 0 N, 1 S, 2 E, 3 W, 4 U, 5 D (U, D after W, so a four-face design keeps its four low bits)
in_mask 6 bits, faces it receives from; derived from the neighbours' out_masks and stored anyway

The consistency rule: a reader recomputes every in_mask from the neighbours' out_masks and refuses the file if any differs. It also refuses: two cells on a square, a square outside the board, a face sending into an empty square, a gate without exactly two inputs, an unknown topology, a shift on a gate, a mask wider than six bits. A design with a dangling face cannot be exported (the composer shows it as a warning; the format has no dangling faces).

What a relay is (Alan, 23 Oct 2026): a ram core in its flowing mode — fixed_mode 0, no preload — one word in, any of the six faces out. Read from sub/verilog/ram_cell_v4sa.v (flowing mode: capture on valid_in, offer until ack_in) and icm_v3.CORE_FIELD_TABLES (ram: downstream_mask, upstream_mask, fixed_mode, load_data_valid, init_data). The shift is not a ram field: it is the add-on (addon_config: shift_en, shift_amt, direction), whose bit polarity for shift_left was not checked here. Not simulated in 3D, and the toy's one-tick-per-cell timing is not the ram's (it holds a word for two cycles).

Two forms

  • JSON — human readable; also carries cell names, a description and meta.
  • Binary — little-endian. Header <4s B B B B B H>: magic I3D2, version (2), family (1 = flex), rows, cols, layers, cell count. Then one 64-bit record per cell, then a CRC-32 of everything before it. No names.

Record bits (LSB first): row[0:6] col[6:12] layer[12:17] core[17:19] gate_index[19:22] shift[22:27] shift_left[27] out_mask[28:34] in_mask[34:40] reserved[40:64]. core: 0 ram (flowing), 1 nano. gate_index: 0 AND, 1 OR, 2 XOR, 3 NOR, 4 NAND, 5 XNOR. Reserved bits must be zero; a reader that finds one set refuses (a newer format). Limits: 63 × 63 × 31 squares, 65,535 cells. The 44-cell adder is 367 bytes.

Use

python3 experimental/three_d/icm3d_v2.py convert design.3d.json out.icm3d.json   # composer design -> ICM-3D JSON
python3 experimental/three_d/icm3d_v2.py convert design.3d.json out.icm3d        # -> binary
python3 experimental/three_d/icm3d_v2.py convert out.icm3d back.3d.json          # back to a composer design
python3 experimental/three_d/icm3d_v2.py show out.icm3d

The 3D Composer has Save ICM-3D and Save ICM-3D binary buttons, and Open file… reads either form.

Not done

  • No core other than nano gates and ram pass-throughs: the other ram modes (fixed, preloaded), adder, mul, accumulator, comparator, latch, sequencer, branch, priority, cross, corner, merge and div have no ICM-3D record yet. Their six-face widths are in CELL_AUDIT_6_FACE.md; each would need a per-core record layout of its own.
  • The sub (v4s) family: only flex is defined (family 1).
  • The binary does not carry names, so a name-based check (the adder's "A", "B", "E") needs the names put back.
  • No generator, assembler or RTL reads this.

What each cell type needs to have six faces (N, S, E, W, U, D)

Audit of 23 Oct 2026. Paper analysis of the real RTL and code: no 3D RTL exists and nothing here was simulated in 3D. The number of stacked layers is a free variable (a stack can be 2 or 20 high), so the question is not "how thin" but "what must a cell itself carry to have all six faces". Everything below was read from the named files or measured by the scripts named; the last section lists what was NOT checked.

Scope (Alan, 23 Oct 2026): this is an exploration, not a design under way. There is no card that could run any of it, nothing 3D exists in RTL, and the one 3D layout (the NOR adder) was placed by a hand-derived stage-tile formula with only the end cells and long nets searched automatically; an automatic simulated-annealing placement was tried first (#1036 addendum 50) and never produced a routable layout. Read the decisions at the end as a menu of what six faces would cost, not as a to-do list.

The short answer

A cell touches direction in three places. Each cell type was checked for all three:

  1. Ports (the physical faces).
  2. Direction fields (which faces a cell listens on / sends to).
  3. Face-indexed logic (selects, ack vectors, tie-break order, the programming channel).

The cell families differ a lot:

Family Files Direction in the cell Six faces mean
Flex / sub (the active line, Tang Nano) sub/verilog/*_v4sa.v, *_v4s.v None. Cells have generic lanes (data, valid, ack). Which neighbour a lane meets is decided by the netlist, not the cell. No cell change, except corner, cross, priority. The change is in the ICM masks, the assembler, the layout tool and the VM.
Standard (carrier / super shells, Arria 10 line) fpga/verilog/*_cell_v4c.v, shells, unicell_vix_carrier_v1d.v Everywhere. Four named faces on every core and on the carrier. Every one of the 15 cores, its shell and the carrier.

Flex / sub family: only three cells know about faces

Checked by listing every module's ports in sub/verilog (a throwaway scan, not saved): the only cells with face-named ports are

Cell Why it is face-aware What six faces needs
corner, cross four independent one-word slices, one per face a word enters by; partner(face) is a hard-coded 4-entry table (cross: N-S, E-W; corner: N-E/S-W or N-W/S-E) six slices. Cross gains the U-D pair (three straight-through pairs). Corner is the real design question: with six faces a "turn" is no longer one bit (TURN); a pairing of six faces into three pairs has 15 possibilities, so the partner map needs to be a configured table, not two parameters.
priority four inputs named in_n/s/e/w, four per-face ranks, tie-break "a fixed N>S>E>W order", weighted round-robin credits one per face two more inputs, two more ranks, two more credit counters; the tie-break order extends U, D (so every existing four-face design keeps its result).

Every other flex cell (nano, ram, mask, shift, compare, sequencer, accumulator, latch, merge, router, adder, mul, div, branch) has 2 to 4 lanes in and out and no face in its RTL. A six-face grid does not change them. What it removes is the 2D cost of having more than four neighbours (the toy adder shows 44 cells against 80).

One thing to keep in mind: a face carries a lane in and a lane out, so "faces needed" is the number of distinct neighbours, which is at most the number of lanes. Priority (4 in + 1 out) and the two-output cells (adder, mul, div, branch: 2 in + 2 out) are the ones that can need four or more neighbours.

Also order-sensitive: merge (A = the first set upstream bit in N,S,E,W order) and the two-operand cells (the first arrival is A) rely on face order only to break ties; adding U and D after W keeps every existing result.

Standard family: the core-by-core table (v4c RTL)

Measured from the RTL (fpga/verilog/*_v4c.v, mul_cell_v5c.v):

  • Direction registers are already 6 bits wide in every core ("N/S/E/W real + 2 reserved"), and branch has a 3-bit direction and 6-bit routes. Nothing reads bit 4 or bit 5 of any of them, so this is headroom, not a half-built feature. (Nano ties its top two bits to 2'b00.)
  • Ack vectors are 4 bits (pending_ack, ack_in_vec) in every core except nano, whose pending_ack is 6 bits with the top two always zero.
  • Select logic is four copies: sel_n/s/e/w = arrived_x && mask[0..3], and the data path ORs four buses.
  • The programming channel is four faces in all 15 cores (checked: every file has the prog_sel_n/s/e/w chain with a fixed N>S>E>W priority and four prog_data_in_* buses). Programming reaches a cell through a neighbour, so in a stack a cell must be programmable from U and D as well.
  • Ports: every core and every shell has arrived/fire/ack/ready/data per face, four times.
Core Direction fields today Specific work for six faces
nano (nano_gate_v4c) routing_mask 6, cardinal_edge 6, pending_ack 6; the three 4-bit routing patterns Already the closest: widen the three patterns, add sel_u/d, use ack bits 4-5. Its "ready" is broadcast on all four faces.
ram down 6, up 6 selects and ack vector
adder, mul, div down, up, second-down 6 each same; second word leaves by its own mask
accumulator inc_dir, dec_dir, down same
comparator down, up same
latch set, clear, toggle, down four masks
sequencer down one mask
branch upstream_dir 3-bit encoded (0-3 used), three 6-bit routes the encoded direction already holds 0-5; the compare of == 3'd0..3 extends; routes widen their active use
priority masks 6, ranks 2x4, sequence_0..3 2-bit ranks and credits per face; sequence entries become 3-bit (a six-turn order needs six entries)
merge up, down A/B order by face index
cross, corner 4 slices six slices and the partner table (see above)
command drive_dir 3-bit (0-3 used) freeze / program drive outputs for U and D; drive_dir already holds 4-5

The ICM v3 file format is the one real squeeze

nano/icm_v3.py's core_config is a 42-bit union shared by all cores. Re-run python3 experimental/three_d/cell_face_budget_v1.py:

core uses with six faces verdict
nano 41 47 over by 5
ram 42 46 over by 4
accumulator 37 43 over by 1
comparator 40 44 over by 2
branch 42 49 over by 7
priority 29 41 (47 if a full six-turn order is allowed) fits (tight)
adder, mul, div 25 31 fits
latch 16 24 fits
sequencer 38 40 fits
cross, corner, merge 8-10 12-14 fits

So five cores do not fit the 42-bit union with six faces; the worst needs 49. This is a limit of the file layout, not of the cells: the standalone v4c cores take 64-, 80- or 128-bit config words, and the VIX carrier's core_config is 128 bits. The old 80-bit SUPER_LATCH has 11 reserved bits [79:69], enough for the worst case (7), but using them moves every field after them (the carrier shells and the ICM encoder/decoder would change together). The 3D toy's own header (#520) already said branch was at the edge of the 42 bits (41 then; 42 today, since rolling_mode was added) for the same reason.

Wires per face (the cost of two more faces)

Counted from the port lists:

Where Wires per face Four faces Six faces
flex lane (one link, WIDTH = 32) 34 (data 32, valid, ack) n/a (per link) n/a
unicell_super_v3 shell 102 408 612
unicell_vix_carrier_v1d 141 (four 32-bit buses: data in/out and programming in/out) 564 846

For a real stacked chip the two vertical faces are the through-silicon connections, so these counts matter. The flex lane is far cheaper than the carrier face, because the carrier face carries a programming bus both ways.

Software that hard-codes four directions

49 non-archived Python files in nano/ and tools/ name four directions (delta tables, opposite-face tables, direction-bit maps), including icm_v3.py, unicell_super_automaton_v1.py, flex_grid_v1/v2.py, flex_layout_v1.py, design_map_v1/v2.py, walker_card_v1/v2.py, and every flexsub_icm_* generator. (Found by searching for the direction tables, not by reading each file; some may need no change.)

What was NOT checked

  • The per-core shells (*_shell_v1c.v) and carrier internals beyond their port lists and the header of v1d.
  • The Flex-Sub assembler / ICM generators: found by name only; not read for how a mask becomes a link.
  • Timing and area of six-face cells (nothing built).
  • Whether priority's weighted round-robin keeps its fairness with six requesters (a behaviour question, not a width one).
  • The standard-VM's treatment of simultaneous arrivals on U/D (the VM would need the same extension).
  • The sub (v4s) family was checked by port list only (same result as flex: only corner and cross carry faces).

Decisions only Alan can make

  1. Which family first? Flex/sub needs almost no cell change (three cells) and the most tool change; the standard family needs all 15 cores plus shells.
  2. Corner in 3D: keep it as a fixed set of turn tiles, or make the partner table configurable?
  3. Fixed-order extension: U and D after W everywhere (keeps all four-face designs identical) — recommended unless there is a reason to put them first.
  4. ICM format: a v4 with per-core widths, or use the 11 reserved bits.
  5. Programming a stack: the programming channel enters through faces, so it needs vertical entry; decide whether a stack is programmed layer by layer or through the vertical faces.
