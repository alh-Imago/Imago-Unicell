## CORRECTION 2026-11-17: the "intermittent DDR3 errors" were the host link losing bytes (jtag_link_v1), not DDR3, heat or the card

The block-RAM build (no DDR3 anywhere) shows the same errors under `ddr3test.py` (364 and 124 wrong words in "pattern A again", one clean run), so the earlier suspects (placement seeds, heat, channel 0 banks, damaged card) were chasing the wrong thing. Cause, from the code and reproduced in simulation (`fpga/tb_jtag_link_stress.v`): `jtag_link_v1` drops a received 32-byte window when its receive FIFO is above the `rx_ready` threshold at the moment the window is acted on, although the host sent it legitimately (it sends when the LAST response said ready) and deleted its copy at once. 32 bytes = four 8-byte 'w' commands = the aligned groups of 4 lost words seen on the card. It only bites when the host scans faster than the bridge drains the FIFO (one byte per RXGAP = 512 clocks, about 330 microseconds per window); the real scan rate depends on USB timing, so it came and went with hub, port and PC load. Stride order and DDR3 (slower per access, so the FIFO is fuller) lost more. A second weakness: `rx_ready` kept room for two windows, three can be in flight.
Simulation, 16384 bytes, v1: lost 10560 / 7904 / 2176 / 0 bytes at 0 / 2000 / 10000 / 16000 clocks between scans; v2 (`fpga/jtag_link_v2.v`: always queue the window, keep 3*K+2 free): 0 lost at every gap.
New files (the v1 files are untouched): `fpga/jtag_link_v2.v`, `fpga/sc_top_k7_v3.v` (BRAM pool), `fpga/sc_top_k7_v4.v` (far RAM as ports); builds `k7/Makefile.v2` + `k7/sc_k7_v2.v` and `k7/ddr3_gpl3/Makefile.v2` + `sc_k7_ddr3_v2.v` (`make -f Makefile.v2`). Built and proven on the card the same day (see the entry above). The stage 1 "proven on the card, 12 runs, 24 of 24" result used small `scbatch` traffic, which does not outrun the drain; it stands, but bulk host writes (`ddr3test.py`, large `w` bursts) were affected by this bug.
Ledger entry (cross-referencing the stage 1 and stage 2 entries) still to be added.

**What was built** (all new files; nothing proven was edited except two small additions named below):
- `fpga/jtag_link_v1.v`: a byte link through the JTAG user register 1 (BSCANE2) instead of the UART. All logic in the system clock, JTAG signals synchronised and edge-detected (no second clock domain); only BSCANE2 outputs that the open toolchain is known to route (DRCK, CAPTURE, SHIFT, SEL, TDI). One scan = 272 bits = up to 32 bytes each way; a host word is acted on at the next scan (so the host flushes with an extra scan), an ack empties the shown bank of a two-bank outbox one scan late (so the response to an ack scan is ignored). RX bytes reach the bridge one per 512 clocks (parameter; the UART gave one per 4,340).
- `fpga/host_bridge_v10.v` (cloned from v9, the UART replaced by a byte port), `fpga/farram_bram_v1.v` (block RAM, same request/ack interface as `sdram_ctl`, 64K words = 256 KB, upper address bits ignored), `fpga/sc_top_k7_v1.v` (cloned from pool15: SYS_CLK, 3 LEDs, BSCANE2, jtag link, bridge v10, BRAM far RAM; cores, sc_sys_v12, copy engine and batch_seq_v2 unchanged).
- `jtagport.py`: the host side, a serial-port look-alike over OpenOCD's TCL port (`irscan`/`drscan` on `xc7.tap`); `host_sc.Board('jtag')` or `'jtag:HOST:PORT'` selects it (small addition to `host_sc.py`); `scbatch.py` now converts clocks with 50 MHz when the port starts with `jtag` (small edit).
- `k7/`: project folder for the openXC7 flow (Makefile, `sc_k7_v1.v` top wrapper with S=4, xdc, `stage.sh`, OpenOCD config copied from the earlier Kintex test, README).

**Tests (simulation, iverilog + Python):** `test_k7_sim.py` is the batch-sequencer test of `test_seq_sim.py` run on the Kintex top through a behavioural BSCANE2 and a host that scans the user register: board version 12; the two-phase chain finished by itself, error 0, tag 0x600d, 28 steps; clock counters 89,833 total / 1,492 copying / 87,865 waiting; all 4 jobs finished; the 20 gathered result words equal the Python answer; the word past the block untouched; the four refusals give errors 6, 7, 1, 8; **RESULT: PASS**. `test_jtagport.py` (pure Python, host side against a Python model of the link): echo of 1,500 bytes in writes of 1/5/32/33/200 bytes and a 5,000-byte burst, in order, about 2 scans per 32 bytes; wrong marker raises an error; **PASS**. ## Stage 3, step 2: batch script handler (2026-11-16; simulation AND ON THE CARD)

A batch is a script of fixed 4-word steps held in far RAM (opcode + 3 arguments): END, LOAD_CODE (far to code store), LOAD_DATA (far to shared RAM), SAVE (shared RAM to far), SUBMIT, WAIT, JUMP (chain to the next script), REGION, WINDOW, LIBRARY. Format and rules are in the header of `batch.py`. The host still does the splitting and compiling (it builds the scripts, code images and window images and writes them into far RAM, then opens the copy window); from there the handler walks the scripts by itself using the same host commands as before, so the dispatcher is not touched. WAIT compares the board's done counter with the number of jobs submitted since the last WAIT (checked in `sc_sys_v12.v`: the counter is incremented in the same place that stores the trap flag, so a job that traps still counts as finished). Rules enforced in the handler: LOAD_CODE / REGION / WINDOW / LIBRARY with jobs still in flight is refused (error 7), so code is never replaced under a running job (this settles the overwrite problem for chained batches only; a host that bypasses the handler is still unchecked); a copy the card refuses stops the batch with the copy engine's error code.

Files: `batch.py` (steps, Script builder, Layout for far-RAM addresses, two executors with identical rules: PlanExec emits the commands for the whole-board simulation, LiveExec reads each step back out of far RAM on the real board), `batch_demo.py` (two-phase chain: phase 1 vsum + vscale, phase 2 REPLACES the code store and the class regions with vstress + vscale on other class numbers, window sizes and addresses; all four results gathered into one far-RAM block), `test_batch_sim.py`, `run_batch_board.py`, stand-in check added to `test_runner_standin.py`.

Simulation (`test_batch_sim.py`, S=2, PASS, about 1 minute): step encode/decode, the in-flight refusal, JUMP and the runaway limit in plain Python; then the chain on the simulated board: both phases finish with no trap, the 20 gathered result words equal the Python answer (phase 2's words are right, so the new code was really loaded), the word past the block is untouched, no SDRAM model timing violations. Stand-in board check passes (logic of the runner only, not the hardware).

**Board result (Alan, 2026-11-16, pool13_5 as already loaded, no rebuild): `run_batch_board.py` RESULT PASS, 7 of 7 checks, one run.** Board version 10, 5 slices; the 28-step chain ran to END with tag 0x600d in 0.82 s (host-driven over the serial link, so this time is mostly round trips, not the board); all four jobs finished with no trap; the 20 gathered result words equal the Python answer, phase 2 included; both negative controls behaved (error 7 and error 1). Repeat runs not yet done. Command: `python3 run_batch_board.py /dev/ttyUSB1`. It also runs two negative controls: code load with a job in flight (error 7) and a copy outside the window (error 1, refused by the card).

What this is NOT: the sequencer is still host software (the host executes the steps), so the host must stay connected during a chain. ## Stage 3, step 1: job input / result convention and gathering results (2026-11-16; simulation AND ON THE CARD)

Every job (program class) has a shared-RAM window that starts with an 8-word header: w0 in_off, w1 in_len, w2 out_off, w3 out_len, w4 status (0 pending, 1 ok, 2 and up = the job refused, e.g. 2 = output area too small), w5 n_out (words produced), w6 arg (one job-specific number), w7 spare; then the inputs, then the output area. Offsets are in words from the start of the window, and a job sees its window starting at byte address 0x10000 wherever it sits, so a program does not depend on where its window is. The host writes the header and inputs, submits the job, reads status and n_out afterwards, then moves exactly n_out words out of the window. Windows are laid out one after another, and `jobio.stitch()` plans the copies that gather every job's outputs into ONE contiguous block of far RAM.

Files: `jobio.py` (host side: Job, build_link, prepare, stitch; expected answers are computed in Python, independently of the core), `jobio/lib_io.s` (library: lib_io_in, lib_io_out, lib_io_done, lib_io_fail; they touch only t0, t1, a0, a1, so a job keeps its state in t2..t6 / a2..a7 across the calls and saves only ra), example jobs `jobio/vsum.s`, `vscale.s` (out = 2*in + 1), `vstress.s` (repeats a shared load and store per word), `test_jobio_sim.py`, `run_jobio_board.py`. A class can be cloned (same code, own window) to save code store: `Job(..., clone_of=)`. Linked together the library and the three programs are 107 code words, which fits the 128-word store of the Tang build with 21 words to spare.

Simulation (`test_jobio_sim.py`, S=2 with the far RAM and SDRAM model, PASS): vsum, vscale, a vscale clone with data that wraps 32 bits, and a vsum clone told it has no output space (it refuses: status 2, n_out 0, nothing written); the 21 result words from three jobs gathered into one block of far RAM equal the Python answer, and the word just past the block was not written; the stress job (a shared load and store per input word, 12 repeats) gives the right result alone and with a 256-word copy running, and takes exactly 116,250 clocks both ways. So in simulation a copy does not take a core's shared-RAM turns, which closes the gap left by the earlier sum-only check. The model reports no timing violation.

On the card: `python3 run_jobio_board.py /dev/ttyUSB1` with the pool13_5 design loaded (stress job repeats raised to 400 so that the copy overlaps it for real; timing allows 4 clocks of launch jitter as seen before). The runner's logic was exercised only against a stand-in board (`test_runner_standin.py`), not the hardware.

Not done in this step: nothing yet chains batches by itself (done in step 2 as host software), and the code-store overwrite check (item 2) is not built in hardware.

## Stage 3 plan: what to include (agreed with Alan 2026-11-16, not built)

1. Task input/result convention: a job gets its inputs through a descriptor in the shared RAM and returns results there; per-core output windows planned to follow each other so the pieces are already in order.
2. Code-store protection: do not overwrite code words that a queued or running job still needs (today nothing checks; the host must wait for those jobs). Applies to program loading from far RAM (dir 2 of the copy engine) as much as to the W command.
3. Blocks of 8: today ONE code store is shared by all slices of the build (sc_sys_v8 onward). For a bigger chip the question is whether each block of 8 gets its own store; open design decision, to be settled before the Kintex growth.
5. Batch sequencer (Alan's idea, 2026-11-16): a small state machine beside the dispatcher that runs a script held in far RAM, so a large run is chained without the host in between and without changing the dispatcher. Steps: load code (far to code store), load data (far to shared RAM), submit jobs (through the same submit port the host uses), wait until every submitted job is done (compare submitted count with the done counter, which is safer than looking at empty queues), save results (shared RAM to far RAM), then either jump to the next step pointer in the script or raise a "batch complete" flag the host polls (no interrupt). Because code is only replaced after all jobs are done, it also settles the overwrite problem for chained batches. Cost on the Tang not estimated; the chip is already nearly full at 5 slices.
4. Fused widths: the hardware pool path (v5 to v12) runs every task at 1 bit per clock ("h_lw should be 0: no fusion", sc_sys_v12.v line 48). The 2/4/8/16/32-slice fused cores exist only in the earlier simulated array (`sc_sys.v` to `sc_sys_v4.v`, `uc_core_rw.v`). Bringing fusion onto the board path is not planned yet.

## Far RAM, stage 2: copy engine between the cores' RAM and the SDRAM (2026-11-16; simulation + place-and-route; NOT yet on the card)

The cores still see only block RAM. `fpga/far_copy.v` is a separate engine that moves blocks between the SDRAM ("far RAM", 2M words) and (dir 0) the shared data RAM to far, (dir 1) far to the shared data RAM, (dir 2) far to the shared CODE store, so programs can be kept in far RAM and loaded on command. It uses only the host port of the shared RAM, which already yields to the cores, and the host's code-store write port, so `sc_sys_v12` and the cores are unchanged. New files: `fpga/far_copy.v`, `fpga/host_bridge_v7.v` (clone of v6 plus commands, V reply version 10), `fpga/sc_top_pool13.v` (pool12 + `sdram_ctl` + engine; `build_tang.sh --pool 9`), `fpga/tb_top_far.v`, `test_farram_sim.py`, `run_farram_board.py`, helpers in `sdt_host.py`.

Commands (all little-endian): `F dir near(2) far(3) count(2)` start a copy; `N` status (12 bytes: busy/done/ignored, err, init_done, words moved, clocks); `D base(3) len(3)` the window of far RAM that copies may touch (default length 0 = nothing allowed; not cleared by R); `w addr(3) data(4)` / `r addr(3)` direct far word write/read (refused while a copy runs); `I`, `K cl dly inv` far RAM settings (default 2 1 0, proven). Errors: 1 far range outside the window, 2 near range past the end of the shared RAM / code store, 3 far RAM not ready, 4 bad direction, 5 timeout. A refused copy moves nothing. While a copy runs do not send M or L (poll N until done). The far RAM controller is reset by power-on only, so far RAM contents, settings and the window survive a core reset (R).

Simulation (`test_farram_sim.py`, S=2, against the checking SDRAM model, PASS): default window refuses; 16 words shared to far and back exact (to a different place); refused copies (below the window, across its end, near range past shared RAM, past code store) move nothing and leave sentinel words outside the window intact; far RAM and window survive R; a 7-word program stored in far RAM was copied into the code store and RAN with the right result (1830, equal to the ISS); a 32-word copy during a running job completes, and the job takes exactly the same clocks (24,166) as on an idle board, so a copy does not delay a core; model reports no timing violation. ## Far RAM, stage 1: the onboard 8 MB SDRAM (2026-11-16; simulation, place-and-route AND ON THE CARD)

The Tang Nano 20K has a 64 Mbit SDRAM in the package (32 bits wide, 2M words = 8 MB, no hard controller). Stage 1 is only a controller and a memory test, as its own small design, so the cores are not touched until the SDRAM is proven. Files: `fpga/sdram_ctl.v` (the controller), `fpga/sdt_selftest.v` (test engine inside the FPGA: writes N words then reads and compares, in order or in bit-reversed order that hops banks and rows, with hashed or address-pattern data, and counts clocks), `fpga/sdt_bridge.v` (UART commands V I K w r T Q), `fpga/sc_top_sdt.v`, `fpga/sc_top_sdt.cst`, `fpga/build_sdt.sh`, host side `sdt_host.py`, board runner `run_sdram_test.py`, simulation `test_sdram_sim.py` against `fpga/sdram_model.v` (a checking model of the chip written by me from the usual SDR SDRAM rules, so it is a model, not the real chip).

How it works: one word per request, 4 banks x 2048 rows x 256 columns, each access is ACTIVE then READ or WRITE with auto-precharge, refresh every 200 clocks, power-up wait 200 us then PRECHARGE, 2 refreshes and the mode register. About 12 clocks per word at 27 MHz (about 9 MB/s), so roughly ten times slower than block RAM; this is for bulk copies, never for cores' own loads and stores.

Three things I could not know without the card, so they are run-time settings, not guesses: the chip's CAS latency (2 or 3), whether the clock to the chip is inverted, and the read capture delay (0..3). `run_sdram_test.py` sweeps all 16 combinations with a quick test each, then runs the full 8 MB four ways with the middle passing setting.

Simulation (`test_sdram_sim.py`, PASS): version/info; single words in all four banks and the top of memory; the test in all four modes; scattered test at the top of memory; data kept over 0.5 million idle clocks (refresh); the model reports no timing violation (power-up order, tRCD, tRP, tRFC, tMRD, refresh interval); negative controls: a wrong capture delay fails with 256 of 256 wrong at CL 2 and at CL 3, so the test can fail. Scope: in simulation a wrong capture shows as undriven bits, so the "got" value of a failure is only meaningful on the card. Place-and-route at 27 MHz: 2,391 LUT4, 883 DFF, no block RAM, Fmax 63.7 MHz, all SDRAM pins placed by nextpnr from the in-package table (clock on IOR11B). I have not checked those pins against the board schematic.

On the card (Alan, 2026-11-16, `run_sdram_test.py`): the whole 8 MB (2,097,152 words) written and read back correctly four ways (in order / scattered, hashed / address-pattern data) with cl 2, dly 1, inv 0 (the setting worked out from the chip's rules); 12.2 clocks per word, 8.9 MB/s for writes and for reads, 1.9 s per full test. Also passed at 64K, 256K and 1M words. Quick sweep (4096 scattered words): 14 of 16 settings passed; only dly 3 with the inverted clock failed (both CL 2 and 3). So the sweep does NOT show where the true capture edge is (in simulation only dly 1 passed): my explanation, not proven, is that the data bus holds its last value after the chip releases it. Use cl 2 dly 1 inv 0, the derived setting. One incident: during the first full-size run the board's USB chip disconnected and re-enumerated (dmesg: ftdi_sio disconnect); it did not happen again in the later runs (64K to 8 MB, run without reloading), so the cause is not known (a power or cable glitch is a guess).

To run it: `fpga/build_sdt.sh`, then `openFPGALoader -b tangnano20k fpga/sdt/sc_top_sdt.fs`, then `python3 run_sdram_test.py --port /dev/ttyUSB1`. LEDs: 0 heartbeat, 1 SDRAM initialised, 2 UART rx, 3 UART tx, 4 test running, 5 last test clean.

Design agreed with Alan, not built yet: cores only ever see block RAM. A copy engine (stage 2) would be one more client of the shared RAM's single port, using only the turns the cores leave free, moving blocks between the shared RAM and the SDRAM on a command; programs are stored in SDRAM and block-copied into the code store before a job starts; each core's output window planned to follow the previous one gives the stitched result. Stage 3: task input/result convention.

## v12: status, per-core usage and trap cause read-out (2026-11-16; simulation; place-and-route see below)

## v11: code library window + stacks + a small linker (2026-11-15; simulation, place-and-route and on the board)

**What it is:** one window of the shared code store, set by the host with `Y base(2) len(2)` (board version 8; cleared by `R`), that EVERY program class may execute in addition to its own code window. Library code runs under the CALLER's limits (its private data limit and its shared-data window), so a library function cannot reach anything the calling task could not. Calls are ordinary `jal`/`jalr`; the hardware change is one extra pair of compares in the fetch check (`own_bad && lib_bad`). Files: `sc_sys_v11.v` (clone of v10), `fpga/host_bridge_v5.v`, `fpga/sc_top_pool11.v`; build with `--pool 7`.
**The linker `sclink.py` (software only):** puts the library first, then each class (its own code window), writes a start-up stub in front of every class (`li sp,TOP ; jal ra,main ; ebreak`, so a class's `main` is an ordinary function that ends with `ret` and leaves the result in a0; a `main` that calls anything must save `ra`, `push ra` / `pop ra`), prefixes class-local labels (`c<id>_`) so two classes may both have a label `loop`, adds the pseudo-instructions the assembler lacks (`ret`, `call`, `push`, `pop`), lays out the shared data RAM (a window per class: data words, then the stack if it lives there), and produces the host commands (`W`, `Y`, `B`, `X`, `M`). The assembler itself is untouched.
**Where the stack goes (per class):** `stack='private'`: top of the slice's private memory (sp = 4 x private limit); the hardware traps a stack that runs off the bottom (word 0). `stack='shared'`: top of the class's shared window; hardware traps a stack that grows below the window start, but NOT one that grows into the class's own data words inside the window. **A window belongs to a class id, not to a task:** two tasks of the same class running at the same time share one window and therefore one shared stack, which corrupts both (found in the first test run: fib(12) came out 142 instead of 144). For concurrent instances that need their own shared-RAM stack use `clone_class(new_id, of)`: same code, own window. Private stacks have no such problem (private memory is per slice).
**Tests (`python3 test_link_sim.py [S]`, `POOL=7`; programs in `link_cases.py`):** a library of `lib_sum`, `lib_fill` and a recursive `lib_fib` (3 stack words per level) is called by nine classes and two clones, 13 tasks: sum of 16 shared words through the library = 136; fib(7) on the private stack = 13; fib(12) on a shared stack = 144 (36 stack words, more than the 32-word private memory); fill-then-sum through the library = 24; two classes with the same label names = 20 and 10; **traps (all correct):** the same fib(12) on the private stack overruns the private memory; a jump into another class's code window; a library function reading past its caller's window (`lib_sum` over 16 words from a window of 4). Passes at S=1, 4 and 8, results identical. Reference check: `lib_fib` run on the independent ISS gives the same values (13, 144). **Negative control:** with the library window forced off, 8 of 13 tasks fail (the ones that call the library; the two that do not, and the three expected traps, still give their results). Regression: the v10 tests (`POOL=7 python3 test_shared_sim.py 4`), the regions test and the kernel set (`POOL=7 python3 test_board_sim.py --S 8 --imw 256 --dmw 16 --hold`: 12 of 12) all still pass on v11.
**Size / board:** S=6, 128 code words, 256 shared words: 13,432 LUT4, 3,184 ALU, 5,104 DFF, 231 LUT-RAM blocks, 19 BSRAM, Fmax 50.5 MHz (v10 same settings: 13,273 / 3,008 / 5,055 / 231 / 19 / 48.9 MHz), so the library window costs about +160 LUT4 and +180 ALU at S=6 (the extra comparators). S=8 with 128 code words does not place.
**Board result 1 (2026-11-15, Alan, own build `--pool 7 --slices 6 --code 128 --shared 256`: 13,432 LUT4, 3,184 ALU, 50.5 MHz, same as built here):** `run_link_board.py`: board reports version 8, S 6; link report as in simulation (122 code words, library 31 words); **13 of 13 tasks ok, RESULT PASS**, identical to the simulation: sum through the library 136, fib(7) on the private stack 13, fib(12) on a shared stack 144, fill-then-sum 24, the two same-label classes 20 and 10, the clone classes 144 and 24; the three expected traps (stack overrunning private memory, jump into another class's code, library reaching past its caller's window) all trap with the same a0 values as the simulation (2, 1, 65552).

## v10: a shared data RAM (2026-11-15; simulation, place-and-route and on the board)

**What it is:** one block RAM (`--shared N` words, power of 2, default 256) that every slice can reach, on top of each slice's private memory (unchanged from v9). Data word indices below 2^14 are private exactly as before; **word index 2^14 and up (byte address 0x10000 and up: `lui t0,16` gives the start) is the shared window.** The host gives each program class a window with `X prog(1) base(2) len(2)` (words [base, base+len) of the shared RAM; the program sees it as words 0.. from 0x10000); a class with no `X` has length 0, so any shared access traps (safe default). A window asked for beyond the RAM is clamped to the words that exist. Windows that overlap share data on purpose; disjoint windows are private. The v9 limit check is kept: a shared access at or beyond the window length, or beyond the window range, aborts the core as a trap and a store is blocked.
**How the port works:** one single-port 32-bit-wide block RAM; the slot counter (as for the code store) gives each slice one clock in S. A slice keeps ONE registered request (read or write, with its physical address). A LOAD stalls the core with `ce` until its word is there (the word lands in the slice's write accumulator, which is idle during a load, so no extra 32-bit register); a STORE is posted: the finished word waits in the accumulator until the slice's slot. About 2 extra clocks per shared load at S=1 and about 8 at S=8 (measured: 64 loads in a loop, 30,243 vs 30,371 clocks at S=1, 30,499 vs 31,026 at S=8: under 2% of a load-heavy loop). A store followed by a load of the same word is ordered (the read waits for the write). Cores have no atomic operations, so two tasks that write the same word at the same time just race.
**Host access (version 7, `host_bridge_v4.v`):** `M addr(2) word(4)` write, `L addr(2)` read (4 bytes back), `Z` -> size / window bit / address bits. The host never takes a clock a slice wants: its request waits (`dh_busy`) for a slot whose owner has no request, so it is safe while tasks run. `R` clears the windows but not the RAM contents (the board scripts clear the RAM first so stale results cannot pass). Files (v9 left as proven): `sc_sys_v10.v`, `uc_core_v2v.v` (v2u + a `dmem_ld` output), `fpga/host_bridge_v4.v`, `fpga/sc_top_pool10.v`, `tb_sys10.v`; build with `--pool 6 --shared N`.
**A flaw found and fixed on the way:** the first version let a host request take the RAM clock outright. The stress test (the host reading nonstop while 4 slices ran) showed that with an even number of slices the host could starve slices 0 and 2 forever (only 6 of 8 tasks finished). Now the host yields to any slice that has a request; the stress test passes at S=1, 2, 4 and 8, and fails again (0 tasks finish) if the yielding is removed, so the test does see it.
**Tests:** (1) `python3 test_shared_sim.py [S]` (whole board through the UART pins; programs and map in `shared_cases.py`): sum windows of four classes with six tasks at once, producer class then (second phase) consumer class on the same window, a store one word past a window traps and does not land (the guard word beside it is intact), a load past the length traps, a class with no window traps, a window of 100 words asked at word 244 is clamped to 12 words (word 255, the last word of the RAM, works; word 256 would alias to word 0 and traps instead), a mixed program using private and shared words; the host preloads 64 inputs and reads back 81 words, all compared. 15 tasks and 81 words, passes at S=1, 4 and 8. **Negative controls:** with the shared length check removed the four trap tests (past-the-end store, class with no window, clamped window overrun, load past the length) no longer trap, the stray stores land, and the host sees the damaged words (guard word 208 and word 0). (2) `python3 test_shared_stress.py [S] [word]` (`tb_sys10.v`): host reads one word every few clocks while S slices run eight sum tasks; every host read and every task result correct (S=1, 2, 4, 8); fails if the host is allowed to take slice clocks. (3) Regression: the v9 regions test (`POOL=6 python3 test_regions_sim.py`, 12/12) and the kernel set (`POOL=6 python3 test_board_sim.py --S 8 --imw 256 --dmw 16 --hold`, 12/12) pass on v10.
**Size (nextpnr, 256 shared words):** with 64 code words: S=8 15,279 LUT4, 3,514 ALU, 5,950 DFF, 199 LUT-RAM blocks, 25 BSRAM, 53.2 MHz (v9 S=8: 13,971 / 3,248 / 5,391 / 179 / 24 / 50.7), so v10 costs about +1,300 LUT4 and +270 ALU at S=8; S=6: 13,053 LUT4, 3,002 ALU, 5,028 DFF, 19 BSRAM, 49.6 MHz. **With the 128-word code store the tests need, S=8 does NOT place (utilisation limit) for v10 or v11.** The board candidate is S=6 with 128 code words: 13,273 LUT4, 3,008 ALU, 5,055 DFF, 231 LUT-RAM blocks, 19 BSRAM, 48.9 MHz (clock 27 MHz). Bitstreams were built here (not on the board PC): `pool10_6/sc_top_pool10.fs`, `pool11_6/sc_top_pool11.fs`; the build is deterministic for a given seed, so Alan's build should match.
**Board result 1 (2026-11-15, Alan, Tang Nano 20K, own build `--pool 6 --slices 6 --code 128 --shared 256`: 13,273 LUT4, 3,008 ALU, 48.9 MHz, identical to the numbers built here):** `run_shared_board.py`: board reports version 7, S 6, 128 code words; shared RAM 256 words, window bit 14, 8 address bits; **15 of 15 tasks ok, 81 of 81 shared words correct, RESULT PASS**, task for task the same as the simulation (the trapped tasks even leave the same a0 values). ## v9: regions - base / limit checks per program class (2026-11-15; simulation, place-and-route and on the board)

**What it is:** the host can give each program class (the 6-bit `prog` id a task already carries) a **code region** (first word and length in words of the shared code store) and a **data limit** (words of the slice's private data memory, from word 0), with the new host command `B prog(1) cbase(2) clen(2) dlen(2)` (board version 6; entries are cleared by `R`, so send them after the reset and before the tasks). At task start the slice latches the region of its task's class. From then on: every instruction fetch outside [base, base+length) or outside the store, and every load/store word index at or beyond the data limit, aborts the core as a TRAP (the task ends with the trap flag in the task table) and a wild store is blocked. A class with no entry gets the whole store and all physical data words (32, because the block-RAM shape needs at least 32).
**Behaviour change vs v8, deliberately:** a data access beyond the physical memory used to alias silently (word 35 hit word 3); it now traps even with no region set. Code fetches beyond the store used to alias; they now trap too. Nothing in the existing kernels does either (gate below).
**Files (v8 left as proven):** `sc_sys_v9.v`; `uc_core_v2u.v` (v2t plus an `abort` input that halts the core with trap, and a `dmem_act` output that says the data address is live); `fpga/host_bridge_v3.v`; `fpga/sc_top_pool9.v`; `tb_sys9.v`; build with `--pool 5` (now the default of the named-option form). Safety detail: the register/data write counters are cleared at every task start, so a task aborted in the middle of a write pass cannot leave a half-counted write for the next task on that slice. The abort lands in clock 0 of the first load/store step, before any write of that instruction.
**Tests:** (1) reference gate v8 vs v9 with no regions set, 3 workloads x 24 tasks: all ok, every duration and makespan identical. (2) Whole-board simulation, one slice running twelve programs back to back (`python3 test_regions_sim.py`; programs in `region_cases.py`): in-region programs ok; wild store (word 20, limit 4) traps and does NOT land (a later program reads word 20 = 0, word 3 still 0x1234); wild load traps; fetch one word past the end traps; a jump out of the region traps; store at word 4 with limit 4 traps; word 3 with limit 4 works; a default-class store at word 35 (beyond physical) traps; sum30 and a default-class sum20 are correct afterwards (the slice recovers). 12 of 12. **Negative control** (`NOREGION=1`, no regions set): the wild store lands (word 20 reads 0x5555), the fetch-past-end and edge-store tasks do not trap and the runaway jump hangs the slice, so the test does detect what it claims. ## v8: one shared code store for all slices (2026-11-14; simulation + place-and-route; not yet on the board)

**Idea (Alan):** code that is the same for every core should exist once. v7 held a private copy of the code in every slice (64 words x 32 bits in LUT-RAM each); v8 holds ONE copy and a small fetch register per slice.
**How:** `sc_sys_v8.v` (clone of v7) + `uc_core_v2t.v` (clone of uc_core_v2s with one extra output, `fetching` = state is FETCH; logic unchanged). The shared store is LUT-RAM with asynchronous read, so a slot is ONE clock: a free-running slot counter lets slice 0, 1, ... S-1 load its 32-bit fetch register `fw` in turn (no arbitration, wait at most S-1 clocks). While a core runs, its slice fetches the NEXT sequential word (`cur_a + 1`; `cur_a` is latched at FETCH because the core's pc rotates mid-instruction), so straight-line code finds its word already there. A branch or jump changes the address, so the core is stalled through its own `ce` input until its slot comes. A host code write invalidates every fetch register. The host still loads the code with the same `W` command (now one copy, not S).
**Results:** gate v7 vs v8 (3 workloads x 24 tasks, S=32 in the harness): all 72 tasks correct; durations are NOT identical any more (by design): +1% to +7% at S=32, because every taken branch can wait up to S-1 clocks for its slot. Whole-board simulation `POOL=4 python3 test_board_sim.py --S 8 --imw 64 --dmw 16 --lw 0 --hold`: 10 of 10 ok (e.g. sum 24403 vs 24165 clocks in v7). Place-and-route (64 code words, 16 data words), nextpnr, no hold violations:

| 8 (v7) | 13,706 | 2,876 | 4,970 | 377 | 24 | 54.5 |
| 8 (v8) | 12,887 | 2,950 | 5,077 | 153 | 24 | 54.3 |
| 10 (v8) | 14,921 | 3,376 | 5,903 | 153 | 30 | 53.8 |
S=10 places and routes with v8 (it did not with v6/v7). **S=12 fails ("Unable to find legal placement ... utilisation limit"); S=16 fails earlier: no block-RAM site left for the register file ("no BELs remaining ... ## Correction 2026-11-12 (late): duration-profile "known" bit was lost in v3 and v4 (found on the real board)

**Bug:** the profile word is {known, 24-bit running average}. Averaging a second sample was written as `{1'b1, (a + b) >> 1}`, which is 26 bits wide inside a 25-bit assignment, so the leading 1 (the known flag) was cut off. Every 2nd sample of a program class therefore turned that class back to "unknown". The first-sample path was fine, so a class sampled an odd number of times stayed known, an even number did not.
**How it showed:** Alan re-ran the same batch on the S=2 board without reloading (profile should persist across `R`): `tasks with a duration prediction: 5 of 10` and identical `waste_tail 99567` both times. Each class runs twice per batch, so each batch ended with all classes unknown. Reproduced in the whole-board simulation (0 of 10 after a reset), found by dumping the profile RAM (values present, bit 24 clear).
**Fix:** `sc_sys_v3.v` (v3.1) and `sc_sys_v4.v` (v4.1): the average is computed into its own 25-bit `davg`, then written as `{1'b1, davg[23:0]}`. Edited in place (one line plus one declaration, marked in the source) because the build scripts name these files; the unfixed behaviour is recorded in `matrix_v3b_before_fix.txt`.
**Re-measured** (`profile_matrix_v3b.py`, a reconstructed script: 48 tasks, S=32, FIFO vs longest-first cold vs warm with the profile learned on a different workload; same script on unfixed and fixed code): warm beats FIFO in **11 of 12** before the fix, **12 of 12** after. The one loser (batch, mixed widths, seed 7, +1.3%) is now -21.5%. Other rows moved by a few percent either way. Cold longest-first can still be worse than FIFO (stagger, mixed, seed 7: 73,874 vs 63,553), as expected when it has nothing to go on. Because the earlier matrix script was an inline run that was not kept, `matrix_v3_longest.txt` is not reproduced by this one; compare only the before/after files.
**Board result after the fix (Alan, 2026-11-14, S=2 rebuilt with v4.1, `--lw 0`):** run 1 (cold): 5 of 10 tasks with a prediction; run 2 straight after, no reload: **10 of 10**, so the profile now persists on the real chip. Schedule and numbers are otherwise identical in both runs (batch 179,768 clocks, waste_tail 99,567, all 10 tasks ok): sum, fib and crc all fall in the same coarse bucket (clamp(log2(d)-8,0,6) = 6, durations 24k/32k/48k) and the two mul tasks are critical, so longest-first has nothing to reorder on this batch. Not a failure of the profile; the buckets are too coarse for this mix.
**New test:** `test_board_profile.py` (whole board, S=2, same batch twice with `R` between): after the fix 10 of 10 tasks have a prediction. `test_board_sim.py --S 2` still passes. The v4 bitstreams built earlier carry the bug; rebuild before the card test.

**Board result (Alan, 2026-11-12):** S=1 bitstream, `run_board.py /dev/ttyUSB1`: `RESULT PASS`, 12/12 tasks ok, launch_err 0; durations match the simulation (sort 74195 clocks). **S=2** (`--lw 0`): 10/10 ok, launch_err 0, tasks ran on both slots side by side; waste_tail 99,567 (cold profile, uneven batch end). **Measured:**
- Simulation: v4 passes the v3 gate in 12 policy/seed combinations; makespan = 2.00 x v3 (1.998 to 2.000), as expected for the 2-clock step. Whole-board test through the UART pins passes for S=1 (1 bit/cycle), S=2 (both widths, two tasks side by side) and S=8, at a fast and at the real 115200-baud divider. 16 data words per slice are enough for the test kernels, 8 are not.

**What it means:** `uc_core_rw` is a simulation model (32-bit masked buses). It cannot be replicated 8-32 times on the Tang; at most two slices fit. The array needs the real fusable 1-bit slice, or narrow cores, in place of one masked 32-bit core per slice. The Kintex-7 480T has roughly 15x the logic, so the same model might reach a few tens of slices there; that is an extrapolation, not a measurement.

## v3b: duration-profile store, longest-first bulk queue (simulation)

Files: `sc_sys_v3.v` (parameter `LONGEST`, `PROF`), `tb_sys3.v`, `sched_tests_v3.py`, `matrix_v3_longest.txt`.

**Built:** a dedicated profile RAM (512 x 25 bits: 64 program classes x 8 widths). The submitter gives a program-class id (`h_prog`); at completion the dispatcher writes the measured duration (end minus start from the task table) into the profile, averaging with the old value. At submit, the predicted duration picks one of 8 bulk buckets (about log2 of cycles; unknown goes to the top bucket so it is run and learned first). The dispatcher takes the highest non-empty bucket: no queue scan and no sorting. Critical tasks stay FIFO. LONGEST=0 is the old behaviour.

**Measured (12 cases: batch/staggered x uniform/mixed widths x 3 seeds; profile learned on a different workload):**
- Makespan vs FIFO bulk: better in 11 of 12 cases, worse in 1 (batch, mixed widths, seed 7: +12.7%). Mean change -6.0% for batch and -4.9% for staggered; best single case -19.3%. Per-row numbers in `matrix_v3_longest.txt`.
- Critical latency: unchanged within noise (critical class is untouched).
- Cold start (empty profile): identical to FIFO in a batch, since every task is submitted before any has finished; staggered arrivals learn online and gain a little.
- Prediction error is large (15% to 75% mean) because task size varies 2-5x inside one program class. A size hint from the submitter would be the next step.

**An earlier version keyed the profile on the code address; that was wrong (each task has its own address, so it only worked as a per-task memory and collided). Replaced by the class id.**

**Caveats:** 3 seeds; bucket resolution is a factor of 2; the prof RAM is cleared at reset only in simulation; not synthesised.


## v3: request table, task table, priority dispatcher (simulation, Verilator)

Files: `sc_sys_v3.v`, `tb_sys3.v`, `sched_tests_v3.py`, `matrix_v3.txt`.

**Built:** a 16x16 request table (set-only producers, clear-only watcher, set wins a same-cycle clear). Lines 0-63 mean "core with leader slice n finished"; lines 64-255 are peripheral lines whose payload is written first and logged once. A task table stores arrival, start, end, a0, trap, state and the slice the task ran on. There are two queues (critical, bulk), a wake-on-event dispatcher (no idle polling), best-fit placement, a GUARD/MAXPASS starvation guard, and waste counters.

**Measured:**
- Gate: all tasks complete, none trap, every a0 matches the ISS, `launch_err` = 0. Events logged exactly once with the right payload, served within 8 cycles (4 configs x 4 seeds, 40 events each).
- Regression: with PRIO=0, BESTFIT=0 it matches the v2 strict FIFO within 0.04%.
- Priority: critical-task latency falls by about 2x to 2.4x (batch) and 1.1x to 1.6x (staggered), at the cost of makespan, +4% to +9% in batch runs (full table in `matrix_v3.txt`).
- Best-fit: no effect when widths are uniform (aligned groups cannot fragment). With mixed widths 1..16 it changed 10-11 of 48 placements on 2 of 3 seeds, and cut makespan by up to 2.1% (batch) and 10.8% (staggered, seed 3). On one batch seed (7, PRIO=0) it was worse: worst wait 34023 -> 42137. So it is not a guaranteed win.
- Earlier worry (identical results with BESTFIT 0/1) was checked: uniform widths give identical placements; mixed widths do not. The code path is live.

**Not measured / caveats:** 3 seeds only, so the best-fit gain is indicative. Waste breakdown counters exist but are not tabulated here. Not synthesised for area. The 16x16 table is not yet attached to real I/O cores.


## Read this first (most recent)

**Dispatcher policies (12 Nov) -- overtaking and a reserved region give small gains; priority-aware dispatch is the missing lever.**
- `sc_sys_v2.v` (old `sc_sys.v` untouched): look-ahead overtaking (`LA`, with a `MAXPASS` anti-starvation limit), a reserved region for critical tasks (`RESERVE`), a critical flag per task. With `LA=1`, `RESERVE=0` it reproduces the earlier makespans exactly.
- Mean of 5 workloads of 48 tasks, every run through the correctness gate. Critical 8 / bulk 4 wide, strict FIFO versus reserve 8 + overtake 16: critical latency 22809 -> 21264 (batch, -7%) and 14978 -> 12593 (staggered, -16%), makespan unchanged.
- Reserving 16 of 32 slices hurt badly (makespan +25-30%, utilisation 63-66%). Reserve without overtaking also hurt slightly.
- Biggest effect was rescuing a bad width choice (critical 32 wide / bulk 1): 382901 -> 208775 cycles, still 21% utilisation. The anti-starvation limit kept worst-case waits within a few percent of strict FIFO.
- Submitting critical tasks first (host side, last entry) beat every dispatcher setting here for critical latency (about 6500 versus 12000-23000, different workload set, batch only). Next candidate: priority-aware dispatch (two queues, critical served first), which also covers staggered arrivals.
- Not the 16x16 request table: the queue here is for task submission by the host. The event table with its watcher core (hardware events, I/O cores) is still design-only.

**Array + dispatcher (12 Nov) -- width chosen per task works; critical tasks get ~3.7x lower latency at about the same total time.**
- `uc_core_rw.v`: width chosen at task start. 276/276 regression runs match the reference; cycles equal v2 (+1 start cycle).
- `sc_sys.v`: 32 slices, a core instance per slice, private regfile and data memory per instance, shared code image, submission and completion queues, and a dedicated dispatcher FSM (one-cycle aligned-group search, launches 3 cycles apart, strict FIFO). No interrupts; the host polls the completion queue.
- Correctness gate: every task completed, none trapped, every a0 equal to the reference simulator's. Passed in every run (random widths and arrival times, and all policy runs).
- Mean of 5 workloads of 48 tasks (makespan / critical latency / bulk latency, cycles): fixed W=32 66441 / 38259 / 33783; fixed W=8 43844 / 24078 / 21757; fixed W=4 longest-first 37306 / 29868 / 28039; critical W=8 + bulk W=4, critical first 44378 / 6496 / 26001.
- Reading: fixed wide is the worst for throughput; width-per-task buys low latency for the critical class at ~1% makespan and ~19% worse bulk latency; best raw makespan came from a fixed narrow width with long tasks first. One workload family, one dispatcher policy.
- Strict FIFO is fragile: a wide task among narrow ones can leave the pool mostly idle (9% utilisation seen). Backfill or reserved regions are the obvious next policies.
- Note: at W=32 a core costs 128 slice-cycles per instruction versus 66 at W=1 (fixed fetch/setup passes), so per-slice throughput is better narrow.
- Verilator is needed for the array runs (about 100x faster than iverilog here: 0.4 s versus 88 s for the same workload).
- Not built: loader/readout over JTAG or UART, real memory banking, any area figure for the array.

**v2 (12 Nov) -- pc, immediate and address register held as digit shift registers: 9-45% fewer LUTs, identical behaviour.**
- Measured first: knocking out blocks of v1 at W=1 showed the indexed 32-bit register access cost ~270 of 469 LUT4 (pc write ~91, address write ~75, imm read ~46, pc read ~34, imm decode ~27).
- `uc_core_v2.v`: pc rotates/inserts one digit per cycle, address register is insert-only, immediate is loaded at setup and rotated. v1 left untouched.
- 276/276 runs match the reference; cycle counts identical to v1.
- iCE40 LUT4 v1 -> v2: W=1 469->326, W=4 478->383, W=8 547->484, W=16 740->677, W=32 1258->1108. Xilinx LUT6: W=1 342->239, W=8 608->405, W=32 1616->890. Flops rise by 32 (the immediate ring).
- The W=1 floor is still ~326 LUT4, well above SERV; the rest is decode, immediate formation, control and the shift/compare logic (not yet broken down).
- Gowin (Tang Nano) counts from yosys 0.33 are unreliable and not recorded; measure with the Gowin tool.
- Harness bug found and fixed: the testbench filename buffer was 32 characters and silently truncated longer output names.
- Targets stated by Alan: Tang Nano 20K (Sipeed) and Kintex-7 XC7K480T with no PCIe side, so JTAG only. A loader/readout path is needed for each (Xilinx JTAG user register; Tang Nano UART).

**First prototype (12 Nov) -- one RV32I binary runs correctly at W = 1, 2, 4, 8, 16, 32 bits per cycle.**
- Correctness: 276 runs (6 directed programs and 40 random programs, each at all 6 widths) match an independent reference simulator on final registers, data memory, pc and instruction count. A planted bug in the signed-compare logic was caught by the suite (5 failures), so it can fail.
- Cycles per instruction (random programs, average): W=1 69.8, W=2 36.0, W=4 19.1, W=8 10.6, W=16 6.4, W=32 4.3. Model: ALU and branch 2N+2, load/store 3N+2, N = 32/W.
- Area (yosys, iCE40 4-LUT, core logic only): W=1 469 LUT4, W=2 476, W=4 478, W=8 547, W=16 740, W=32 1258; flops about 118-122 at every width.

**What the numbers say (measured, not guessed):**
- Width buys a lot of speed (about 16x from 1 to 32 bits) for little area (about 2.7x). Best LUTs x CPI is at W=8 to 16.
- The narrow end is not small: about 470 LUTs even at W=1 (SERV is about 125 on 7-series, taken from its project page, not measured here).
- Marginal cost of widening is roughly 24-32 LUTs per added bit between W=8 and W=32, so a 512-slice array extrapolates to more than the 10k LUTs first assumed. That is an extrapolation, not a measurement.

**Hypothesis, not yet tested:** the floor comes from `pc`, `ir` and the address register being 32-bit registers read and written through variable-index muxes. Turning them into digit shift registers should cut it.

**Simplifications in this prototype:** instruction fetch is a whole word in one cycle; word loads/stores only, aligned; no fetch/execute overlap; register file and memories not counted in area.

## Decisions so far
- One ISA (RV32I) at every width; width is a datapath property, not an ISA property.
- Width is allocated at task start, not changed mid-task (re-slicing live state is disruptive).
- No interrupts. Task queue and dispatcher are built (simulation); the 16x16 event table and I/O cores are designed on paper only.
- Scheduling is done by a dedicated hardware dispatcher, not by a compute core, so no task ever runs scheduling code.
