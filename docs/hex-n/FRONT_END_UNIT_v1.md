# Hex-N front end for the open unit, v1 (1 Nov 2026)

Alan, 21:02: 'now we need the front end to be caught up to match the new functions'. Chosen shape (21:04, from three options): **one general ESP32 gateway sketch plus a PC module**, with the intake and analysis engine getting a 'send to unit' step. Alan, 21:05: once that is stable, it may become **hosted on the ESP32 itself**, capturing data through the ESP32's own pins, the Tang's pins, or uploaded directly to the ESP32. The design keeps that path open (see the last section).

## The three pieces

1. **`tools/esp32/hexn_gateway/hexn_gateway.ino`** (ESP32). Only moves words: `ID`, `R reg`, `W reg value`, `WW addr w1 w2 ...` (up to 255 words), `RW addr n`, `SPD hz`; text lines, numbers in hex, 921600 baud, one reply line `OK ...` or `ERR ...`. Needs the open unit builds (v2 bridge). Close the Arduino Serial Monitor before running the PC tool (only one program can hold the port).
2. **`tools/hexn_open_host_v1.py`** (PC). Class `OpenUnit` over any link with `.cmd(line)`: `mode`, `preset`, `status` (mode, readiness flags, preset active, raw results, live level of the 16 pool pins by Tang pin number), `load_space` (reaction, Morse, decode, glyph, presets), `binning`, `set_inputs` / `set_outputs` / `pins_default` (by Tang pin number), `define_preset`, `restore`, `stream` (raw scorer words with one or two judges; long streams are cut into runs and the judge state is carried across runs), `load_judges`. `SerialLink` is the real link (needs `pyserial`).
3. **`tools/hexn_front_unit_v1.py`** (PC). From the same files and task as the intake engine (`--future`, `--rule`, `--label`; the intake file is unchanged and reused for loading and features): learns the table on the training part, **fits it to the unit** (the scorer has 8 detector slots, 12 bins, two classes, whole-number weights): detectors are ranked on the TRAINING part only, the best 8 are kept, weights are made whole numbers (scale 4), then the test rows are sent as raw words and **every result is checked against the bit-exact reference**. `--bias-b N` also loads judge B with the same weights and bias N, so each row gets two answers. `--out pkg.json` saves the package (chosen detectors with names and bin edges, the table words, the scale, the AUCs).

## Checked so far (model only, no hardware)
`tools/hexn_open_emu_v1.py` is a Python model of the unit behind the gateway's text protocol (registers, scratch RAM, table spaces, presets, raw stream with one or two judges, using the bit-exact scorer reference). It proves the PC side sends the right words in the right order; it does not model the games, display, pins or timing. The unit itself was proven by the Verilog simulations and the board runs.
- `tests/vm/test_hexn_open_host_v1.py` (5 pass; shown to fail when the judge state is not carried between runs): the register encodings equal the ones the Verilog tests use; modes, presets, tables, pins, binning; a single-judge stream; two judges over a 900-result stream cut into runs; control words inside a stream.
- `tests/vm/test_hexn_front_unit_v1.py` (passes): the four real River Exe files, task `--future flow --q 0.9 --hours 6`: 16 detectors available, 8 kept; whole-number table within 0.01 AUC of the same detectors in floating point; 0 result words wrong against the reference; judge B (bias -40) raises fewer false alarms than judge A.
- The gateway sketch is compile-checked with a stub only.
**Honest number:** fitting 16 detectors into the unit's 8 slots costs accuracy. On River Exe the 8-slot whole-number table gives AUC 0.9626 on the test part (24,504 rows, 603 positive), against 0.976 for the full 16-detector table in the intake engine. A unit with more detector slots (the scorer's NS) would close part of that gap; not built.
Model run (not hardware), 1,000 evenly spaced test rows: judge A caught 26 of 26 positives with 216 false alarms; judge B (bias -40) caught 20 with 58 false alarms.

## Hosting it on the ESP32 later (Alan, 21:05)
The split is chosen for that. The gateway holds no logic; all the logic is in `hexn_open_host_v1.py` (plain steps over `.cmd(line)`) and the fitting in `hexn_front_unit_v1.py`. Moving it onto the ESP32 means (a) the same steps written in the ESP32's language, calling the SPI functions directly instead of the serial protocol, (b) a way to feed it data: the ESP32's own pins, the Tang's pin pool (levels are already readable in the status word, and the raw stream accepts words), or a file uploaded to the ESP32, (c) the learning step either done on the ESP32 (the counted-detector table refresh is a few tallies per row, so it is small) or done on the PC once and uploaded as a package. Nothing about this is built; the package file (detectors, bin edges, table words) is the interface between the two.
