# Hex-N front end for the open unit, v1 (1 Nov 2026)

Alan, 21:02: 'now we need the front end to be caught up to match the new functions'. Chosen shape (21:04, from three options): **one general ESP32 gateway sketch plus a PC module**, with the intake and analysis engine getting a 'send to unit' step. Alan, 21:05: once that is stable, it may become **hosted on the ESP32 itself**, capturing data through the ESP32's own pins, the Tang's pins, or uploaded directly to the ESP32. The design keeps that path open (see the last section).

## The three pieces

1. **`tools/esp32/hexn_gateway/hexn_gateway.ino`** (ESP32). Only moves words: `ID`, `R reg`, `W reg value`, `WW addr w1 w2 ...` (up to 255 words), `RW addr n`, `SPD hz`; text lines, numbers in hex, 460800 baud, one reply line `OK ...` or `ERR ...`. Needs the open unit builds (v2 bridge). Close the Arduino Serial Monitor before running the PC tool (only one program can hold the port).
2. **`tools/hexn_open_host_v1.py`** (PC). Class `OpenUnit` over any link with `.cmd(line)`: `mode`, `preset`, `status` (mode, readiness flags, preset active, raw results, live level of the 16 pool pins by Tang pin number), `load_space` (reaction, Morse, decode, glyph, presets), `binning`, `set_inputs` / `set_outputs` / `pins_default` (by Tang pin number), `define_preset`, `restore`, `stream` (raw scorer words with one or two judges; long streams are cut into runs and the judge state is carried across runs), `load_judges`. `SerialLink` is the real link (needs `pyserial`).
3. **`tools/hexn_front_unit_v1.py`** (PC). From the same files and task as the intake engine (`--future`, `--rule`, `--label`; the intake file is unchanged and reused for loading and features): learns the table on the training part, **fits it to the unit** (the scorer has 8 detector slots, 12 bins, two classes, whole-number weights): detectors are ranked on the TRAINING part only, the best 8 are kept, weights are made whole numbers (scale 4), then the test rows are sent as raw words and **every result is checked against the bit-exact reference**. `--bias-b N` also loads judge B with the same weights and bias N, so each row gets two answers. `--out pkg.json` saves the package (chosen detectors with names and bin edges, the table words, the scale, the AUCs).

## Checked so far (model only, no hardware)
`tools/hexn_open_emu_v1.py` is a Python model of the unit behind the gateway's text protocol (registers, scratch RAM, table spaces, presets, raw stream with one or two judges, using the bit-exact scorer reference). It proves the PC side sends the right words in the right order; it does not model the games, display, pins or timing. The unit itself was proven by the Verilog simulations and the board runs.
- `tests/vm/test_hexn_open_host_v1.py` (5 pass; shown to fail when the judge state is not carried between runs): the register encodings equal the ones the Verilog tests use; modes, presets, tables, pins, binning; a single-judge stream; two judges over a 900-result stream cut into runs; control words inside a stream.
- `tests/vm/test_hexn_front_unit_v1.py` (passes): the four real River Exe files, task `--future flow --q 0.9 --hours 6`: 16 detectors available, 8 kept; whole-number table within 0.01 AUC of the same detectors in floating point; 0 result words wrong against the reference; judge B (bias -40) raises fewer false alarms than judge A.
- The gateway sketch is compile-checked with a stub only.
**Honest number:** fitting 16 detectors into the unit's 8 slots costs accuracy. On River Exe the 8-slot whole-number table gives AUC 0.9626 on the test part (24,504 rows, 603 positive), against 0.976 for the full 16-detector table in the intake engine. A unit with more detector slots (the scorer's NS) would close part of that gap; not built.
Model run (not hardware), 1,000 evenly spaced test rows: judge A caught 26 of 26 positives with 216 false alarms; judge B (bias -40) caught 20 with 58 false alarms.

## Hosting it on the ESP32 later (Alan, 21:05)
The split is chosen for that. The gateway holds no logic; all the logic is in `hexn_open_host_v1.py` (plain steps over `.cmd(line)`) and the fitting in `hexn_front_unit_v1.py`. Moving it onto the ESP32 means (a) the same steps written in the ESP32's language, calling the SPI functions directly instead of the serial protocol, (b) a way to feed it data: the ESP32's own pins, the Tang's pin pool (levels are already readable in the status word, and the raw stream accepts words), or a file uploaded to the ESP32, (c) the learning step either done on the ESP32 (the counted-detector table refresh is a few tallies per row, so it is small) or done on the PC once and uploaded as a package. Nothing about this is built; the package file (detectors, bin edges, table words) is the interface between the two.

## Version 2 of the link (1 Nov 2026, after the first real run)
The first real run (Alan, 21:35 to 21:38) found: the greeting was read as a reply (fixed); then 996 of 1,000 results wrong; then the diagnostic showed 1 and 10 words pass and 100 words get NO reply. Reading of the cause, from that pattern and not yet confirmed on the board: the ESP32's receive buffer is 256 bytes by default and the sketch read one character at a time, too slow for 921,600 baud, so long lines were cut (no newline, no reply) or damaged in the middle (a silently different word, which explains the wrong results). Changes:
- Gateway v2: 8 KB receive buffer (`setRxBufferSize` before `begin`), one bulk read per pass, **460,800 baud**, and a checksum: every command ends with ` #HHHH` (16-bit sum of the bytes before it), a wrong sum is refused with `ERR checksum`; every OK reply carries one too.
- `SerialLink`: always sends the checksum, verifies every reply, and on a missing, refused or damaged exchange clears both sides and resends (up to 4 tries). A line damaged on the way can no longer change a word silently; `link.retries` counts how often it had to resend.
- Test (`tests/vm/test_hexn_open_host_v1.py`, 8 pass in all): a flaky-line model damages every 7th command, drops the newline of every 11th and damages every 9th reply; a 150-row two-judge run still returns exactly the reference words after many resends. It fails if the reply check is switched off.
**You must upload the new `hexn_gateway.ino` to the ESP32** (the old one speaks 921,600 baud without checksums).

## The front end as a web page (1 Nov 2026) — `tools/hexn_front_web_v1.py`
The command line stays; this adds a page in your browser that does the same thing with buttons. It only CALLS the proven code (`hexn_intake_v1`, `hexn_front_unit_v1`, `hexn_open_host_v1`); nothing there was changed.
- **Start it** (on the PC that has the ESP32 plugged in): `python3 tools/hexn_front_web_v1.py`, then open `http://127.0.0.1:8765`. Stop with Ctrl+C. It listens on this computer only. Needs pyserial for the real unit (the model works without it).
- **The page**: 1 pick data files (the River Exe files are listed; 'Choose Files' adds your own csv / csv.gz), press 'Read the chosen files'; 2 choose the task (a sensor will cross a line soon / an existing column / a rule you type); 3 choose where to run (software model, the real unit through the ESP32 and its serial port, or fit only), rows to send, optional judge B bias; press Run.
- **Shows**: the task in words, training and test rows, AUC (whole-number table and float), the 8 detectors with their bin edges, and for a run on a unit the big line 'Every answer matches the reference' (green) or the count that differ (red), AUC from the unit's own answers, and the caught / missed / false alarms / correctly quiet counts for judge A and judge B.
- **Two safeguards** (added after a first board run on the ocean file failed once and then passed twice, cause unknown): if answers differ from the reference the page lists the first five rows with what the unit gave, what the reference says and the bins sent; and a file with no header row (its first data row read as column names) gets a red warning when the files are read. Both come from `tools/hexn_front_unit_v2.py`, a thin clone of v1 (v1 untouched); test `tests/vm/test_hexn_front_unit_v2.py`.
- **Not in it yet**: saving the package (use `--out` on the command line), the hardware clear button, live data from the ESP32's pins, hosting on the ESP32 itself.
- Test: `tests/vm/test_hexn_front_web_v1.py` (starts the server, runs the River Exe files on the model with two judges, 0 wrong; refuses unlisted paths; clear errors for a missing task or port). The page was also driven in a real browser (Chromium). **On the board** (22:08 to 22:14, `/dev/ttyUSB3`): River Exe files 0 wrong, AUC 0.9711, judge A 26 / 216; the ocean file 0 wrong on the page and on the command line (AUC 0.7233, 370 / 381 / 27 / 222), after one earlier failed run (all 1000 differed, AUC 0.5000) that has not repeated and whose cause is not known (ledger, 1 Nov 11:25 to 11:45).

## A different kind of data: hyperspectral pixels (DLR HySU, 1 Nov 2026)
Alan, 01:53: 'another sort of data, not sure if the system could handle it, but give it a shot' (the DLR HySU spectral-unmixing benchmark, supplied as a zip). `tools/hexn_hysu_to_csv_v1.py` turns the image into `docs/hex-n/data/hysu/hysu_pixels.csv.gz`: one row per pixel (10,518 of 10,578; 60 pixels that lie in two or more material ROIs are left out), 135 band columns (nm417 to nm903), and a `material` column (the five target materials or `background`). No position is written. Task as a rule, e.g. `--rule "material == 'redMetal'"`, or in the web page 'a rule I type'. No time column, so the front end splits the pixels at random 60 / 40.
**Model results** (software model of the unit, ALL 4,208 test pixels sent, judge A 0 answers wrong against the reference every time; judge B bias -40 is the River Exe setting, NOT tuned here): AUC on the test part, whole-number table: red metal 0.9795 (10 positive test pixels), bitumen 0.9825 (13), blue fabric 0.9578 (15), red fabric 0.9361 (21), green fabric 0.9961 (3), any target 0.8565 (62). Detectors kept are neighbouring bands (for example 704 to 725 nm for red metal and red fabric, 541 to 559 nm for blue fabric).
**Read these with care**: (1) very few positives in the test part (3 to 21 per material), so each AUC rests on a handful of pixels; (2) the split is random over pixels, and neighbouring pixels of the same target are alike, so training and test pixels of one target are neighbours: the numbers are probably optimistic compared with testing on a target the table never saw (not measured); (3) 'background' means 'not in a target ROI', which includes pixels next to a target that may hold some of it; (4) with one fixed bias, judge A and B behave very differently by material (bitumen: A raised 3,046 false alarms, B caught none), so the bias needs setting per task; (5) the benchmark's own job, estimating how much of each material is in a pixel (unmixing), is not something the two-class scorer does: this is detection only. NOT run on the board yet (Alan was away from the PC).
