# The carrier build system's own frontend: two real selection modes (Alan/Claude, 2026-09-15)

*A direct extension of `#735`'s own VIXb scoping pass, per Alan's own
follow-up design: two real ways to choose which cores a generated VIX
Carrier holds -- (A) the person names them directly, or (B) the system
derives them from an already-existing ICM file. Checked directly
against the real ICM v3 implementation before designing anything, not
assumed from what the format "should" have. Nothing built here.*

## Real, checked-first finding: this needs one real prerequisite that doesn't exist yet

**What ICM v3 actually has today, confirmed by reading `nano/icm_v3.py`
directly:** no separate header field listing "structures used and
their count." Each placed cell is one `IcmV3Record`, carrying its own
`core: str` value; the SET of cores actually in use is something you
derive by scanning every record, not something stored as a pre-
computed summary. There's already a real, direct precedent for exactly
this derivation: `minimum_shell_version(records)` scans `{r.core for r
in records}` and returns the minimum old-lineage shell version that
can run them. Mode B below needs the same shape of function, just
returning the real core set itself rather than a version string.

**The real gap this surfaces, worth stating plainly rather than
glossed past:** ICM v3/v4 are scoped to the OLD core lineage only
(nano/ram/adder/accumulator/comparator/latch/sequencer/branch) --
confirmed directly, not assumed. There is no ICM format for VIX
Carrier at all yet (`#732`'s own status table already says so), and
`mul`/`priority` aren't valid `core` values in any existing ICM format.
**Mode B genuinely cannot work today, not because the derivation logic
is hard, but because the file format it would read from doesn't cover
VIX Carrier yet.** This is a real, separate, necessary piece of work,
not a detail inside the frontend itself -- named as its own item
below, not folded silently into "build the frontend."

## The real design: both modes converge on the same input, to the same generator

**Mode A (manual selection).** The person supplies an explicit list of
core names (`["adder", "ram", "mul", "priority"]`). This is the direct,
minimum-viable use of `#735`'s own recommended Option B generator --
no new mechanism beyond the generator itself, which is still
unbuilt (`#735`'s own real, honest status).

**Mode B (ICM-derived selection).** The person supplies a path to an
existing ICM file instead of a core list. The frontend:
1. Loads the file and derives the real, actual set of cores in use --
   the same real scan `minimum_shell_version()` already does, extended
   to cover VIX's own real core names once a VIX-compatible ICM format
   exists (the real prerequisite named above).
2. Feeds that derived set into the SAME generator Mode A uses --
   Mode B is not a separate code path, it's a different, real SOURCE
   for the same real input the generator already needs.

**Real, honest consequence worth stating directly: Mode B can only
ever run AFTER a real ICM file exists** -- generated by the compiler,
or written by hand -- exactly as Alan's own framing states. This isn't
a limitation to work around; it's the real, correct ordering. A
carrier can't be "sized to fit a program" before that program's own
real shape (which cores it actually places, and where) is known.

## The real, honest "fully loaded vs. trimmed" choice, and who makes it

**Both modes produce a core LIST. What happens next is a real,
separate, third choice, made by whoever is doing the building, not
baked into the ICM file itself:**
- **Trimmed**: generate a carrier holding exactly the derived/chosen
  core set, nothing more. Real, direct benefit: less real fabric area
  used, meaningful on FPGA and in VM simulation, where "how much of the
  chip does this actually cost" is a real, live question.
- **Fully loaded**: generate (or use the already-existing) carrier
  holding every real core type this project supports, regardless of
  what the specific ICM actually needs. Real, direct benefit: the SAME
  ICM file works on ANY fully-loaded carrier, and — critically — a
  fully-loaded carrier is a real, strict SUPERSET of any trimmed one's
  own capability. An ICM built assuming a trimmed set can always run
  on a fully-loaded carrier; the reverse isn't true (an ICM using a
  core a given trimmed carrier doesn't hold simply can't run there,
  the same real way it can't run on a shell version too old to support
  it, `minimum_shell_version()`'s own existing precedent).

**Real, direct consequence Alan named explicitly, worth restating as a
first-class part of this design, not an aside:** the SAME ICM file can
be handed to a different person, who independently chooses trimmed or
fully-loaded for their OWN build, without needing to regenerate or
modify the ICM itself at all. The ICM describes the program; the
build-time choice of carrier shape is a separate, real decision made
by whoever's doing the building, every time, not fixed at ICM-creation
time.

## The real, honest FPGA/VM vs. ASIC distinction, baked into the design rather than left implicit

**Trimming is only ever a real, meaningful choice on FPGA or in VM
simulation.** Both can, in principle, be built or configured to
exactly the real cores a given ICM needs, saving real, measurable
resource (fabric area on FPGA, nothing wasted in the VM's own
modeling). **An ASIC has no equivalent real choice, and this design
should say so directly rather than let someone attempt a "trimmed
ASIC" that doesn't mean anything:** once fabricated, silicon is a
fixed, permanent artifact — there's no way to "not include" a core
after the die is cast, the way trimming means on FPGA. **The real,
correct consequence: an ASIC target is ALWAYS the fully-loaded case,
by necessity, not by choice** -- carrying every real core type this
project supports, and using the SAME ICM file (built for the general,
fully-loaded case, or even one originally sized for a specific trimmed
FPGA build) purely to select, at runtime, which of its own
already-fixed cores actually get used via `core_select` -- exactly the
real mechanism `core_select` already provides today. **This means an
ASIC build never needs Mode A or Mode B's own trimming decision at
all** -- both modes remain useful for CHOOSING what to place in the
ICM's own program, but the ASIC's own carrier shape question is
already answered, always, as "everything."

## Real, honest, open questions and prerequisites -- named precisely, not smoothed over

- **The real prerequisite named above, restated as its own item, not
  buried in prose:** a VIX-compatible ICM format (or an extension of
  ICM v3 covering VIX's own 11-and-growing core names) needs to exist
  before Mode B can do anything real. This is real, separate,
  necessary work, not a detail this frontend can route around.
- **`#735`'s own generator (the thing both modes ultimately feed) is
  itself still unbuilt** -- this frontend design assumes it exists,
  the same way `#735`'s own note left it as a recommendation for
  review, not a completed tool.
- **Real, honest, not-yet-answered question: what happens when an ICM
  file requests a core the current project doesn't know how to build
  a `_v4c` variant for at all** (a hypothetical future core, or a typo
  in a hand-written ICM)? A real, clear error naming the missing core
  is the obvious answer, matching this whole project's own established
  discipline elsewhere (`resolve_core_file()`'s own real, clear
  FileNotFoundError, `#734`) -- not yet built or tested.
- **Real, honest, not-yet-decided: does "fully loaded" mean the
  CURRENT `unicell_vix_carrier_v1.v` file directly** (already built,
  already verified, holding all 11 real cores) **or a freshly-generated
  "all cores" output from the same generator Mode A/B use for trimmed
  builds?** Using the existing file directly is simpler and avoids
  regenerating something already proven; generating it fresh keeps
  exactly one real code path for every carrier shape. Real tradeoff,
  not resolved here.

## Real, honest status

A frontend design, building directly on `#735`'s own recommendation,
not a build plan on its own. No RTL, no ICM format changes, no
generator, nothing built. The real ordering this note makes explicit:
`#735`'s own generator has to exist before Mode A means anything; a
VIX-compatible ICM format has to exist before Mode B means anything
at all, even once the generator does.
