Every picture on the earlier pages was drawn by a small script in the page itself. The VM is the real thing those pictures imitate: a program that holds a whole design as cells, advances it one tick at a time, and lets you look at every value. This page is a map of it: what the parts are, where they live, how they connect, and how far each part has been trusted.

2. The two modes

There is one idea of a cell grid and two versions of the VM, because the hardware has two relatives.

Standard modeMirror mode for the flex family
Name in the codeSuperGridFlexGrid, a subclass of it
ModelsThe original cell grid, the reference for the Arria 10 lineThe flex cells (the ones in this manual), with their valid/ack handshake
Word widthChosen when the grid is made (default 32)Chosen to match the target: 18 for the Tang Nano 20K
How it is trustedIt is the long-standing referenceEach flex cell was added one at a time and checked against the Verilog that the generator really produces, at word widths 4, 8, 18, 32 and 36
When the hardware has a limit–It refuses, and says why, instead of guessing

The rule behind this: the Verilog is the ground truth. The VM comes before any fit to a real chip, because a fit can only be proved by a VM that can mirror the target. An empty FlexGrid was first proved identical to a SuperGrid, then flex behaviour was added one cell at a time.

3. Run it yourself

The same engine that sits behind the composer's Run / Step panel can be driven from a few lines of Python. This loads the library adder from the Composer page, puts 7 and 5 on its two input cells and runs it at 18 bits:

import sys
sys.path.insert(0, "tools"); sys.path.insert(0, "nano")
from flex_layout_view_v1 import Layout
from flex_layout_sim_v1 import StepSim

layout = Layout.load("nano/library_std/add.icm.json")
sim = StepSim(layout, width=18)       # the flex (mirror) VM at 18 bits
sim.inject({"A": 7, "B": 5})          # values on the two input cells
ticks = sim.run()                     # step until nothing moves any more
print("settled after", ticks, "ticks")
for line in sim.log: print(line)
print("r =", sim.seen["R"])

Output from running exactly that, in the repository folder:

settled after 21 ticks
tick 0: item 1 in: a=7, b=5
tick 18: out r = 12
r = [12]

Use sim.step(1) instead of sim.run() to advance one tick at a time, and sim.state() to see every cell's value and whether it is waiting to be taken. Doing that here, the number of cells holding a value was 2 for ticks 1 to 9, 1 for ticks 10 to 17, and 0 from tick 18 on. This is the measurement drawn on the Tour page, now seen as it was taken.

Why 18 ticks for one addition? The adder itself is one cell. The other 26 cells are the input and output ports and the relays that carry the words along the routes. The VM counts every hop, and so does the hardware.

4. How far to trust it

  • Checked against the Verilog, cell by cell. Each flex cell's behaviour in FlexGrid was compared with the generated Verilog, run in a simulator, at several widths. That work found and fixed real faults in the Verilog itself (a cell that captured while not yet configured, and some width limits).
  • Checked against the board. Ten self-checking designs (relay chains, adders with stalls, the three priority modes, the ram hold and one-shot) run on a real Tang Nano 20K and match what FlexGrid says. That shows the cell logic and the handshake on real silicon, at 27 MHz and small sizes. It does not show capacity or speed.
  • The test suite. More than two thousand tests live under tests/vm. A full run takes hours, so they are run on demand.
  • Freeze, save and restore of a running design has only been run in simulation, never on a physical card.
  • The GPU array backend is written, but its header says it was written where no GPU was available, so the GPU path is untested there. Even in its design only the choice of which cells are ready to act is done in bulk; each cell's own logic still runs as ordinary Python.
  • Not the same as timing on a chip. The VM counts ticks of the design, not nanoseconds. The board's clock speed is a property of the chip and the build.
