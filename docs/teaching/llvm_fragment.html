LLVM IR is the plain-text form that many compilers (the one behind C, C++ and Rust among them) write out just before they produce machine code. It looks like assembly for an imaginary tidy processor: every step is one small named operation. UniCell can take that text and turn it into a design of cells, so a function written in an ordinary language can, in principle, become something this machine runs. This page takes real functions through the real compiler, shows what comes out, and is honest about what it refuses.

3. What the cell roles are


A function with three operations did not become three cells. Using the first example, the compiler's job was to turn each line into a working cell and to make sure the right numbers reach it in the right order:


    
  
  • Compute cells are the arithmetic: one adder or multiplier for each add or mul line. The sub %p, 3 line became an adder that adds 0xFFFFFFFD (that is, -3), which is cheaper: the compiler's own note says so.
    • 
  
  • Argument and constant cells hold the inputs and the literal numbers until they are used.
    • 
  
  • Ordering cells (priority cells) sit in front of an arithmetic cell and let its two operands in one at a time instead of racing. As the DSL page showed, two operands arriving on the same tick can lose one. The compiler puts one in front of every two-operand operation, so the answer does not depend on how long each route turned out to be.
    • 
  
  • Relay cells carry a number along a path across the grid, one square per tick, because cells only talk to their immediate neighbours.
    • 



So the clever part of the compiler is not the arithmetic. It is the plumbing: placing cells, routing relays between them, and controlling how arrivals are let in so that nothing is lost the way it was in the DSL page's second run.



4. Choices and loops


There are no jumps on this machine: every cell that exists works whenever data reaches it. So the compiler turns the usual control-flow ideas into dataflow:


    
  
  • An if becomes a select. Choose "A choice" above: the larger of two numbers. Both branches are always computed and a select picks one, built out of smaller operations (a subtract and compare, then masks with and, xor and or). The compiler listed exactly that for it. That is why a tiny function came to 66 cells.
    • 
  
  • A loop is unrolled. Choose "A loop that runs four times": the body is copied four times, one after another, and the loop counter disappears. That needs the number of times round the loop to be known when compiling. The limits in the source are 64 repeats and 600 instructions after unrolling.

5. Which operations it knows


LLVM operationWhat it becomes

  
add, sub, mulAn adder, a subtractor (as an add of the negated constant where it can), a multiplier.

  
and, or, xorA bitwise gate cell.

  
shl, lshrA shift, with the amount a literal number written in the code (shown above as "one-operand shl with amount 2").

  
icmp, select, br, phiSmaller operations put together, as in the max example: both sides are computed, then one is picked.

  
ashr, zext, sext, truncThe source lists these as expandable into the operations above. We did not run them for this page.

  
anything else, such as sdivRefused, with a message (section 4). The source says an escalation scheme for new operations (look in a shared library, then research, then build it in the Composer) is planned and not built.




All of it works on 32-bit integers (i32).



6. On to the flex family


The compiler writes an ICM file for the standard-mode cells. The flex family (the Tang Nano 20K's cells) is reached by two more steps, and we ran them on the first example:






The assembler's report says it made 17 cells with 3 joins from a 20-cell file: the three ordering cells are not cells any more in the flex version. There the cells hand data on with a ready and acknowledge handshake, so the order can be arranged by the wiring itself. The files written are the Verilog for the three kinds of cell used (adder, multiplier, ram) and a top file that connects them.


We generated this Verilog but did not simulate it here: the Verilog simulator is not installed in this session. The project's README says the 41 test programs compiled this way were each run as generated Verilog and matched the VM and plain arithmetic; that is quoted, not re-checked now.



7. What this is not


    
  
  • It is not a general compiler. One function, whole numbers only, a fixed list of operations, loops only when the count is known when compiling. Anything else is refused with a reason, never silently wrong, with the one exception the compiler itself warns about: the signed comparison can give a wrong answer when the two numbers are very large and of opposite sign.
    • 
  
  • Arguments are runtime inputs. The same compiled cells give the right answer for any inputs, as the runs above show, because each argument is a cell you load with a value.
    • 
  
  • An earlier front end still exists. llvm_ir_frontend_v1.py compiles a restricted counting loop onto a small ring of four cells instead of unrolling it. The command line tool used here is the newer one.
    • 
  
  • The VM runs it; the chip has run only smaller things. The README lists designs run live on the Tang board (a CORDIC, a relay, a reduction tree). We have not run these examples on the board.
