“Mirror” is the VM pretending to be one particular card. The MAN File tab described the card; the Assembler tab builds for it; the Two Grids tab showed the two versions of the VM's grid. This page is where those meet, and where they do not meet yet. Everything here was run on the real Python, on the two MAN files in the repository.

Today these are separate. from_man builds a standard grid at 32 bits and checks the layout; the flex mirror is a width you type. Nothing reads the Tang's native width of 18 from its MAN file to start a FlexGrid. Section 5 runs both, by hand, together.

2. The layout rule, and what it does to a design

A card with n cells is laid out as a near-square block, filled row by row: rows = ⌈√n⌉, columns = ⌈n / rows⌉, the last row possibly short. It is the same pair of functions (grid_dims, cell_positions in the assembler) that the build uses, so the mirror cannot drift from it. Choose a card, a cell count and a design from the Composer's library. Green cells are where the design sits inside the layout; red are cells that sit on squares a real build of that size would not have.

4. The Walker: finding out what is on the card

A real card does not hand over its map. The plan (#501 in the ledger) is that a host program walks it: ask a cell “who are you”, or ask it to pass a question one step north, south, east or west, and note who answers. The Walker below is the simulated version, run against the mirrored VM of the library adder (27 cells) on the Tang's layout of 400 cells. 5. Both mirrors together, by hand


The same adder, 200000 + 100000, run two ways. from_man gives the shape check and a 32-bit standard grid. Starting a FlexGrid at the width the Tang's MAN file declares gives the behaviour the chip would have. Doing both is a few lines; no tool does it for you yet. Real output:


import sys
sys.path.insert(0, "nano"); sys.path.insert(0, "tools")
import icm_v3, vm_mirror_v1
from vm_ai_port_v1 import VMSession
from flex_grid_v1 import FlexGrid

man = "docs/man/tang-nano-20k.man.json"
icm = icm_v3.IcmV3File.load("nano/library_std/add.icm.json")

a = VMSession.from_man(man, 400, icm_path="nano/library_std/add.icm.json")   # shape check, SuperGrid at 32

bounds = vm_mirror_v1.load_mirror_bounds(man, 400)
assert not vm_mirror_v1.check_records_fit(icm.records, bounds)               # shape check, by hand
f = VMSession(FlexGrid(icm.records, width=18))                                # behaviour at the MAN's native width
f.mirror_bounds = bounds

Added 20 October 2026: the mirror can take the card's own shape


Sections 1 to 6 were captured when the only mirror target was a MAN file and a cell count. Since ledger #1294 the Workbench can instead take the card's own SHAPE, card.shape.json, written by the Walker after it has run the design on the card. In that case the card is no longer described by what its file says it could hold but by what it was seen to hold: its cells, their types and sites, every connection its hardware has, and which of those connections the card itself saw a word cross (the Walker's "wire witnesses", one stored bit per connection).


    
  
  • A hierarchical design loaded under that target is checked against the card: every cell and connection must exist on the card, and the Workbench says which connections the card has not yet shown a word crossing. A different design from the one the card ran is refused; a flat DSL or flat ICM program is refused too.
    • 
  
  • The card can have fewer or more cells than the design. For CORDIC the design has 40 cells; the simulated card has 36 of them plus 4 merge cores the generator inserted. The 4 design cells the card folded into their branches are shown as absorbed (dashed outline) and the 4 extra card cells as card-only (a badge or a placeholder tile). This is allowed only when the design's fingerprint equals the card's.
    • 
  
  • Measured with the card read-back simulated (CORDIC): 40 cells, 39 connections, all 39 confirmed with the wide vector set (23 of 39 with the small set). On the real Kintex card the Walk gave 39 of 39 on 19 October. The mirror's own cell model is still the VM's standard one.
    •

7. How far to trust this page


    
  
  • Shape only. The mirror checks positions, not chip capacity, speed or routing. Its own file header says so, and section 3 shows how far apart the two questions can be.
    • 
  
  • The MAN file barely matters. The mirror reads only the card id from it. Running every library design at ten cell counts on both cards gave identical fit results; only the card id in the message differed. The Tang and Mustang files differ in what the other tools read (the MAN File tab), not here.
    • 
  
  • The Walker is a simulation. It asks the VM, hop by hop, the questions the real protocol would ask a card, and never looks at the grid directly. The real mechanism it stands for (a discovery mode in the cell) is not built in hardware, and no real card has been walked.
    • 
  
  • Placement has to match the generator. A design placed as a long thin strip (the 32 by 184 fp16 adder) is refused at every cell count up to 400, even though it might be small in cells; the check follows the generator's near-square array, not the design's own bounding box.
    • 
  
  • Not built. A FlexGrid version of from_man and of the Workbench target, and anything that carries the MAN's native width into the VM. The Workbench builds a SuperGrid whatever target is set.
    • 
  
  • Python only. No Verilog was simulated for this page; unit tests not re-run.
