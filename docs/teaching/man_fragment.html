The MAN file is one card, written down. It holds what the card is (the chip, how big it is, what built-in blocks it has, which legs carry the clock and the lights) and what its tools accept. It holds nothing about any program. The previous page showed the assembler reading it; this page opens the files themselves.

Two real files

Both live in docs/man/. They differ in age and in how they were made, and that shows in what they contain. Which fields a card file has decides what the tools can do for that card; where a field is missing, the tools fall back or refuse.

The mirror VM, live

This demo uses the Mustang file (the mirror needs only a card name, so either file would give the same grid). The mirror takes the name and a cell count, and lays out the grid the same way the assembler would: near-square, filled row by row. The add program (27 cells, spread over rows 2 to 6 and columns 1 to 14) is then checked against it. Pick a cell count. Dark squares are positions a real build would have; orange squares are the program's cells; a red outline is a program cell sitting where no real cell would exist.

The same check runs when the Workbench's "set target" is used and when the LLVM command-line tool is given --man with --cells. The mirror VM gets its own page later, and that page will link back here.

The mirror checks shape only: does every cell sit on a position a real build of that size would have, and do none share one. It does not check that the chip has room. That second question belongs to the card-fit check and the cost table below.

What a cell costs on this card

The Tang Nano file carries a table of measured costs: each flex-family cell was built at six widths and counted by the open synthesis tool, and a straight line (or a curve for the multiplier) was fitted through the points. Pick a cell and a width. The page reads the table at measured widths and uses the fit between them.

The count above is plain division of the chip's 20,736 LUT4s by the cell's cost. It ignores wiring, the shared connections between cells and the clock, so it is a ceiling for the arithmetic and not a promise that this many will place.

Positions the card holds

The card-fit check costs a design in positions, one per cell instantiated, at a measured cost per position, and keeps a margin (80% of the chip). The costs below were measured on the older cardinal cell shells, not on the flex cells above, so the two tables answer different questions. Notice how few positions even the cheapest shell gets on the Tang Nano against how many there are LUT4s.

What the card says it can do

The capabilities block is a list of yes/no facts about the card, each with a second flag for whether this project has actually used it yet.

How the files are made, and how far to trust them

Tang Nano 20K: generated

Mustang F100: assembled by hand

Where the generator can read a fact from a source (the chip database, the synthesis tool's own cell library) it does, and the file records where each fact came from. Where a fact is a decision (the no-wide-LUT default), the file says whose decision and which measurements back it.

Gaps, plainly

  • Nothing reads the capabilities block yet. The README describes it as the way a loader or generator refuses features a card lacks. A search of the Python in nano/ and tools/ finds it written by the two file generators and read by no tool; the real refusals above come from the synthesis and device.dsp fields.
  • Nothing reads the cost table in the file except its own generator and a test. The assembler does not use it to refuse a design that is too big.
  • The Mustang file is thin for the newer routes: no word width, no multiplier list, no cost table.
  • The Tang Nano file was never tested on the board. Its own verification block says the schematic is not checked and no bitstream has been loaded on the board by this project.
  • SHAPE and BITSTREAM, the other two of the four artifacts, were not run for this page.

Scope. Section sizes, field values, cost tables, fits, budgets and the mirror results are read from the two files and from nano/card_fit_v1.py and nano/vm_mirror_v1.py by docs/teaching/capture_rtl_v1.py. The descriptions of what each section is for are written from the files' own notes and from reading the code that uses them; the "nothing reads it" statements come from a text search and could miss indirect use. No hardware, synthesis or placement was run for this page.
