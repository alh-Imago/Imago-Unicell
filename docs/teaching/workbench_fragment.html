The workbench is the part of the VM you can sit at. You give it a small program, press a button, and watch every cell's registers change as the clock ticks. You can also push a value into any cell yourself. It is the quickest way to see the VM, the thing the previous page described, doing something.

The first link works only after you start the workbench on your own computer: run python3 nano/workbench_v1.py in the repository folder. It serves on port 7420 and opens your browser by itself (add a number after it for another port). Leave that terminal window open; closing it stops the workbench.

    2. A worked example: 7 + 5

    This is exactly what we did to get the screenshot, and what the cell showed at each point. The numbers are copied from the screen, not typed from memory.

    1. In Demos choose adder_pair and press Load as single program. The grid shows one cell, an adder at row 0, column 0. It sends its result east and takes its two inputs from the north and the west. Everything is zero or false and data_valid is false: nothing to offer yet.
    2. In Execution set row 0, col 0, dir n, value 7 and press Deliver. The cell now shows a_reg: 7 and a_arrived: true. It has the first number and is waiting for the second.
    3. Set dir w, value 5 and press Deliver again. The cell shows out_buffer: 12 and data_valid: true, and a_arrived has gone back to false. That is the answer, already waiting to be taken.
    4. Press Step a few times. Nothing changes: out_buffer stays 12 and data_valid stays true. The adder points east, there is no cell to the east to take the 12, so it simply holds it. A value is never thrown away just because nobody has asked for it.
    5. Now add a neighbour. Type program p2 { place r1 as ram_constant at (0,0) { out: e init_data: 42 } } into Program source, give it the region name answer_ram, clear both offset boxes and press Load as region. The workbench finds a free square by itself, (0, 1), right beside the adder, and the grid now shows a ram cell holding 42.
    6. Under the button an amber hint appears: the adder sends east toward that ram cell, but the ram cell is not set up to listen from the west, so the 12 would never arrive. The workbench tells you, but it does not stop you, because in the VM a connection with nobody listening is not an error, only data that goes nowhere.
    That hint is the useful lesson. Two cells being next to each other does not join them. Each cell has to be set to send on a face and the neighbour has to be set to listen on the opposite face. The workbench checks this for you; on the real chip nothing does.

    3. Everything is also a request

    Each button on the page just sends a request to the workbench's small web server, and the server passes it to the VM. So a script can do exactly what you did by hand. These are the calls behind the buttons you used above:

    requestwhat it does
    GET /stateEvery cell and its registers, as text a program can read.
    GET /demos, POST /load_demoList the ready-made programs; load one.
    POST /compileReplace everything with a new program (DSL or Python).
    POST /load_region, /clear_regionAdd a program as a named region, or remove just that region.
    POST /deliverPush a value into one cell from one side.
    POST /stepAdvance the clock by n ticks.
    POST /start_run, /pause_run, GET /run_statusAuto-play at a chosen rate, pause it, ask how far it got.
    POST /save_icm, /load_icm, /load_icm_regionWrite the grid to an ICM file, or read one back (as the whole grid or as a region).
    POST /set_target, /clear_target, GET /target, /shellsMake the grid a checked copy of a real card (below).

    For example curl -s -X POST localhost:7420/load_demo -d '{"name":"adder_pair"}', then two /deliver calls with value 7 from n and 5 from w, gave back the same cell state as the screen: out_buffer 12, data_valid true. The Save current grid to file button writes an ICM file, the same kind of file the Composer saves (see its page). For the single adder it holds one record: "core": "adder" at row 0, column 0, with upstream_mask ["n","w"] and downstream_mask ["e"], and it says "cell_type": "unicell_super_v1", the standard-mode cell, not a flex cell.

    4. The real target

    Normally the grid is free: any shape you like. The Real target box makes it a checked copy of a real card instead. You give it a card description (a MAN file; the box starts with docs/man/mustang-f100-a10.man.json), a number of cells and a "shell", which is the set of cell kinds that card's chip can actually contain. Pressing Set target with the box as it comes (4 cells, shell v3) gave a 2-by-2 grid for the card mustang-f100-a10-01 and the allowed kinds accumulator, adder, branch, comparator, latch, nano, ram and sequencer. After that, a program that asks for a cell the card cannot hold is refused. Clear target goes back to free mode.

    5. What it is, and what it is not

    • It runs the standard-mode VM. The cells on its grid are the standard ones, with fields such as downstream_mask and upstream_mask. They are not the flex cells from the earlier pages (branch with fixed and flowing inputs, priority, shift and so on). Designs for those are drawn and run in the Composer.
    • You give it programs written as text (the small DSL language, or Python through the Python front end), or ICM files. It has no drawing board. That is the Composer's job; the two are different tools that share the ICM file.
    • It shows registers, not a diagram. Each cell is a box of its fields. There are no wires drawn and no picture of data moving.
    • Seeing a value is not the same as it having moved. A cell like the adder holds its answer until a neighbour takes it, so an unchanging screen can mean "finished" or "stuck". The tick counter and the hint line help tell which.
    • Auto-play stops by itself when a tick produces no activity at all. An empty grid, for instance, ran for one tick and stopped.
    • Machine note: the workbench script keeps the terminal busy in a tight loop while it waits, so it will use one core of your computer fully until you stop it with Ctrl+C.
