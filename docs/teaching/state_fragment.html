A design that is running holds a little memory in every cell: which words are waiting, and what they are. If you could write all of that down at one instant, you could stop the machine, switch it off, and later put it back exactly as it was. That is a saved state. UniCell can do this on the real card, in the simulator and in the VM, and move a state between them.

What is saved, and what is not

The wiring of the design lives in the bitstream, and the cell settings arrive from a configuration pulse, so neither is saved. Only the dynamic registers are: each cell's "I am holding a word" flags and the words themselves. For the LaTeX example y = (z² + 12345) mod 65521 that is 15 cells and 678 bits.

One file, that says what it is

The raw image from the card is just 256 bytes of bits; what each bit means lives in a second file (the scan map), and losing it would make the image useless. So the tool tools/scan_image_v1.py writes one JSON file (format unicell-state-v1) holding the design name, the formula, a fingerprint of the register layout, the point where the run was cut, the closing register, and for every cell and register its name, width and value. A plain-words flag live says which values matter (a data register counts as live when its own pending flag is set). The flag is advisory; the bits are exact.

Loading rebuilds the bits by name against the target design, and refuses, saying what differs, if a cell, register, width or the layout fingerprint does not match. A state for the wrong design can not be pushed in by mistake.

Why the VM needs a translator

The VM is not a copy of the card, clock by clock, so tools/vm_state_bridge_v1.py bridges four differences. The VM divider works out its answer up front and counts down; the card's divider is stepped, so a half-finished card division is finished with the divider's own rule. A join fires on the card when both inputs wait, but the VM takes them one at a time. The assembler removes the priority cells that the VM keeps. And the card's constants are rams that offer their value forever, while the VM's are loaded once and ran dry in round 4 until they were marked as fixed. The bridge refuses VM states the card cannot hold, such as an operand that has only half arrived.

A lesson in it

Every "obvious" step here failed once before it worked: a constant served twice, a wrong answer above 32 bits (the hardware wraps before the remainder), a handshake that needs a one-clock pulse and not a level. The checks that caught them were all the same: run it, and compare with a plain model.
