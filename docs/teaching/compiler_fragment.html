The compiler is the part that turns a description of what you want into cells placed on a grid, with their faces set so they join up, saved as an ICM file. This page follows one real function through it stage by stage, shows how the two ways in (the DSL and LLVM IR) differ, how it reports problems, how it decides what goes in front of an adder, which operations it has, and whether the result fits a real card. The next page covers the placing and tightening in more depth.

2. Two ways in, and what they share


There are two front doors and they do not share all their insides. What they share is the result: a list of cells in an ICM file.


    
  
  • The DSL (and the Python-syntax reader) go through a small description called ProgramIR: a program name and a list of placements, each with a tile, a square and some fields. Then one shared back end checks each placement against the tile's own rules, places it and writes the records. Here is the 7 + 5 program from the DSL page as the compiler sees it:

  • LLVM IR goes a different way. The front end keeps the real dataflow (which value feeds which operation), because a ProgramIR already contains squares, and recovering the dataflow from squares would mean working backwards from geometry. So it builds a list of operations, hands that to a placer, and the placer decides every square itself. The comments in the source say exactly this.
    • 



So a DSL program puts the squares in your hands, and an LLVM program leaves them to the compiler.

4. How two values are let in: the decision rule


The DSL page showed an adder losing a number when both arrived together. When the compiler builds a design, it has to put something in front of every cell that takes two values, and which thing depends on three questions. Answer them and the real rule gives its choice:



  
  
  





These answers come straight from the compiler's own function, run for all eight combinations. In practice the routed placer, which is the usual one, always puts a priority cell in front of a commutative operation and a sequencer in front of a non-commutative one, whatever it could have worked out, so that correctness never depends on how long a route happened to come out. The price is one extra cell per two-operand operation. A subtract of a constant avoids even that: x - 3 becomes x + (-3), which is commutative.

That is the whole library: eleven entries, read from the code. The LLVM names icmp and select are not in it; the compiler builds them from these (a compare is a subtract and a compare-against-threshold, a select is a subtract, an xor, two ands and an or), as the LLVM page showed. A shift is a "ram_flowing" cell with an amount set in its add-on field.



6. Does it fit the card?


All of the above produces a layout of some size. A real card has a fixed grid and a budget of cells. The compiler can be given a card description and refuses a design that does not fit. We asked it to fit the same function onto square grids of several sizes on the Mustang F100 card's description (budget  positions):


gridresultthe compiler's report


One thing we did not get to the bottom of: the layout is 7 rows by 8 columns, yet an 8 by 8 grid was refused and a 9 by 9 accepted. The refusal says no layout fits at any fold width. We did not investigate whether the grid needs a margin or something else is going on. Also, the report says the multiply "fell back to logic" because no free DSP block was found, which means this build uses the slower logic multiplier rather than a hard one. And these are limits the compiler states itself: the card's die coordinates are mapped onto the logical grid by an assumed mapping, because no post-fit data exists yet to fix it.



7. What this is not


    
  
  • It is not an optimiser. The placing and routing are step-by-step heuristics, not a search for the best answer; the next page shows a case where a hand-chosen setting beat the default.
    • 
  
  • It does not verify itself. The runs on these pages compare the compiled cells against plain arithmetic for a handful of inputs. That is a check, not a proof.
    • 
  
  • It stops at the ICM file. Turning an ICM file into something a particular chip runs is the assembler's job (see the LLVM page's last section).
