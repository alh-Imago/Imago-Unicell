## Opening: continuing the shared-storage thread, and the real write-mux race

The session picked up mid-thread on `#561`'s own real shared-storage
idea — Alan's own real, direct reframing of it as "chips on a bus with
a chip-enable" rather than a value-select mux. `unicell_super_v4.v`
was built (`#573`): all 8 real cores wired `EXTERNAL_STORAGE=1` through
one real 170-bit shared register instead of 8 separate internal
register sets. A real, genuine write-mux race was found and fixed
during this file's own sim verification — the write-select logic keyed
off the registered `core_select`, which lagged `cfg_valid`'s own
`incoming_select`-gated enable by one evaluation on the exact cycle of
a switch, silently discarding the newly-configured core's first real
state write. Caught by a purpose-built full top-level self-test the
narrower shell testbench alone didn't expose.

## The real, three-way ALM verdict: shared storage costs more, not less

Real Quartus numbers, N=1: v3 (separate storage) 479 ALM / 301.9 `DUT`
/ 107.05 MHz (`#574`). v4 (shared, wide mux): 708 ALM / 96.9 MHz
(`#575`) — a real, precisely-localized +47.8% ALM cost, all in the
shell's own write-arbitration logic, not the cores (6 of 8 cores
individually got CHEAPER under external storage). Per Alan's own real
follow-up concern about Quartus collapsing a genuinely reprogrammable
mux at compile time (confirmed NOT happening, `core_select` stays a
real runtime input throughout), a redesigned per-bit "chip-enable"
write mechanism was built (`unicell_super_v5.v`, `#576`) — real,
different mechanism, same real cost class (`#577`): the bet that
Quartus's optimizer would prune dead per-bit logic didn't pay off.

Alan then asked the real, sharper question: does this hold at genuine
array scale, not just N=1? `project_assemble_v1.py` gained a real
`--shell` flag (`#578`) to array either shell. Real N=10 results: v3
1030.5 ALM/cell / 68.46 MHz (`#579`) — and a real, previously-invisible
finding along the way: every N=1 self-test had `addon_config` tied to
a literal 0, hiding ~380 ALM/cell of real addon cost (`shift_lane_
addon_v1` alone averaging more than nano or branch). v4: 1307.4
ALM/cell / 58.6 MHz (`#580`) — the relative gap actually NARROWED at
scale (26.9% vs N=1's 47.8%), and register savings compounded far past
a linear extrapolation (-66.2% vs -35.7%), but the real, dominant,
consistent cost remained the shell-glue (6.1-7.6x v3's own figure at
every scale measured). Real, complete answer: v3 remains the cheaper,
faster design at both scales tested; the shared-storage thread closed
here.

## Placement locality: LogicLock, a real Fmax win, and a real area cost

Alan spotted a real problem by hand in the Chip Planner — a cell's own
logic scattered across a ~40-column span to reach a genuinely adjacent
logical neighbor, on BOTH shells (ruling out an earlier v4-specific
duplicate-logic hypothesis). `project_assemble_v1.py` gained a real
`--logiclock` mode (`#582`) — per-cell regions, `AUTO_SIZE`. Real

cost — but the SAME real result showed only 32.2% average region

fixed-size mode was added in response (`#583`'s own extension), tested
at 25% headroom: v3 held Fmax flat (`#583` retest) while recovering
real area — but the identical methodology REGRESSED v4's own Fmax by
13.8% (`#585`), a real, fourth independent axis (after ALM, Fmax, and
register-scaling behavior) on which v3 proved the sturdier design.

## Config-off-shell: a real, incremental rollout, and a real bug found live

Alan's own real, direct proposal, checked against RTL before building
anything: `compare_cell_v1.v` re-latches its own config fields into a
private local copy on every `cfg_valid`, duplicating what the shell's
own `core_config` already holds stable. `compare_cell_v3.v` (`#584`)
removed the redundancy — architecturally safer than the shared-storage
attempts, since config has exactly one writer and needs no write
arbitration at all. Real result: `CORE_CMP` itself -14.3% (10.5 -> 9.0
ALM). Latch (`#587`, the smallest core, per Alan's own request) and
accumulator (`#592`, the widest real config budget, 37 bits) followed
the same pattern. Real, cumulative Quartus results across four
separate builds: compare's own win held and grew (-26.7% cumulative,
`#591`/this session's own final v8 result) — a real, confirmed,
non-noise signal. Latch's own win was smaller and noisier. Accumulator
went the WRONG direction on its own build (+5.8%), while `DUT` overall
still dropped to its lowest point, because completely untouched cores
(branch, nano) swung ±10% in the same builds — real, honest evidence
that build-to-build placement noise on this device is larger than
several of the real effects being measured.

Alan flagged a real, consistent Fmax decline across all four builds
(107.05 -> 106.54 -> 102.9 -> 95.99 MHz). Two real Chip Planner
screenshots (the moat tile's own `#595` control build, and v8 itself)
resolved this cleanly: the real worst-case path in BOTH builds runs
through `accumulator_cell_v1`'s own internal `Add1`/`Add2`/`LessThan0`
chain, unrelated to the `_v3` config mechanism entirely — a real,
generic, pre-existing critical path, not a cost of the new mechanism.

## The moat idea: a real, honest negative result, and a clean control

noise) — LogicLock was never the real driver; the moat's own real
connectivity is the genuine cost, and LogicLock's own real Fmax
benefit (98.66 vs 83.84 MHz without it) is confirmed real and separate.
