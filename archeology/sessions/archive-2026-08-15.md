## Opening: RAM-side memory questions (#301/#302)

Alan raised a genuinely new mechanism, sideways from the queued BRAM
circular-buffer plan: letting a CELL supply the RAM address (not just
`addr_counter_v1.v`), giving real random-access read/write. This
creates a stall hazard (a downstream chain stalled means counter-fed
data is lost or the whole system backs up) — resolved with a retry
loop feeding a new priority-arbitration core, made cheap by RAM's own
non-destructive read (only the ADDRESS needs stashing, not the data).
A real out-of-step staleness hazard was flagged, structurally similar
to `#37`'s already-accepted staleness window but not obviously bounded
the same way. `#302` sharpened Alan's own multi-chain out>in worry with
a concrete case grounded in the real, already-confirmed tree-system
topology (`#273`/`#286`): write traffic scales with join COMBINATIONS,
read traffic scales with chain COUNT — a real structural asymmetry.
Both entries logged as speculative direction, no RTL, needs real
testing before trust.

## Continuation: the super carrier shell goes real (#318-324)

Alan asked two precise architectural questions before building anything
further. Checked both directly against RTL: could `ram_cell_v1.v`'s
mechanism fold into the shell itself (no — the shell's own `ready_out`
is a static config flag, RAM genuinely needs a dynamic state-tracking
signal the shell doesn't have), and does the BRAM controller's 40-bit
interface make the whole system 40 bits wide (no — fully contained
inside the controller's own interface to the physical M20K primitive,
confirmed via `#257`, with zero DSP involvement since DSP/M20K are
confirmed disjoint hardware resources) (`#318`).

Alan then set the real baseline-rebuild task in motion. A fresh, same-
session, same-Quartus-version rebuild of the plain `top_stripped_
