## Where the session started

Picking up from `#198`: `top_stripped_zone750_v5`, the 750-cell zone
build, stood at 89,818 ALM, 259.61 MHz, -2.852ns worst slack, with the
worst-path list finally showing genuinely local paths (a single-cell
`cmd_latch[13]` self-loop, one adjacent `w0_bus` hop) rather than any
remaining global-fanout signal. Two queued diagnostic experiments from
`#200`/`#201` were still outstanding. The session's task: close that
remaining slack, then investigate why per-instance ALM cost at 750-cell
scale (`#199`'s original finding) ran so far above earlier isolated
measurements.

## The timing-closure detour (#206-#209)

`#206` queued `OPTIMIZATION_MODE "Aggressive Performance"` as its own qsf
variant, reasoning that of the two queued levers, this one (trading
packing density for wire length) was the one actually aimed at slack,
unlike `#200`'s duplication-OFF flags (predicted to move slack the wrong
direction). Real build data came back in `#207`: a resource-sharing/
routability-focused qsf variant Alan had built independently showed the
worst path was NOT cross-cell resource sharing as first suspected — every
node in the reported chain belonged to the same cell instance, just
scattered ~14 LAB columns wide by the placer despite being purely
single-instance logic. `#208` sharpened this further with a LogicLock
region test: one cell locked into a spacious, 6%-utilized, near-zero-
recoverable-by-packing region STILL cost 108 ALM, ~32x the old isolated
baseline — ruling out congestion as the driver for that specific finding,
since there was none.

`#209` then swept the full per-instance entity report across three whole
rows (59 cells, `ROW[13]`/`14`/`15`) and found the ~100+ ALUT/cell
interior cost was UNIFORM across every position, not scattered like a
congestion signature — pointing at something structural rather than
placement-driven. Diffing the isolated 25-cell baseline's instantiation
against the 750-cell zone's found a real, verified RTL difference: the
isolated test tied `prog_data_in_w`/`prog_arrived_in_w` to constant 0 for
every cell, while the 750-cell build wired them to a genuinely live,
row-wide broadcast bus. A diagnostic variant
(`top_stripped_zone750_v5_progw_tiedoff.v`) was built to test this
directly — tying the same signals off in the 750-cell build to see if the
per-cell cost collapsed back toward the isolated figure.

## The architecture conversation (#210-#220)

While the diagnostic build ran, a substantial architecture discussion
unfolded. `#210` traced the real mechanism behind `#209`'s finding: the
programming channel is genuinely receive-only (no relay path exists at
all — `cmd_out_n/s/e/w` are unconnected everywhere), and the current
top-level design broadcasts the same command word to all 750 cells
simultaneously rather than delivering it point-to-point. Alan clarified
in `#215` that the programming ABILITY has to live in every cell
regardless (since which cells become targets is decided at model-load
time, not compile time) — settling the "compile-time gate it" option as
genuinely wrong, and reframing the real question as purely about
DELIVERY topology. `#218` connected this whole line of thinking
explicitly to `#153`'s own earlier precedent — the full-fat cell's wired-
OR bus contention problem, and how its "free N-way combine" property was
recovered on the nano cell's point-to-point wires without reintroducing
the bus that caused the original cap — as the right discipline to apply
going forward: concept survives, code doesn't.

Separately, `#213`/`#214` recorded a real strategic shift: chase a
reliable, always-passing floor Fmax (Alan floated ~200 MHz, not fixed)
rather than a chased maximum, with every future addon carrying both a
size AND a timing cost in its manifest, explicitly not assumed additive
across combinations. `#216` laid out a full VM-core architecture
(root definition mechanically derived from RTL, grid construction, dual
CPU/GPU execution, JSON introspection, an AI-interaction port, timing-
awareness for the workbench, a fresh `core/` folder) — and `#217` did the
real legwork behind it: a full sweep of all 77 root-level Python files
found ZERO reference the stripped/nano cell at all, 35 explicitly target
the old full-cell format, and two genuinely reusable architecture
patterns exist (`gpu_array.py`'s CPU/GPU backend, `companion.py`'s
`attach_ai()`) even though neither targets the right cell. `#219`
reaffirmed and sharpened the existing photonic-interconnect research
note (`#124`) with a clearer motivating story: it's specifically the
physical medium the full-fat cell's original on-the-fly-reprogram
ambition needed, not just an Fmax fix. `#220` confirmed BRAM+DSP hybrid
integration as the next horizon once the cell stabilizes, pointing at the
substantial existing design already in `current/PLAN.md`.

## The programming format correction (#211)

A real, small correction: Alan's recollection of the programming word
format (location-then-value as two packets) didn't match what's actually
in the RTL (`#140`'s single self-describing `{3-bit ID, 16-bit data}`
word). Checked directly against the code and confirmed the RTL is what's
actually built, with Alan agreeing the ID-tagged format is correct as-is.
The same build that prompted this also produced a new, cleaner worst-path
finding: an ordinary two-arrival compute write (writing `out_buffer`),
the most basic operation every cell performs on every normal fire,
scattered 27 LAB columns across two directly-adjacent cells — the third
independent mechanism to show the same placement-scatter signature.

## The diagnostic result and the wrapper's own bottleneck (#221)

`#221` brought the `progw_tiedoff` diagnostic result home: a real,
informative NEGATIVE result. Tying off the programming-channel inputs
changed nothing — total ALM stayed flat (90,599 vs 89,818), and the
per-cell interior cost was statistically identical to before (confirmed
at the entity level, not just totals). `#209`'s hypothesis was wrong. A
genuinely new bottleneck surfaced in its place: the wrapper's own JTAG/
host daisy-chain bus (`cell_wrapper_v2.v`'s `bus_out_addr`/`match`/
`Equal1` chain) — a deliberately-designed, already-registered one-hop-
per-stage pipeline, yet even a single intentional hop between two
adjacent wrapper instances was now the tightest path, with the same
14-column placement scatter as everything else. Five real hypotheses for
the underlying 25-cell-vs-750-cell scale gap were checked and eliminated
in sequence in this same entry: feature growth, programming decode,
placement congestion, RTL drift, and resource-sharing QSF settings. All
ruled out. The cause remained genuinely unidentified.

## The density-threshold experiment (#222-#224)

Alan proposed a new, different hypothesis: overall netlist SIZE itself,
not local placement freedom, might change Quartus's fitter behavior at
some threshold between 25 and 750 cells. `#222` built a controlled
240-cell midpoint (`top_stripped_zone240_v1.v`, a direct clone of `v5`'s
structure with only `ROWS` changed, keeping `COLS` fixed at 30 for a
genuinely single-variable comparison), after checking and rejecting the
existing `zone500` build as unsuitable (it predated the `#180`/`#186`
row-buffer fixes entirely). `#223`'s real numbers complicated the naive
form of the theory — slack was actually WORSE at 240 cells than at 750,
the wrong direction for a pure congestion-scales-with-size story — and
flagged that the sampled row (`ROW[0]`) was itself a grid edge in the
smaller build, not directly comparable to the 750-cell interior sample.
`#224` resolved that once a genuinely interior row was sampled: the
240-cell interior cost (100.2-106.8, avg 103.8) was statistically
indistinguishable from the 750-cell interior sample (100.1-106.2, avg
102.8) — decisively narrowing the density-threshold search window from
25-750 cells down to just 25-240.

## The device speed-grade detour (#225-#227)

A real device mismatch surfaced mid-investigation: the 240-cell rebuild's
Fitter report showed `10AX066H3F34E2SG`, not the `H2F34E2SG` every qsf in
the repo specifies. `#225` verified via web search that `H2`/`H3` are
genuinely distinct part numbers (not a display artifact — an earlier,
incorrect reassurance in this same session was corrected here), with `H3`
likely a slower-binned part. `#226` confirmed with Alan directly that
`H2` is the correct grade — a device-picker selection mistake, not a
repo error, with every qsf file having specified the right device the
whole time. `#227`'s corrected rebuild then showed this ALSO wasn't the
explanation: Fmax/slack were essentially unchanged from the mistaken
build (237.93 MHz/-3.203ns vs 238.66 MHz/-3.190ns), and the worst path
was physically identical in both. A real, worthwhile bug fix, but not
the answer to the actual question being chased. One thing worth
carrying forward: `cmd_latch[13]` (`ready_bit`) — the same signal from
`#198`'s original finding — kept recurring as the worst-path signal
across multiple independent builds now.

## The major correction (#228)

While reconfirming `#171`'s original isolated 25-cell baseline (the
number every ALM/cell comparison this session had been measured
against), Alan noticed only 3 of 25 `cell_command_v1`/`unicell_stripped_v1`
instances appeared in the resource report, versus all 25 wrapper
instances. Checked against the RTL first (the `generate` loop
instantiates all 75 components unconditionally, confirming this wasn't a
missing-instantiation bug) and then confirmed directly by Alan that the
full connectivity list showed the same pattern with nothing hidden or
truncated: only 3 of 25 cell/command-cell instances were ever genuinely
live in that smoke test's stimulus. The other 22 were fully pruned by
Quartus, not small or zero-valued — absent entirely.

This meant `#171`'s headline "3.36 ALM/cell" was never a measurement of
what one active cell costs — it was 84 total design ALM (dominated by 25
genuinely-live wrappers plus top-level glue) divided by a nominal cell
count where 88% of the "cells" contributed nothing. The entire
`#199`-`#227` investigation thread had potentially been chasing an
explanation for a gap that never existed as a real phenomenon — it's
entirely possible a genuinely active cell has always cost ~100+ ALM,
consistent across every real scale actually measured. The scale-side
findings in that thread (`#207`, `#209`, `#211`, `#221`, `#224`) all
measured genuinely live cells and stand independently; only the baseline
half of every comparison was invalidated. Flagged prominently at the top
of `current/latest.md`, not left as a quiet correction buried in
`points.md`.

## Closing: real capacity numbers and the plan forward (#229)

With `#209`/`#224`'s ~100-106 ALM/cell figure established as the real,
trustworthy reference point, Alan extrapolated real per-card capacity
from the two genuine data points measured today: `240 * 80/11 ≈ 1745`
and `750 * 80/36 ≈ 1667`, both verified precisely, landing on a
conservative working estimate of ~1500 cells at an 80% utilization
ceiling. This is a real, substantial structural finding: `current/
PLAN.md`'s original per-card target was 16 zones × 750 = 12,000 cells —
roughly a 7-8x downward revision from what this specific device can
actually hold. Flagged as needing to feed back into the multi-card/lab-
cage planning whenever that's revisited, not resolved in this session.

The confirmed plan for next session: drop the target clock to a level
that reliably passes timing (the real floor, not a chased maximum, per
`#213`/`#214`'s earlier strategic shift), use that floor as genuine
headroom for future addons, and test every addon's real size-and-timing
cost against a full-card build specifically — not small-scale, since
`#224` already showed small-scale numbers don't necessarily predict
behavior near real capacity.

### Stripped cell: new mechanisms (#115-#120, #123-#126, #140-#144)
- **Memory cell system**: `hold_in` (freeze the first-arrival value across
  multiple fires), `fb_internal_in` (internal self-feedback, no external
  round-trip), `a_reemit_in`/`a_update_in` (pure pass-through vs. genuine
  update of the held value), `a_self_update_in` (self-adjusting threshold).
- **Command mechanism, REDESIGNED TWICE this session, final form confirmed
  cheap and fast**: `program_in`/`program_done` + a genuinely CARDINAL
  (`prog_data_in_n/s/e/w` etc.) dedicated programming channel, separate from
  ordinary data ports (#133, after #131/#132 found sharing the data port and
  a non-directional single wire both cost real Fmax). Programming itself is
  now VARIABLE-LENGTH and ID-TAGGED (#140/#142) — each word is
  `{3-bit field ID, 16-bit data}`, touching only the field it targets ("a
  scalpel, not a hammer"), not a fixed 96-bit overwrite. A reserved
  `COMPLETE` ID triggers `program_done`.
- **Branch mechanism** (#140/#142): ported from the FULL cell's
  `pattern_low/equal/high` + `dynamic_route_en` (same aligned bit positions,
  `[93:76]`/`[94]`), simplified to 4 wired bits per pattern (N/S/E/W). A live
  comparator result (`second_val` vs. held `input_val`) now genuinely picks a
  DIFFERENT routing direction per fire — confirmed: B>A/B<A/B=A route to
  three different, correct directions.
- **Bit `[10]` aligned** with the FULL cell's own `command_cell`/
  `COMMAND_EMIT` concept (#143/#144) — a config-time, fully self-contained
  permanent re-emitter, no external control wire needed.
- **A companion module, `cell_command_v1.v`** (~6 lines of real logic):
  holds one control line on trigger, releases on `program_done`. Genuinely
  separate from a stripped cell — not a mode, a distinct small instance.

### The wrapper, REBUILT for full host/JTAG parity (`cell_wrapper_v2.v`, #127)
Replaces `cell_wrapper_v1.v`'s single opcode with 5: `PROGRAM` (now via the
target's ordinary/dedicated programming port, not `cfg_data`), `COLLECT`,
`SET_CTRL`/`CLR_CTRL` (toggle any of the 6 control lines, persistent latches
inside the wrapper), `DIAG` (reads back `program_done`/`a_arrived`/`ready`/
`pending_ack` — deliberately minimal, not full state). Address field widened
twice this session (5→7→10 bits) to keep pace with cell-count scale-ups.

### RAM / PCIe throughput analysis (#147) — a real, grounded conclusion
On-board DDR4 (Mustang-F100-A10, 8 GB, PCIe Gen3 x8) is a BUFFER AT BEST at
current wrapper throughput: single-chain 771 MB/s, both RAM buses ~1.54
GB/s, vs. PCIe's raw ~7.88 GB/s ceiling — PCIe is ~5x faster than the
wrapper mechanism can currently sustain. Confirms #121's earlier
speculation with real numbers: PCIe direct cell interfacing becomes the
essential lever for real throughput, not a nice-to-have — still blocked on

### Freeze / ward-sentinel connection (#152) — real, and genuinely cheap
Freeze-driven runaway prevention, host-controlled targeting, save/restore,
self-healing relocation, and loader integration all map onto
`archeology/shared/docs/software/VISION.md`'s already-documented "ward/sentinel" layer (systems-level,
explicitly placed LAST in VISION's own dependency order). Key insight:
freezing the LAST cell in a chain (or any point in it) makes the ALREADY-
PROVEN backpressure cascade (#91/#92) stall every upstream cell for free —
no new zone-targeting RTL needed, and it's genuinely MORE granular than a
flat zone-broadcast would have been. Confirmed still working on today's
fully-redesigned cell (`tb_stripped_v1_ring.v` re-run, byte-identical), and
confirmed via the REAL host-driven path (`tb_wrapper_freeze_cascade.v`,
new): freeze B via wrapper `SET_CTRL` before A fires → A offers data to
frozen B → `A_ready` correctly drops to 0 (NOT B's own ready — a real
correction made mid-test) → release B via `CLR_CTRL` → `A_ready` recovers.
