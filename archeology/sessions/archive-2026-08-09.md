## The RAM-cell design thread (#231-#236)

While Alan was away, a design-note thread turned into real, tested RTL.
`#231` proposed a minimal "RAM cell" — a latch-only cousin of the compute
cell, no NOR-tree at all — built to attack the memory bottleneck without
reintroducing the shared/addressed bus that capped the FULL cell
(`#153`'s contention history). The genuinely elegant piece: the ordinary
ack a cell already receives on consumption ALSO means "I'm empty," which
becomes the trigger for a pull toward its own upstream neighbor via the
normal arrived/fire path — no new signal invented, the passive ready/ack
fabric already does the work. `#232` reframed the whole chain as a
feeding-buffer INTERFACE to real BRAM (confirmed still 0% utilized on
every build to date) rather than a BRAM replacement — giving `#220`'s
already-planned hybrid integration a ready-made front door. `#233`
named the real cost honestly: a RAM cell is a genuinely different cell
type, a real divergence from the fabric's single-uniform-cell-type
philosophy, not a config variant — flagged, not resolved. `#234` framed
the whole electrical RAM-cell mechanism as a size-compliant workaround
for CURRENT physical bottlenecks specifically, with photonic data
storage (fully parallel, not just addressable-without-collision) named
as the real long-horizon target it's working around.

`#235` turned this into real RTL: `ram_cell_v1.v`, plus two passing
iverilog testbenches (a FIXED-mode cell re-offering its constant
repeatedly; a 3-cell chain proving the cascading pull-refill). `#236`
then verified Alan's own follow-up point directly — that freezing a
RAM cell should cascade backpressure both directions via the same ack
mechanism already used elsewhere — and it already did, by construction
(the freeze gating had been mirrored off the compute cell's own pattern
when first drafted). A dedicated freeze testbench proved it, catching
and honestly fixing one over-strict test assertion along the way (the
test initially expected zero consumer receives during the freeze
window; the real invariant is zero NEW captures crossing the frozen
cell, not zero drains of what a downstream cell already held).

Both `ram_cell_v1.v` and the cfg-field layout are explicitly flagged
throughout as DRAFT — Alan asked to confirm the read/write mechanism
himself before any of it is trusted, and that confirmation hasn't
happened yet.

## The SDC investigation (#237-#241) — the session's real turning point

Alan returned and asked to drop the target clock to 200MHz. `#237`
made that edit (`stripped_zone750.sdc`'s `clk_div` from a mechanically-
fixed 25MHz generated clock to a direct 200MHz override) — but the
edit surfaced a real discrepancy: the OLD generated-clock definition
(25MHz, 40ns budget) could never have produced `#198`'s own
`-2.852ns`/`259.61MHz` figures; that math only reconciles against
something close to a 1GHz budget. `#238` checked Alan's recollection
of the clock/pin history (originally 25MHz, "upped to 50" at some
point, sourced from pin E23) directly against every committed file —
confirmed the pin and the original 25MHz tap, found zero trace of any
50MHz variant anywhere in tracked history, but the core discrepancy
stayed unresolved.

`#239` found the real candidate explanation: Alan uploaded
`Unicell-Q.sdc`, whose own header states plainly that skipping SDC
application makes Quartus invent a 1GHz clock and report fake
violations — exactly the numeric signature already found. Checked
directly: that file governs the separate PCIe-integrated `top_arria10`
project family (confirmed via every `.qsf`'s own `SDC_FILE`
assignment), not the zone750 builds — but `stripped_zone750.sdc` uses
the identical clock mechanism and should give the same comfortable
margin if genuinely applied. `#240` got real supporting evidence from
Alan's own compile report (SDC absent from a "source files read" list)
but correctly flagged that the specific report shown doesn't by itself
distinguish "genuinely missing" from "just not shown at that stage" —
and named the precise TimeQuest-specific check needed.

`#241` closed it: Alan's TimeQuest screenshot showed the literal
message, *"Synopsys Design Constraints File file not found:
'stripped_zone750.sdc'."* Confirmed, not inferred — every Fmax/slack
figure across the ENTIRE `#176`-`#227` timing arc had been computed
against a phantom auto-derived ~1GHz clock, not the real target. Root
cause: a genuine workflow gap (a fresh Quartus project folder per
build variant, and the shared SDC file wasn't being copied into it),
not an RTL or repo problem — the file itself had been correct in git
the entire time. `current/latest.md`'s CRITICAL section was updated to
flag this prominently, on the same severity level as `#228`'s
correction.

## The BRAM controller thread (#243-#246)

While the 750-cell build compiled, Alan raised the real interface gap
between the RAM-cell chain mechanism and actual BRAM: `#243` named it
precisely — BRAM needs an address (the RAM-cell chain has none by
design), has real multi-cycle read latency (unlike the chain's
same-mechanism pull), and whatever handles that also has to distribute
results to the correct chain head across however many chains share the
resource, at a throughput that scales with chain count. `#244` gave a
real, concrete partial answer: a dual-bus (in/out) design matching real
M20K dual-port BRAM directly, USB as the initial connection point, and
address generation reduced to a simple wrapping counter rather than
per-request computation — though the "write keeps pace with read"
assumption was flagged as unconfirmed.

`#245` relaxed that flag directly: Alan pointed out the starvation/
resume behavior is the natural, already-proven behavior of the pull
mechanism (`#236` already tested exactly this shape), not a fragile
throughput requirement. `#245` also answered two direct technical
questions with RTL evidence rather than assumption: no arithmetic
increment exists anywhere in the compute cell's gate table (every
`g0`-`g9` term is a purely bitwise, per-bit-uniform NOR-derived
Boolean combination — none carry information between bit positions,
and binary addition needs a carry chain), and `ram_cell_v1.v` genuinely
has ack-based handshaking on both directions, confirmed against the
actual RTL, not just asserted.

`#246` checked the FULL cell's own history before building anything —
its `loop_back` mechanism (Alan's dim memory: "the latch A was the
value to add... used an and?") turned out to be the same class of
Boolean-only feedback loop as the stripped cell's `#118`/`#120`, never
real arithmetic either, confirmed directly against `unicell64_v3.v`.
With that settled, built and iverilog-verified the actual base
primitives Alan asked for: `adder_v1.v` (a small, standalone,
genuinely arithmetic N-bit adder, deliberately NOT a fabric cell) and
`addr_counter_v1.v` (built on it, with `advance_en` deliberately
ack-gated rather than free-running, per the RAM cell's real
handshaking). Both testbenches pass — correct addition across several
cases including carry, and correct ack-gated pacing and wraparound.
Not yet wired to `ram_cell_v1.v` or real BRAM — this is the address-
generation primitive only, not the full controller.
