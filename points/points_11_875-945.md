## 875. THE `branch` CORE IN ROLLING MODE IS A GENUINE CHANGE DETECTOR -- the primitive I told Alan did not exist. Found by running an experiment after Alan asked whether the comparator was the cell that "sees the matching value, the zero count, and sends either the value or a 1/0". `tests/vm/test_branch_change_detector_v1.py`, 5 tests; suite 1494 passed (was 1489), all 49 script checks pass; cheat sheet's branch row updated. (Alan/Claude, 2026-09-28)

**A correction to my own claim.** At `#863` (and again in chat) I said no edge-detector primitive existed ready-made in the project and that the continuously re-offered latch level was therefore unusable as a trigger without inventing one. Wrong: `branch`'s rolling mode is one. I had read its fields but never asked what rolling mode was FOR. The lesson is the same as `#866`'s: claims about what a cell can and cannot do must come from running it.

**Alan's question, answered from the code.** By its fields, "if it sees the matching value it sends either the value or a 1/0" is the `branch` core, not `compare`. `branch` (`_deliver_branch`): the first arrival becomes a held reference and is never itself compared; each later arrival is compared `<` / `=` / `>`; per outcome an independent `emit` flag (emit or stay SILENT), `value_source` (pass the INPUT value, or a FIXED value -- 7-bit, so 1 or 0 fit), and a `route`. `comparator` (`compare`, `_deliver_comparator`): signed `>=` against a threshold, and it offers a 0 or 1 for EVERY arrival -- no emit-only-on-match option -- so it cannot be a one-shot trigger on its own. (This also explains `#858`'s "the comparator is single-shot" note better than I did then: it always answers, and the accumulator kept feeding it.)

**The experiment:** a latch (a continuously re-offered level) fed a rolling-mode branch configured silent on `equal`, emitting a fixed `1` on a rise and a fixed `2` on a fall. SET at t1, CLEAR at t4. The branch emitted `1` at t2 and `2` at t5 and nothing in between, while the latch re-offered `1` across several ticks: exactly two emissions, one per change, received in order.

**What the 5 tests pin:** exactly one emission per change of a re-offered latch (a fixed 1 on the rise, a fixed 2 on the fall, nothing while the level held); the first arrival is only a baseline and an unchanging level produces NO emissions; a non-rolling contrast (compare against a FIXED baseline) turns ONE change into a stream that fills the collector -- which is exactly why rolling mode matters; a `comparator` contrast that answers `0,0,0` although nothing ever changed; and a value-stream case (arriving 1,1,1,2,2,3 through a rolling branch that passes the input value on a rise emits only 2 then 3). Two bugs in my own tests were fixed on the way: the VM's core name is `comparator` (not `compare`), and a chain cell nearest its consumer speaks first, so I had loaded a stream in the wrong order and the branch was correctly silent on a falling stream.

**Why this matters for `#873`/`#874`.** It removes my caution from `#874`: a level source is safe as a trigger if a rolling-mode branch sits after it, because that turns every re-offer of an unchanged level into silence and every change into one discrete value -- and each value can be a fixed 1 or 0, exactly the 1-bit trigger Alan described for the sequencer, on the ordinary handshake. It also gives a second, grid-native route to `#858`'s drain event that needs no connection-point harness: latch or counter -> rolling branch -> one value on the change.

**Real, honest limits:**
- Verified on a latch and a synthetic value stream only. "Count became ZERO" from an accumulator is NOT yet shown: a rolling branch reports CHANGE (`<` means the count decreased, not that it reached zero), so a "reached zero" event likely needs a second stage comparing against a reference of 0, and the reference is always the first arrival (no config key preloads it), so that stage would need a 0 delivered first. Untested idea, not a result.
- The fixed value is 7-bit; a full-width marker still needs another cell.
- VM only; not run in RTL (the branch RTL has its own proofs, `#504`).

## 876. THE DRAIN EVENT BUILT ENTIRELY FROM GRID CELLS -- no connection-point harness, no data values, and it handles SEVERAL items in flight. An `accumulator` counts occupancy by arrival direction; a rolling-mode `branch` passes only CHANGES of that count; a fixed-baseline-0 `branch` fires a fixed 1 only when a changed value equals 0; one relay cell after it delays the trigger exactly one tick, per Alan. `tests/vm/test_grid_native_drain_event_v1.py`, 8 tests; suite 1502 passed (was 1494), all 49 script checks pass. **Alan's instruction:** test the zero-count case, and "add a delay on the branch dispatch side ... so even if the trigger is on the actual arrival, this ensures the branch is clear completely."

**The construction (each stage earns its place, shown by a control):**

- **Delay:** one relay cell after stage B.

- *No zero reference:* I predicted "the detector never fires". **An honest finding about the delay, pinned by a test, not spun.** In this VM the trigger ALREADY reaches its consumer one tick after stage B's output goes valid (offer/ack pipelining), and stage B has cleared by then, so here the delay cell is a MARGIN, not a fix. I built it as a RELAY CELL in the path (one extra cell), not as a delay parameter inside the branch core; the latter would be a core change (the 15-step map) and is Alan's call.

**Also worth recording:** the exit copy travels a relay path as long as the section, so the count reaches zero slightly AFTER the last item really leaves -- a conservative lag, never early, which is the safe direction for a drain signal. The section here passes one item per two ticks per cell (RAM relays are half-rate), which is why a short section never showed more than one item in flight.

## 877. THE RELAY PATH IS BOTH THE DELAY AND THE BUFFER -- Alan confirmed the delay should be a relay cell, and that it "allows a variable buffer, fully dependent on the distance between the end of the chain and the command cell's placement requirement." Measured, and the claim holds exactly, with one limit worth recording. Extends `#876`'s test file to 12 tests; suite 1506 passed (was 1502), all 49 script checks pass. Resolves `#876`'s open question on the delay's form. (Alan/Claude, 2026-09-28)

**A reframing accepted.** In `#871` I called the long relay columns "placement artifacts, not a design requirement". Alan's point is that the path length does real work, and I undersold it: the same relay cells that satisfy a command cell's adjacency constraint ARE the settling delay and the event buffer. The delay is therefore set by placement distance, not by a fixed core parameter -- which is why a relay cell is right and a `dispatch_delay` field in the branch core would not be (it would fix one value and cost a core change).

**Measured (deterministic):**
- **Delay:** N relay cells delay the trigger by exactly N ticks (0..5 relays measured: landed at t19, t20, t21, t22, t23, t24), while the detector itself is untouched (stage B fires at t18 in every case).
- **Buffer depth:** with the consumer blocked, the path holds exactly N + 1 events (N relays plus the consumer's own register): 0 relays -> 1, 1 -> 2, 2 -> 3, 4 -> 5; once full, stage B is held back rather than the event being refused upstream.
- **Nothing is lost while there is room:** with `bursts = relays + 3`, every fired event is delivered once the consumer drains.

**A LIMIT, found by releasing the consumer and counting, not assumed: beyond capacity, events are dropped SILENTLY.** After the consumer stalls the path absorbs exactly `relays + 3` events (the relays, the consumer register, stage B's output, and one more held upstream). Anything beyond that is lost -- I fired `relays + 5` bursts for 0, 1, 2 and 4 relays and got exactly 2 lost each time -- because stage A cannot accept new counts while blocked, the accumulator keeps updating internally, and the intermediate changes collapse into one comparison against the old reference. There is NO overflow flag: the sentinel has a sticky one (`err_overflow`); this construction does not. Pinned by a test so it cannot change silently.

**What that means for placement.** The placer must size the path for the most drain events that can be outstanding at once, or guarantee the consumer keeps up. In the reprogram loop that number is ONE, because the source is held until the reprogram completes -- so a short path is plenty there, and the only reason to make it longer is the settling margin or a placement constraint. The compiler must also know each path's delay: the sentinel's `chain_length` is a per-model value the compiler supplies (`#279`: "the compiler always had to know the depth and timing of each model"), and this is the same principle. The RTL timing question from `#876` (is the delay needed at all?) is unchanged and still open.

**One thing this does NOT solve, and it is the real gap next.** `#876`'s event means "the count became zero", and it fires at EVERY zero crossing, whether or not the pass is over (two bursts give two events, by design). The sentinel's `safe_to_intervene` is "the pass has ENDED AND the count is zero": a bubble mid-pass that briefly empties the section would fire the grid-native event early. Closing it needs a pass-end event ANDed with the drain event. The natural grid-native AND is probably a `nano` rendezvous (it fires only once both operands have arrived, in either order), with the pass-end pulse coming from an `accumulator` in `pulse_mode` counting feeds up to the pass length -- but that is an UNTESTED idea, not a result.

## 880. THE ACTUAL FOLD -- the cell the loop reprograms is now a cell IN the data path, so each pass is genuinely processed by the configuration loaded for it. Until `#862`-`#879` the reprogrammed unit was a separate target the items never touched, so the loop proved SCHEDULING only. Now the same `nano` computes `AND` with a constant for pass 1 and `XOR` with the same constant for pass 2, reconfigured live by the grid-native loop. `tests/vm/test_fold_v1.py`, 8 tests; suite 1528 passed (was 1520), all 49 script checks pass. Resolves the top open item from `#879`. (Alan/Claude, 2026-09-28)

**The construction.** The fold cell F is a `nano` in a 3-cell section (entry E0 -> F -> tail T) with `hold_in`. A constant K (`0x0000FFFF`) is its operand A; each streamed item arrives as operand B; so F computes `f(K, item)` where `f` is whatever topology the loop last programmed. The loop programs AND, then XOR, then OR. The topology has to be one where B matters: `NOT_A` would ignore the item entirely.

**Observed (deterministic, ~105 ticks):** program 0 completes t7 (topology `0x7` = AND, mask N); K is captured ALONE at t8; source released t11; pass 1 leaves t23-25 under AND; drain pulse t25; reprogram at t48-54 to `0xBC` (XOR) with `A = 0xFFFF` intact throughout; pass 2 leaves t70-72 under XOR; program 2 sets OR at t97-101. Outputs oldest-first: `['0x5678', '0xbeef', '0xfffd', '0xcafe0ff2']` -- exactly `[AND, AND, XOR, XOR]` of the inputs with K.

**Three facts about the fold cell, each found by RUNNING it and each contradicting an assumption I had:**
- **K cannot be pre-loaded.** A nano that has not been STARTED (`start_flag` false) is effectively frozen and refuses EVERY arrival, including its own constant. My first isolated test showed `a_arrived` stuck False and no outputs. K can only be captured AFTER the first program arms the cell; it waits, offering each tick, and is taken the tick after arming (t8, program 0 done at t7).
- **K must arrive ALONE.** The nano's first arrival becomes A, every later arrival becomes B, and simultaneous arrivals OR-combine into one operand. The long transport line (source -> F) is what guarantees K lands first, with a wide margin.
- **With `hold_in`, A survives both firing AND reprogramming** -- it stayed `0xFFFF` throughout, including across both live reprograms.

**A scratch-code bug found by tracing, not glossed over.** An early isolated test appeared to lose an item. ## 882. IS THE FOLD WORTH IT? -- Alan's economic framing, and the command cell's face arithmetic, with the costs MEASURED. **Measured cost of the one-fold-cell loop (`#880`'s grid):** 59 cells in total, of which the folded logic (the fold cell and its constant) is **2**. ## 883. AN EXTREME CASE: fp4096. Alan asked for a calculation on something extreme ("that's a big array"), noting the adder's carry-forward is missing beyond fp32 ("a separate issue"). Calculated with every input labelled EXACT, MEASURED or ASSUMED. No code changed except a lesson added to `CORE_CHANGE_IMPACT_MAP.md`. (Alan/Claude, 2026-09-28)

**EXACT -- the format.** IEEE 754's interchange formula (k >= 128, a multiple of 32) gives, for k = 4096: exponent `round(4 log2 4096) - 13` = **35 bits**, precision **4061 bits** (4060 stored), i.e. **127 limbs** of 32 bits. A schoolbook significand product is 127 x 127 = **16,129 limb products**.

**MEASURED -- cadences, and a measurement pitfall I nearly reported wrongly.** Fed from ONE interleaved operand stream (`a0, b0, a1, b1, ...`), values verified correct: `adder` **4.0 ticks per result**, `mul` (low 32 bits) **4.0**, `mul` in `wide_mode` (low + high) **6.0**. Those are bound by the FEED (a RAM relay chain moves one item per 2 ticks), not necessarily by the cells. My FIRST attempt fed A and B from two faces and returned "5 of 10 results" and a plausible "4 ticks/output": the two operands arrived on the same tick and OR-combined, so every product silently consumed two pairs (the known simultaneous-arrival collision, `#750`/`#764`/`#776`). Caught because the result COUNT was exactly half; recorded as a rule in `CORE_CHANGE_IMPACT_MAP.md`: feed two-operand cells from one interleaved stream, and check values, not just timing. Also measured earlier (`#882`): 45 ticks per fold pass boundary, 57 cells of fixed fold machinery.

**VERIFIED -- the carry gap, as Alan said.** The adder core computes only `(a +/- b) & 0xFFFFFFFF` (`_deliver_adder`): no carry-out and no carry-in, so nothing can chain limbs. EXCLUDED from every estimate below, per Alan; but it gates BOTH multi-limb add and the multiply's column accumulation (127 products per column overflow 32 bits), so it is a prerequisite for any work above fp32, not a refinement. It would add at least one or two limb-ops per limb (detect and propagate).

**The central result -- fold efficiency by precision (measured inputs, exact arithmetic).** Efficiency = useful ticks / (useful + the 45-tick boundary), with useful = limbs x 4:
fp32 (1 limb) **8.2%**; fp64 (2) **15.1%**; fp128 (4) **26.2%**; fp256 (8) **41.6%**; fp1024 (32) **74.0%**; **fp4096 (127) 91.9%**. 50% efficiency at about 11 limbs per pass, 90% at about 101. This is Alan's "at small scale maybe not, at large scale yes" in numbers: the overhead is per PASS BOUNDARY, and a pass at fp4096 carries 127 items, not the demo's 2.

**MUL is NOT a fold problem at all.** The same operation repeats 16,129 times, so it is streaming through fixed hardware and the 59-cell fold machinery never enters. Its cost is operand delivery (each limb of A pairs with all 127 of B: BRAM addressing, the `#805`-`#822` protocol) and accumulation with carry. ASSUMING two accumulate-adds per product: one `mul` plus one adder (~2 cells) takes about **97k-129k ticks**; 8 lanes about 12k-16k; **127 lanes (~254 cells) about 0.8k-1k ticks**; the fully unrolled array is about **32,258 cells**. It is a lanes-versus-time trade with no reconfiguration in it.

**ADD is where the fold matters, and here the numbers are ILLUSTRATIVE (assumptions stated):** ASSUMING per limb 3 ops to align, 1 to add, 3 to normalize, 2 to round (9 total, carry EXCLUDED): 127 x 9 x 4 = **4,572 ticks** of work, plus 3 boundaries x 45 = **135 ticks**, i.e. reconfiguration overhead of **2.9%**. A fully parallel static datapath, ASSUMING ~3 cells per limb per barrel-shifter stage (12 stages, two shifters) and ~6 cells per limb for add, leading-zero scan and rounding, is roughly **9,900 cells** against about **67** folded (57 fixed plus ~10 for the stage): ~150x the area. Its latency (ASSUMING ~30 stage-delays at 4 ticks, so ~120 ticks) would be ~40x shorter -- very rough, that latency is an assumption, not a measurement. So at fp4096 the fold trades about 150x area for about 40x time.

**Two things this calculation exposed that the demo had hidden:**
1. **The command words are not constants.** In `#879`/`#880` every program word was a compile-time constant preloaded into the store. Alignment and normalization need DATA-DEPENDENT parameters: the shift amount comes from the exponent difference (up to 4061 bits: a limb offset plus a bit count). So the word stream would have to be BUILT from data at run time. This is `#843`'s open question ("what decides the next configuration") made concrete, and it is exactly what `#859`'s command-word builder (OR-accumulating slots, VM-proven) and `#860`'s release gate were begun for -- so pieces exist, but the loop has never used them.
2. **Fixed overhead stops mattering; what dominates is the array machinery** -- operand streaming and addressing, the carry chain, and the shifters. Cutting the fold's 57-cell fixed overhead (`#882`) matters far less at fp4096 than at fp32.

**Real, honest scope:** every ADD and static-area figure above is an estimate resting on stated assumptions (ops per limb, cells per shifter stage, static latency); the MUL lane figures assume two accumulate-adds per product; ticks are protocol rounds, not clock cycles; nothing was built or run beyond the two cadence measurements; carry is excluded throughout. What IS solid: the format arithmetic, the cadences, the 45-tick boundary, and the efficiency table.

**Real queue:** (1) the carry-forward gap -- a prerequisite for anything above fp32, both add and multiply (Alan flagged it as separate; it should be scoped as its own item now); (2) computed command words -- run the loop with a program word built from data (a shift amount), using `#859`/`#860`; (3) decide what workload the fold is FOR, now with fp4096 add's staged shape as the strongest candidate; (4) the feedback path so a fold is genuinely iterative; (5) controlled command mode with a direction-carrying Start, and the triggered sequencer, re-measured; (6) per-direction ack in the VM; (7) RTL path for `hold_in`/`a_reemit_in`; (8) N passes; (9) overflow indication for grid-native paths; (10) fp32 ADD/MUL/DIV substrate mapping; (11) `#846` G/R/S to real rounding; (12) MIN/MAX via `branch`; (13) `v1d` VM model (`#841`); (14) LLVM gap list (`#830`); (15) scope items 3, 4, 6; (16) VIX Carrier backlog (`#824`); (17) documentation catch-up (`#829`/`#856`) -- timely; (18) paired-cell/command-bus (`#835`/`#836`); (19) N-way sort network (`#837`); (20) collapsed-assembler idea (`#838`); (21) keep `CORE_CHANGE_IMPACT_MAP.md` current.

**MEASURED, the comparison (function XOR -> NAND -> AND -> XNOR, K = 0x9C3E5A17, 8 items):**
- **Static stage pipeline:** 24 cells, of which **8 machinery** (4 op-cells + 4 constants) and 16 storage. First result 5 ticks after release, last **19**; cadence exactly 2 ticks per item. Matches the reference.
- **Fold:** 60 cells, of which **56 machinery** (including the folded logic) and 4 storage/port. Four programs, four drain pulses, correct after EVERY pass (`ALL 8 CORRECT` after passes 1, 2, 3 and 4). Release t11, done t215: **204 ticks**, i.e. a pass every 59 ticks (pulses at t37, t96, t155, t214).
- **Result: the fold is ~10.7x slower and uses ~7x the machinery cells** for this function. The pulse period (59 ticks per pass) carries only 16 ticks of useful work (8 items at 2 ticks each): about 27% efficient at 8 items per pass.

**A structural fact, from the measurements: the fold can NEVER beat the static pipeline on time.** It runs every stage serially on one datapath, so its time is at least N_STAGES x the static time; boundary overhead is on top of that. Modelled: fold ~ N x (2n + B) with B ~ 35 measured, versus static ~ 2n + N + 2; at n = 8 that is ~9-10x (matches), at n = 127 it tends to ~N (about 4x). Larger passes amortise the boundary (`#883`) but cannot remove the factor N.

**A second structural fact, from counting cells at 3 and 4 stages: as BUILT the fold never wins on cells either.** Each extra stage adds **3 cells** to the fold's serial program store (topology, mask, COMPLETE words) but only **2** to a static pipeline (an op-cell and its constant). So however many stages there are, the built fold's marginal cost per stage exceeds the static's; its 44 cells of fixed machinery are never repaid. Only a COMPACT program store -- BRAM, or a sequencer holding several words per cell (`#873`/`#874`) -- would change that, bringing the marginal cost per stage toward zero and putting break-even near 22 stages (44 / 2, DERIVED, not measured). **This makes the program store the scaling term, and is the concrete argument for the triggered sequencer.**

**Four things that went wrong on the way, each recorded because each would have produced a plausible-looking wrong comparison:**
1. **A degenerate test function.** My first choice (XOR, AND, OR, XNOR) returned `0xFFFFFFFF` for every item -- AND-then-OR collapses to the constant -- so it could not have caught a mixed-up item or a wrong stage. With a CONSTANT operand every bitwise gate is a one-input function per bit and the lossless ones (XOR/XNOR/NOT) commute, so an order-sensitive, information-preserving composition cannot exist. I searched for a usable one by criteria (four different gates, 8 distinct outputs, every stage needed, order matters); the pair-cancellation and information criteria I first demanded were impossible and were dropped.
2. **The fold builder hard-coded its own constant** (`0xFFFF`) while the static side used `0x9C3E5A17`; the fold silently disagreed with the reference. Found by comparing, fixed with a `k_value` parameter.
3. **Forcing state from a harness corrupts the grid.** My first loader emptied the output chain by setting `valid` to 0. The cells kept their `pending_ack` bits, the stale offers re-fired, 7 of 8 cleared cells refilled with old data, and the 8th result was blocked in the tail while the exit counter had already counted it. I instrumented the fold cell and showed it had computed pass 2 CORRECTLY (`0x8e0a0c6f` with the constant intact and NAND active gave `0x73f5f7f8`), so the fault was mine. Replaced by a real writeback port: a sink `accumulator` that acknowledges and discards, its `deliver` tapped to read each result as it arrives. Forcing `pending_ack` to 0 as well was tried and made things WORSE (a stall), which confirmed forcing state is the wrong approach.
4. **Staging the next pass before the gate froze the source.** Once fixed, passes 2-4 still mismatched: I staged the next pass when the 8th result arrived (~t37) but the gate freezes the source only when the drain pulse arrives home (~t60), so pass 2 began under the OLD configuration. Kept as a control; I predicted "all 8 items under the old stage" and the truth is worse: the first 7 items had stage 1 applied AGAIN (XOR twice cancels to the original value) and only the 8th got NAND, because the reprogram landed mid-pass. One pass split between two functions, no error anywhere.

**Mutation-checked, five breakages across both designs, all caught** (restored byte-identical, bytecode cleared): fold stages in the wrong order -> 2 fail; fold constant differs -> 3; one static stage with the wrong gate -> 2; drain threshold one short -> 1; source gate neutralised -> 5.

**Real, honest scope:** VM only, ticks are protocol rounds. The loader is a BRAM stand-in and a harness step. The static pipeline's 16 storage cells are a modelling artifact (a BRAM in reality), so the comparison is on MACHINERY cells with storage reported separately. Eight items per pass is small. The 2 cells per static stage assumes one constant cell per stage. The 22-stage break-even is derived from the marginal costs and assumes a compact store that does not yet exist. One function, one gate family, constants identical across stages (a held constant cannot change between passes).

**What this means for the fold:** for a fixed sequence of a few stages the static pipeline wins on time AND on cells, now measured. The fold's real claim is narrower and different: RUN-TIME-VARIABLE behaviour -- the same physical structure taking on different roles over time. Alan's branch case is exactly that: a `branch` cell whose routing is reprogrammed so the same chains serve different program branches.

**Real queue:** (1) the branch-reconfiguration demonstration: a `branch` cell whose route/emit rules are reprogrammed between passes so the SAME downstream chains serve different roles -- Alan's stated use, and the fold's real niche; (2) the compact program store: prototype the triggered sequencer (`#873`/`#874`) and re-run this comparison to see whether the marginal cost per stage falls; (3) scope the carry-forward gap as its own item; (4) computed command words (a shift amount from the exponent difference); (5) controlled command mode with a direction-carrying Start; (6) per-direction ack in the VM; (7) RTL path for `hold_in`/`a_reemit_in`; (8) overflow indication for grid-native paths; (9) fp32 ADD/MUL/DIV substrate mapping as STATIC stage pipelines (`#843` point 1, now measured); (10) `#846` G/R/S; (11) MIN/MAX via `branch`; (12) `v1d` VM model (`#841`); (13) LLVM gap list (`#830`); (14) scope items 3, 4, 6; (15) VIX Carrier backlog (`#824`); (16) documentation catch-up (`#829`/`#856`) -- timely; (17) paired-cell/command-bus (`#835`/`#836`); (18) N-way sort network (`#837`); (19) collapsed-assembler idea (`#838`); (20) keep `CORE_CHANGE_IMPACT_MAP.md` current.

**Why a wrapper is needed at all, and what it costs.** A raw shell's own ports run to 140-500+ raw signal bits (four 32-bit cardinal buses each way, 64-128 bit `cfg_data`, per-direction program channels) -- the QN88 package has only 66 pins total, so NO standalone cell can ever be placed with every port bound to a real pin. `tools/gowin_sizing/gen_mesh_top.py` (new) wraps N=1 or a real 3x3 mesh of ONE cell type in a closed system using only 5 real, already-verified board pins (`docs/man/tang-nano-20k.cst`, `#887`): clock, reset button, entry button, 2 LEDs. **Three real collapse bugs found and fixed, each confirmed by direct evidence, not assumption:**
1. **Signal reuse.** The first version tied one raw board button to several live inputs at once. The synthesiser proved them algebraically identical and deleted the whole latch cell -- confirmed directly: its "26 ALU cells" were the harness's own heartbeat counter, renamed by the optimiser; the latch's own instance had zero surviving DFF. Fixed with a real 32-bit LFSR (seed mixed with the board button, so it isn't a provable constant either) driving every live signal from a distinct bit/word.
2. **Single-direction stimulus.** For an isolated cell, three of four cardinal directions were tied to a hard 0. If a cell's config-selected routing mask happened to pick one of those (confirmed: this is exactly what happened to `mul`, whose post-place cells came out byte-for-byte identical to `adder`'s), the whole compute core saw a constant zero and vanished. Fixed by giving every direction genuinely live, distinct LFSR-derived data.
3. **Bit-0 observability.** Even after fix 2, `adder` and `mul` were STILL byte-identical. Direct iverilog simulation of both designs, with real toggling stimulus, proved the RTL and wiring were correct all along: adder settled on `0x5b3104cb`, mul on `0x6ef4668a` from the same inputs -- genuinely different. The real cause: the anti-pruning XOR-guard only reduced **bit 0** of each 32-bit output, so the synthesiser correctly (not a bug) discarded 31/32 of the real arithmetic as unobserved. Fixed by XOR-reducing the FULL width of every `dout`.

A fourth, smaller bug (undeclared `entry_active_n`/`entry_data_n`/`entry_arrived_n`: only cell `(0,0)` had a north-facing alias, but every OTHER row-0 cell in a 3x3 mesh also lacks a north neighbour and hit the same fallback name) was caught by yosys's own frontend before it ever reached synthesis.

**The real, load-bearing consequence, named directly by Alan before any RTL was written:** removing backward ack makes every cell's latency a fixed, known number of cycles at build time, and any two paths converging on a later cell must arrive latency-matched or a fresh value silently combines with a stale one. That is the real next piece of work this direction creates, not something resolved by this entry.

**First real cell: `sub/verilog/adder_cell_v4s.v`, built and measured.** Two fixed operand ports (`in_a`/`in_b` -- read as: "no cardinality" removes the runtime direction-decision, not a binary function's real arity), one output, one forward-only "timing line" (`valid_out`, asserted exactly one cycle per genuine new result, carries no backward information, never stalls anything). Fixed one-cycle latency, unconditional once armed -- the whole point. `cfg_data` reduced to a single `subtract_mode` bit; nothing else is left to configure. Live per-direction reprogramming and `freeze_in` both deliberately removed for this first cut, not oversights -- see the file's own header for why.

**A real testbench bug found and fixed before trusting the result -- the same discipline that mattered three times last night.** The first simulation run showed the reconfigure-to-subtract-mode step silently not taking effect (10-4 computed as 14, i.e. still add mode). Root cause: the testbench cleared `cfg_valid` with a bare blocking assignment immediately after `@(posedge clk)`, zero delay -- racing the DUT's own same-edge-triggered `always` block for which one reads `cfg_valid` first, with Icarus's scheduler consistently resolving it the wrong way. Not an RTL bug: adding a `#1` delay before every post-edge clear fixed it, and all 6 real checks (pre-configuration gating, add, subtract, three back-to-back single-cycle-apart results) pass clean.

**Real, measured size (same free-port `synth_gowin -noiopads` methodology as `#886`, so directly comparable):** 66 LUT4 total (32 ALU for the 32-bit carry chain, 32 LUT1, 34 LUT2) -- against `adder_full`'s 2,348. A 97.2% reduction, bigger than the 60-80% guessed last night once actually measured rather than estimated. This is close to exactly "just the bare adder plus a one-bit mode register," which is what the design predicts once the addon chain, the mask decode, and the ack state machine are all genuinely gone rather than merely unused.

## 899. BUILD-TIME-FIXED CONFIG, not just runtime-loaded -- Alan's own idea (limit shift range, chain for larger totals) led to a real, deeper insight: `shift_stage_v4s` at 26 LUT4 vs `shift_cell_v4s`'s 3,261, a 99.2% reduction. Plus 8 more `v4s` cells built, simulated, and measured this session.

## 906. ACK AND FREEZE, REINTRODUCED MINIMALLY -- a real, measured surprise: adding both back costs LESS than the pure no-ack cell, not more.

Alan's own Saturday design direction, picked up after Friday's "it all comes down to timing" cliffhanger: reintroduce a backward ack, but a minimal, point-to-point one (one bit per fixed connection, a receiver telling its one fixed sender "I am clear, so it sends its data" -- a classic ready/valid handshake, not the original cardinal family's N-way arbitrated version). Separately, reintroduce freeze -- but GLOBAL, not per-cell, after Alan's own mid-conversation refinement: one signal broadcast identically to every cell, not threaded through the ICM graph. Freeze's real purpose confirmed as boot-side specifically (`#899` already removed live per-cell reprogramming, so there is no runtime reprogramming event to guard against yet) -- holding the whole system still while config loads safely into every cell -- plus a genuine side benefit of going global that Alan surfaced himself: a synchronised, whole-system pause point for reading out state and comparing it against the VM's own mirror, which per-cell freeze could never offer as cleanly.

**Why this is not a retreat from `#898`'s "physics, not control" -- stated precisely, not just asserted:** the original cardinal family's ack was expensive because of ARBITRATION (`#889`) -- a 4-way mask deciding WHICH direction to wait for and route to, every cycle. This ack is point-to-point, one fixed sender, one fixed receiver, decided at build time, same as `in_a`/`in_b` -- there is no "who" to decide. This adds a cheap synchronisation primitive on top of a graph that stays fixed by construction; it does not reintroduce the runtime routing decision that was the actual expensive part.

**A real, valuable consequence, worth stating plainly: this likely removes the need for the static latency-padding work that has sat in the queue since `#898`/`#899`.** That scheme only works if every cell's latency is known at compile time, and breaks the moment any future cell has data-dependent timing. A local ack solves the same real problem -- don't let a fast path's fresh value collide with a slow path's stale one -- in a way that is robust to ANY timing, known or not, with zero static analysis anywhere. Paying 2 bits to delete an entire not-yet-built subsystem is a good trade.

**`sub/verilog/adder_cell_v4sa.v` built: standard ready/valid semantics.** `ack_out = armed && !pending && !freeze_in` (a frozen cell must not claim readiness); `valid_out` now stays HIGH across multiple cycles if the downstream receiver is not ready, rather than `adder_cell_v4s`'s one-shot pulse -- the real, honest behavioural change reintroducing ack requires. `freeze_in` gates the ENTIRE update, including whether a fresh `cfg_valid` may take effect, so config can load safely while frozen. `armed` keeps its own separate, narrower, permanent meaning; freeze is new, orthogonal, and re-triggerable.

**A real testbench-tooling trap, caught and fixed, worth remembering for next time:** the first draft named its check task `expect` -- a RESERVED SystemVerilog keyword (concurrent assertions), which `-g2012` parses for. Every call produced cascading, misleading syntax errors far from the true cause (reported at line 87, the real issue was the task name at line 25). Renamed to `check_cond`; fixed immediately once correctly diagnosed rather than guessed at via several wrong hypotheses (begin/end imbalance, stray apostrophe) first.

**Two real bugs found by simulation, not assumed correct:** (1) `ack_out`'s first draft lacked its own `!freeze_in` gate -- a frozen cell was still claiming readiness, caught by the very first real check. (2) A hand-computed arithmetic mistake in the TEST itself (`6+7=42`, which is wrong -- `6+7=13`) produced three cascading false failures, caught by adding cycle-accurate debug tracing and reading real register values rather than continuing to guess. All 14 real checks pass clean after both fixes: boot-time freeze, freeze releasing, unstalled operation, real multi-cycle backpressure (held steady, not overwritten, across several stalled cycles), correct resume once acked, and mid-operation freeze being a true, total pause unaffected by anything toggling while frozen.

**Real, measured result (same free-port methodology as `#886`/`#898`, directly comparable): 37 LUT4 -- LOWER than the pure no-ack `adder_cell_v4s`'s 66, not higher.** A genuine surprise, reported honestly rather than smoothed into false certainty: register counts are similar (34 DFFRE vs 35), so the likely explanation is that the "hold the current value unless genuinely capturing" logic this design needs maps onto the flip-flops' own native clock-enable input rather than requiring extra LUT-level muxing the original's different structure needed elsewhere -- a plausible, not fully isolated, explanation. Real place-and-route (actual Fmax on real silicon, not just free-port synthesis) has not yet been run for this variant.

**Both variants kept, deliberately:** `adder_cell_v4s` (zero-wait, fixed one-cycle latency) for anyone who genuinely needs guaranteed fixed-cycle throughput and is willing to build the static latency-padding machinery it requires; `adder_cell_v4sa` (ack + global freeze, variable latency, zero static analysis needed anywhere) as the likely better general default given this result.

## 923. FLEX-SUB ASSEMBLER STEP 2, FIRST SLICE: the ICM-VIX netlist extractor -- and what reading the file as a "map" actually involves. Read-only; no Verilog generated yet.

**What reading the "map" really means (each point read from the source, not assumed):**
- **The `connections` list is ADVISORY, not the wiring** (`ICM_VIX_FORMAT.md`). The authoritative wiring is each flattened cell's own `upstream_mask`/`downstream_mask` plus its grid position. - **Branch routes by OUTCOME, not by mask:** `route_low/equal/high` (direction lists), not `downstream_mask`. My first extractor missed this: cordic showed 35 edges instead of 43, every adder looked single-sourced and every branch looked like a dead end -- caught because the adders' masks listed two directions but only one source was found.
- **Constants are not pins:** cells with no incoming edge but a `preload_value` are constant sources (cordic has 12), not top-level inputs.
- **VM semantics that a fixed-port cell must reproduce** (read from `unicell_super_automaton_v1.py`): several masked directions arriving on one tick are OR-combined (a "merge"); a two-operand cell (adder, mul) takes operand A = the FIRST arrival and B = the SECOND, by ARRIVAL ORDER and not by direction; and one stream may deliver both operands on successive ticks.

**Findings on the three shipped examples (all structurally mappable, 12/12, 40/40, 8/8 -- "clean" means no hard blocker, NOT that the translation is built):**
- `small_relay_chain`: 8 cells, 7 edges, plain relays.
- `parallel_reduction_tree`: 12 cells, 11 edges, 4 inputs, 3 adders each with exactly 2 sources at different hop depths.
- `cordic_z_convergence`: 40 cells, 43 edges, 12 constants, 7 merges (OR glue), 4 branch fan-outs, 8 adders each with 2 sources (a constant and a branch output), 1 observed output, 0 undriven. **All four branches are representable on `branch_cell_v4sa`:** each routes low/equal to one face (S) and high to one other (N), which maps onto out1/out2 with route bits low=1, equal=1, high=2.

**Operand order verified against the VM:** a static estimate (longest hop path from the roots; the earlier source is operand A) was checked against the REAL VM by wrapping the adder's deliver in the handler registry and recording which face landed in A and which in B. It matched at **all 7 adders that received both operands** (3 in the tree, 4 in cordic). The other 5 cordic adders are the branch's not-taken paths and only ever receive the constant, as expected. My first run of this check reported 0/7 -- that was my own bug (logged direction indices 0..3 but looked them up as letters; the encoding is N=0,S=1,E=2,W=3, `icm_v3._DIR_BITS`), not a finding. **Honest limit:** 7 data points from two small examples is a validation, not a proof; ties, and a single stream delivering both operands, have no rule yet.

## 924. ALAN'S RULINGS ON THE STEP-2 DECISIONS (#923): merges are an OR, operand pairs on one stream are staggered in time, `sub` is pure time-dependent wiring, `flex` fan-out needs an ack join.

## 929. ALAN'S RULING: OPTION C -- order non-commutative operands by `#771` path equalization (strict priority mode 0), not by the sequenced channel. No file-format change. Findings on what C actually requires; nothing built.

**Decision (Alan, 4 Oct 2026):** of the three options put to him after #927 -- (A) record operand roles on the adder, (B) record the mode-2 sequenced order, (C) compile non-commutative ops with `#771` path padding -- C "seems the better choice in the entire scheme of things". **What C actually requires -- found by reading and by experiment, NOT yet agreed:**
1. **It is not a flag flip, and the compiler's authors said so in the code.** `vix_dag_dispatcher_v1.py` passes `all_arrival_ticks_knowable=False` with a comment that the dispatcher "does NOT yet compute real, precise arrival-tick formulas ... confirmed directly to produce a wrong result when assumed otherwise", so SEQUENCER is chosen for every non-commutative case. Its STAGGER lowering is a fixed `extra_hops=2` on one side, not real equalization. The exact formulas exist (`rats_nest_timing_v1.py`: `symbolic_arrival_tick`, `composed_output_ready_tick`, #773) but are NOT used to compute padding.
2. **Experiment (read-only; forcing the chooser to STAGGER in the `growth` dispatcher, which is the placer `auto` picks for these small programs):** `x - y` -> priority mode 0, no seq order, 8 cells (was 6), and the VM computes the right answer from the compiled records (4294967295 / 97 / 4294967292). `(x - y) - z`, where the natural path lengths differ -> NO result at all (None for every input). So the naive stagger works only when the natural paths happen to be equal. (My first attempt patched the `routed` placer's chooser and had no effect, because `auto` selected `growth` -- recorded so the null result is not mistaken for a finding.)
3. **A conflict with `#774` that must be resolved by a convention, not ignored.** #774 (Alan's, confirmed) says path equalization is "structurally inapplicable" when an operand's arrival tick is unpredictable, and a compiled function's arguments are runtime values injected at `dynq` cells -- so the sequencer is "the ONLY robust" shape for them. C reverses that only if the arrival TICK becomes knowable even though the VALUE is dynamic. The natural way: a calling convention in which every argument of a call is presented on the SAME tick (a call strobe). #774's point is about unpredictable ticks, not unpredictable values. For the `sub`/`flex` fixed-latency targets this is already inherent (the generated top takes aligned in_*_valid pulses). For the carrier lineage it must be stated and ideally guarded, because a host that violates it gets the #770 failure (silently wrong operand order for subtraction).
4. **A detail to verify, not a claim:** the dispatcher sets every priority rank to 0, so for a non-commutative STAGGER pair operand identity rests on the orientation helper placing `in_a` on the face that wins the N>S>E>W tie. The forced `x - y` came out right, but ranks should probably encode A/B explicitly.

**Connection to #927 (the selectable VM):** the arrival convention looks like a natural TARGET-PROFILE attribute (arguments presented simultaneously: inherent for sub/flex, declared for the carrier lineage).

**Plan for C, in order (proposed, nothing done):** (i) agree the convention; (ii) wire the #773 timing math into the dispatcher and the routed placer so padding is computed, and set ranks for operand identity; (iii) use STAGGER only where ticks are computable under the convention and keep SEQUENCER as the fallback for genuinely asynchronous inputs (VM-only until hardware exists); (iv) four test files assert mode 2 / `seq_orders` (`test_counter_feedback_v1`, `test_priority_multiway_v1`, `test_vix_dag_dispatcher_v1`, `test_llvm_dag_frontend_v1`), so introduce this as a selectable ordering rather than flipping the default, per clone-don't-modify; (v) verify compiled `x - y`, `(x - y) - z` and a longer chain: VM from the SAVED file correct, and generated sub RTL == VM.

## 933. `sub` MERGES: the gated OR is built and verified -- same-cycle arrivals OR together (RTL == the real VM), stale data from an idle source is masked, and an ungated OR provably fails. Cordic's only remaining blocker on `sub` is now the branch core.

Alan's ruling (#924): same-time arrivals on one input are OR-combined -- "a free OR when needed", the basic truth of UniCell. Built for single-input cells (ram, comparator) in `tools/flexsub_icm_generate_v1.py`.

**The one non-obvious rule, found by measurement, not argument:** these cells keep driving stale `data_out` after their valid pulse (a flowing ram holds its `data_reg`; #925). A raw OR of the sources would therefore leak an idle source's OLD value into a later item. So each source is GATED by its own valid before the OR: `(vA ? dA : 0) | (vB ? dB : 0)`, with valid = the OR of the valids. Same-cycle arrivals still OR together, which is the VM's rule; items from one source alone pass through untouched.

**Two refusals, each for a definite reason:** a merge that INCLUDES A CONSTANT (the constant is always valid, so the OR would swamp the stream -- no definite behaviour); and a merge of sources arriving at DIFFERENT LATENCIES (the cell's output time would depend on which source fired, which a fixed-latency design cannot align -- that needs flow control, i.e. flex).

**Verified (`tests/test_flexsub_merge_v1.py`, 17/17), on hand-built ICM v3 designs with a real merge (two source rams into one, N and W faces):** five same-cycle pairs (including identical, all-ones/zero and overlapping bits) -- RTL == the real VM == the OR; a single active source passes through unchanged (each source alone, RTL == VM); **gating** -- after both sources fired, a later item from E1 alone is 0x11 (not 0x11 OR the stale E2), likewise for E2 alone, and a mixed stream of alternating and simultaneous items comes out as the OR of each item's active sources. The VM cannot model back-to-back items (it handshakes them), so the gating checks use an explicit oracle -- "the OR of the sources that fired" -- and are RTL-only; the one-shot checks are against the VM. **NEGATIVE CONTROL:** stripping the gating from the generated Verilog makes the second result leak the stale value (0x5511 instead of 0x11), so the test is not vacuous.

**One stale assertion updated, not a regression:** the generator suite required cordic to be refused for "merges"; merges are now translated, so cordic's refusal names only the branch core (`no v4s branch cell exists`) and the test now also asserts that merges and constants are NOT blamed. ## 936. THE BRANCH LOWERING IS DONE: the hand-built CORDIC design (branches, merges, constants, adders -- 36 cells) now runs as generated `sub` Verilog and matches the real VM on all 12 starting angles, including the repo's independent anchor (z0 = 50000 -> -404).

**What the ICM branch actually is, read from the VM's `_deliver_branch` (this decided the whole design):** a HELD-REFERENCE comparator with ONE input face. The FIRST arrival is captured as the reference and emits nothing; every later arrival is compared (signed) with it; the outcome (low / equal / high) picks {value source, emit, route faces}; with `rolling_mode` the value just compared becomes the new reference. The cell the lowering targets has two dedicated inputs, so the question was how a held reference maps onto them:
- **`const_ref`** -- the branch is fed by a MERGE of a constant and a stream. This is exactly how the hand-built cordic loads its reference (the constant zero arrives first, then the signal; the repo's own harness comment says so). The merge is removed: in1 = the stream, in2 = the constant (flowing, valid = the constant's own valid), so every stream value is compared with it. Two variants: the stream is another cell, or the stream is the merge's OWN external entry (cordic's `z_input`, injected straight into the merge) -- then the branch itself becomes the entry point, under that io_name.
- **`rolling`** -- the stream feeds BOTH inputs with in2 HELD, loaded by the same valid: the cell reads its held register before updating it, so each value is compared with the previous one, and the very first arrival finds nothing loaded and so becomes the reference with no output -- exactly the VM.
- **Refused, each with its reason:** a reference that is the first arrival of a plain stream with rolling off (holding only the first value needs a "first only" state bit -- control, which sub does not have); a constant reference together with rolling; value sources or fixed values that differ among the emitting outcomes (the cell has ONE shared `emit_source`); more than two routed faces; a routed face with no cell on it; a branch fed only by constants. A disabled outcome (`emit_x = 0`) is expressed as "route to neither"; a fixed emit value is `fixed_value & 0x7F`, as the VM masks it.

**Generator changes:** a `branch` entry in the core table; a rewrite pass `lower_branches` (like the priority elimination); per-face output nets with a `net(consumer, source)` helper so each consumer connects to the right one of the branch's two ports; the cfg word built from the plan; a cell with an `io_name` is never derived as constant (it has an external input the graph does not show -- this is what made cordic's first merge look constant); the removed merge's hop still counts in the VM-time used for operand IDENTITY (otherwise the branch looked one hop early and tied with a constant).

## 937. THE SUB SEQUENCER: tick-driven, "loses the ack side and goes back to just the clock pulse side" (Alan). Built and verified against the VM -- and a finding about the VM that makes one topology a refusal.

**Alan's rulings (4 Oct 2026):** (1) leave the flex no-size fallback for now -- "a relatively easy fix"; decision (a) from #934 is deferred, not closed. (2) The sequencer on the sub version loses the ack side and goes back to just the clock pulse side; the ack belongs to the flex side, which already has it. This corrects what I wrote earlier in this session ("the sequencer ... is not expressible on sub"): it IS expressible, in exactly the way `sequencer_cell_v4s`'s own header already says -- "a dedicated `advance_in` pulse, an explicit external 'move to the next value' event -- a forward control input, not a backward ack."

**What the VM does, read from source:** the sequencer is perpetually live (`seq_data_valid` is True from configuration), offers VALUE_0 first, and advances to the next each time a consumer drains its offer (the backward ack), wrapping after SEQUENCE_LEN+1 values; it refuses every arrival (ack tied low).

**The translation (`tools/flexsub_icm_generate_v1.py`):** the pulse becomes a top-level input `adv_<name>` (1 bit), presented on the SAME cycle as the design's other arguments -- the calling convention already in force (#929). One detail in the cell matters: on each pulse `sequencer_cell_v4s` emits the value at the NEXT index, so its first pulsed value would be VALUE_1. The generator therefore stores the values rotated one step (new[j] = V[(j-1) mod n], n = SEQUENCE_LEN+1) so the pulsed sequence starts at VALUE_0 and wraps exactly like the VM's -- pure configuration, no control logic. `ASSEMBLY.json` records the host contract per sequencer (advance port, length). Refused: anything feeding a sequencer; extra config keys; an addon on a sequencer.

**Verified against the real VM (`tests/test_flexsub_sequencer_v1.py`, 20/20):** the bare sequence a draining consumer sees, for lengths 1, 2, 3, 4 (and an 8-bit-range set 255/128/1/0), 10 values each, past the wrap: RTL == VM == VALUE_(k mod n), starting at VALUE_0. And a non-relay consumer: sequencer [10, 60, 49, 50] into a comparator (>= 50): RTL == VM == 0,1,0,1,0,1,0,1.

**A FINDING ABOUT THE VM, and the reason one topology is refused.** I first built and tested the case I expected to matter most: the sequence PAIRED with a data stream through an adder (item k + VALUE_(k mod n)). The generated RTL did exactly that (all three lengths) -- but the VM did something else entirely (e.g. results 300, 70, 300, 71, ...): the VM's sequencer re-offers at once and its adder pairs by ARRIVAL, not by source, so the adder takes VALUE_0 as A and VALUE_1 as B (100 + 200 = 300) with no data item involved. In the VM a sequencer into a two-operand cell self-pairs. So for that topology the VM and the tick-driven hardware mean different things, and silently producing hardware that disagrees with the ICM's VM semantics would break the rule this project follows throughout (refuse rather than mistranslate). Therefore a sequencer feeding a two-operand cell, or a merge, is REFUSED with that reason. The finding is recorded as a test (it asserts the VM does not compute X_k + VALUE_(k mod n); it will need revisiting if the VM changes). **If Alan wants host-tick pairing with a stream as a deliberate sub feature, that is a decision to make explicitly, not something the VM defines.**

**Mistakes of my own, caught by running:** I wrote the first paired test with values 300 and 400 in 8-bit fields (rejected at save: `VALUE_*` are 8-bit); and I assumed the VM would pair the sequence with the stream and used it as the oracle -- the result disagreed, and the investigation is what produced the finding above rather than a wrong "verified" claim.

## 938. THE LEVEL-SOURCE RULE: accumulator and latch on `sub` -- built and verified against the VM. A level source's valid is held high; it counts as constant-like for timing. Includes a VM sampling quirk found on the way.

Alan: "Yes, start with those" (the accumulator and latch level-source rule, in answer to my question after #937).

**What the VM and the cells do, read from source:**
- **Accumulator, continuous mode:** the VM offers its running total ALWAYS VALID (a LEVEL source); `accumulator_cell_v4s` pulses `valid_out` only on an update. **Latch:** the VM offers its 0/1 state ALWAYS VALID; `latch_cell_v4s` pulses valid only on an event. These two are the level-vs-pulse gap.
- Already identical: the arithmetic (delta = +step on inc alone, -step on dec alone, 0 on both or neither; the arriving value ignored), the threshold/abs test, the reset-to-0 on a pulse-mode hit, the latch priority clear > set > toggle, and set needing bit 0 of the arriving value. **Accumulator in PULSE mode** needs no rule: the VM offers a discrete event on the crossing and the cell pulses valid on the crossing -- it stays an ordinary timed event source.

**The rule (`tools/flexsub_icm_generate_v1.py`):** a LEVEL source (continuous accumulator, or a latch) has its valid held high (`assign <cell>_v = 1'b1`; the cell's own valid pulse is unused), and it joins the constant-like set for timing -- always available, never constraining alignment, exactly like a constant (its data changes, its availability does not). Anything fed only by constants and level sources is therefore also always-valid, which is what the VM does (a comparator on a level offers its result continuously). The pulse inputs are the valids of whatever feeds each role: `inc_pulse`/`dec_pulse` from the inc/dec faces, `set`/`clear`/`toggle` from theirs (set additionally gated by the arriving value's bit 0, as in the VM); several sources on one role OR together. cfg words: step_amount [7:0], pulse_mode [8], threshold [24:9]. `ASSEMBLY.json` lists the level sources.

**One refusal, with its reason:** a constant or level source into an accumulator's inc/dec input, or into a latch's toggle input. The VM counts/toggles once per DRAINED OFFER while this design does so once per CYCLE, so the result would depend on the rate. Set/clear from a level source is idempotent and is translated -- that is exactly the sentinel pattern. Also refused: an accumulator or latch with no pulse input connected, extra config keys, an addon.

**Verified against the real VM (`tests/test_flexsub_level_v1.py`, 16/16):** a counter (nine increments of 3, the arriving value ignored); up/down including a simultaneous inc + dec (net zero) and negative totals; a PULSE-mode accumulator on 13 items crossing in both directions (+30 and -30 events, nothing between); a latch over ten items exercising set (bit 0 set and clear), toggle, set+clear (clear wins), toggle+set (set wins) and toggle+clear; and a sentinel chain accumulator -> comparator -> latch SET (a level driving a level) -- the latch reads 0,0,0,0,1,1,1,1,1 as the count crosses 5. RTL == VM in every case. Four refusal cases.

**A VM QUIRK FOUND ON THE WAY (not a defect of the sources):** my first level tests all failed by exactly one item -- the RTL gave the right totals, the VM the same sequence shifted by one (0, 3, 6...). The VM's accumulator total was correct after every item (traced: 3, 6, 9, 12). ## 940. LOOPS ON `sub`: counted loops work (the frontend unrolls them); genuine cycles are refused with the reason -- and a REAL BUG found on the way: the generator exported the wrong cell as the output when a result also fed dead code. Fixed; the saved ICM does not record the result cell.

Alan: "Yes the loop and mask side." (Mask/invert and the shift: #939.) This entry is loops.

**What "a loop" is in this project -- found by looking, before building:**
- **Compiled loops are UNROLLED** (#801-802): the trip count must be known at compile time, a data-dependent exit is refused by the compiler, and the result is an ACYCLIC graph. So every counted loop already translates to `sub` like any other design. Checked: four compiled loops (`sum 0..4`, a multiply-accumulate, a shift/xor recurrence, a two-carried-value Fibonacci recurrence), 14 vectors each incl. 32-bit wrap: generated RTL == the arithmetic.
- **The VM's `counter_feedback` suite is NOT a dataflow loop**: it is a flow-control model (per-chain counters gated by in-flight counts, backpressure from a stalled chain) -- exactly what the ack/flex family is for and the ack-free `sub` family lacks.
- **Genuine cycles exist only in hand-built rings** (e.g. #638's four-cell bounded-loop ring: loop variable -> loop control -> adder -> relay -> back), whose exit depends on the DATA and whose controller uses nano's dynamic-routing modes. The number of times round it -- and so the output's arrival time -- is variable; fixed-latency wiring cannot align that, and a second item entering while one circulates would collide. Refused on `sub`, with that reason, and with the note that counted loops DO translate. That needs the handshake (flex) or an explicit one-item-at-a-time host contract -- a decision, not built.

**A REAL BUG, found by the Fibonacci loop.** The RTL returned 34 where the VM (running the compiled ICM) and true LLVM semantics both give 13; bisecting N=3..8 showed RTL(N) = true(N) + true(N+1) every time. Root cause: the generator exported "the cell with no outgoing edge" as the output. The unrolled loop contains iterations nobody uses; the compiler's result cell (`bn__it0`) also feeds them, so the LAST dead adder was the only sink and the RTL faithfully computed its dead sum. **The deeper cause is a gap in the FILE:** the compiler's result cell has NO face leaving the grid and is not marked -- `result_cell` lives only in the compiler's memory (the same class of omission as the sequenced-priority order, #926). From the saved file alone, a result that also feeds unused logic is indistinguishable from a design whose last cell is the result. It never showed in the 41-program corpus because there the result happened to be the only sink.
**Fix:** `flexsub_compile_v1` now records the result cell using the format's OWN field (`io_name`, "a genuine external entry/exit point", #667) as `result`; the generator takes, in order: a cell marked `result` (authoritative), a cell with a face that leaves the grid, then sink inference -- and says which in `ASSEMBLY.json` (`exit_rule`); anything that cannot reach an output is dead and pruned (`pruned_dead_cells`). The Fibonacci design drops from 52 to 36 cells and from 25 to 18 cycles. **Limit:** a file straight from the stock `llvm_cli_v1` has no marker, so it falls back to sink inference and can still mis-export a program with dead code -- use `flexsub_compile_v1` for sub/flex (the recorded `exit_rule` makes the inference visible).

## 944. FLEX ICM GENERATION, STAGE 1: `-s flex --icm` now generates ram / adder / mul designs as handshake (ack) hardware -- eager forks for fan-out, joins for two-operand cells -- verified with streams through random gaps and stalls.

Alan (4 Oct 2026): hard-DSP on the Arria 10 is a future item ("I get the new PC and hopefully fire up the Arria 10 card again, but that's future me, resources are limited at this stage"); so the flex side: "hopefully this will be slightly easier as it has the ack side, which is in the nano version." It is easier in the way he meant: the VM itself models offers and acknowledgements, and flex needs NO latency alignment and NO padding -- the handshake absorbs arrival-time differences.

**The flex handshake, read from `adder_cell_v4sa.v` / `ram_cell_v4sa.v`:** a cell CAPTURES when `valid_in` is high and it is not `pending` (that is its `ack_out`, "ready"); `valid_out = pending`, held until `ack_in` is high at an edge (`ack_in` = the downstream's READY level); so a transfer is an edge where the source's valid_out and the consumer's ready are both high; a cell cannot capture in the cycle it releases (the one-item-per-two-cycles of #934/#935).

**What the emitter builds (`tools/flexsub_icm_flex_v1.py`, new; `plan()` gained a `family` parameter):**
- every top-level port has a handshake: `in_<n>_data/_valid` plus an OUTPUT `in_<n>_ack`; `out_<n>_data/_valid` plus an INPUT `out_<n>_ack`;
- a single consumer: the source's `ack_in` is the consumer's ready;
- **FAN-OUT = the ack join Alan ruled in #924, built as an EAGER FORK:** one flop per consumer (`taken`), valid to a consumer is `valid & ~taken`, the source's `ack_in` is high only when every consumer has taken the item (this cycle or before), then all flags clear. The flops matter: a purely combinational "all ready at once" fork forms a combinational LOOP in a diamond (two sources each feeding two adders);
- **a two-operand cell is a JOIN:** `valid_in = vA & vB`, ack to A = `ready & vB`, ack to B = `ready & vA`, so both sources transfer exactly when the cell captures;
- add-on chains (mask/shift/invert) are pure wiring on the data, as on sub.
**Stage-1 scope, with everything else refused by reason (never silently mistranslated):** ram, adder, mul. Refused on flex for now: constants, merges, branch, comparator, nano, accumulator, latch, sequencer. Fixed-latency-only refusals (a merge of unequal latencies) no longer apply to flex.

**Verified (`tests/test_flexsub_flex_v1.py`, 24/24) -- the right test for a handshake design is STREAMS under backpressure, not single items:** items pushed through random INPUT GAPS and random OUTPUT STALLS, plus a heavy-stall mode (ready 1 cycle in 8), asserting nothing is lost, nothing duplicated, ORDER kept, against plain arithmetic.
- the shipped 8-cell relay chain: 24 items x 4 modes; the shipped reduction tree (4 inputs, 3 joins): 20 items x 4 inputs x 3 modes, and one item (1,2,3,4) == the real VM == 10;
- compiled programs: `x+y`, `x-y`, `x*x` (a pair fed from one source), `x*y+z`, `(x+y)*(x-y)`, and `fanout_three` (a real fork): 16 items x 4 modes each, all correct;
- **a TRUE DIAMOND** (`a=x+y`, `b=x-y`, `s=a+b`, `d=a-b`, `r=s*d`: a and b each fan out to two joins; 2 forks, 5 joins): correct under every stall pattern;
- **MUTATION CONTROLS on the diamond:** a fork that forgets who has taken the item, valid not masked by `taken`, and a join that acknowledges A without B -- each is CAUGHT by the stall tests, so the tests have teeth.
- refusals: the branch-and-constants example, a program with a constant (`x+5`), and a merge.

**Mistakes of my own, caught by looking rather than assuming:** (1) a first tree failure (20 instead of 10) was NOT a design fault -- a cycle-by-cycle trace showed the design computing 10 correctly; my test built its port list with a regex that matched each port several times and then overwrote every input with 2x its index (2+4+6+8 = 20, which is exactly what a correct design computes for those inputs). (I had also "fixed" a suspected testbench race first, which was not the cause; the nonblocking style stays, being safer.) (2) I named a program `DIAMOND_diff_of_squares`, but it reports forks 0: the compiler gives each use of an ARGUMENT its own injection cell, so no fan-out exists -- it was not a diamond and the fork was not exercised by it. It is renamed, and a true diamond built from intermediate values replaced it. (3) a stale generator-suite assertion ("flex --icm is refused") and a label that wrongly triggered a sub-only clause, both fixed.

**Not done / limits:** constants, merges, branch, comparator, nano, accumulator, latch and the ack-driven sequencer on flex (each needs its handshake rule worked out and verified; the merge needs the "which source to acknowledge" decision, and Alan said the ack will push back on merges); the streaming tests check VALUES and ORDER, not the rate (flex's one-item-per-two-cycles is as measured in #934, not re-measured here); width is fixed at 32 (no `-w`/native width on the ICM path yet); the host-facing ack ports are a NEW contract for any design driving a flex design (the top has handshakes on every port); no place-and-route yet for flex designs; the VM catch-up (#927) and the deferred no-size fallback stand. ## 945. FLEX ICM GENERATION, STAGE 2: CONSTANTS. A constant is a fixed-mode ram (always valid, always ready, never used up) -- no fork, no ack. 20 of the 41 corpus programs now run on flex, each verified under streams with stalls.
