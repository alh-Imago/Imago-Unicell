## 947. FLEX ICM GENERATION, STAGES 3-4: NANO AND COMPARATOR. ALL 41 corpus programs now run on flex, each verified under streams with stalls and forced operand orders. A VM finding on negative comparator thresholds.

Alan (a new week): "lets get into the nano on flex and move through the field of cores."

**Nano (stage 3) -- the first core whose two operands are NOT symmetric.** Read from `nano_cell_v4sa.v`: the HELD operand A is only a LOAD STROBE (`load_hold` overwrites the held register on any edge, with NO handshake and regardless of `pending`); the FLOWING operand B is the ordinary valid/ready; the gate reads the held register's CURRENT value at capture, so a hold loaded on the same edge is not yet visible (the "A one cycle before B" rule of #932). The emitter adds ONE flag per nano, `aload` = "A is loaded for the current pair": A's ready is `~aload & armed` and the load is `vA & ready` (allowed while the previous result is still pending, so the next pair's setup overlaps the drain); B's ready is `aload & ack_out`, and its capture clears `aload`; `armed` = `ack_out | valid_out` (derivable from the cell's own outputs). **Arrival ORDER no longer matters** -- a B that arrives first just waits -- which is why a handshake design needs none of sub's padding. A source feeding both operands works through the existing eager fork (A is taken first, B a cycle later).
**Comparator (stage 4):** `compare_cell_v4sa` is a single-input cell (signed(data) >= threshold -> 0/1, threshold in `cfg_data`), so its handshake is exactly a relay's; a handful of lines.

**Verified (`tests/test_flexsub_flex_v1.py`, 51/51; was 33):**
- **THE CORPUS: all 41 of 41 programs are accepted on flex** (was 20 after constants, 31 after nano), each 12 items x 3 modes (plain, random stalls, heavy stall) == plain arithmetic, 18 of them using constants. The four signed-compare programs (`icmp_slt/sgt/sle/sge`) apply the corpus's OWN rules (arithmetic is the oracle only where the stock compare lowering's subtraction does not overflow, #931; vectors filtered by `no_overflow`) and are ALSO checked against the real VM on the 8 overflow-boundary vectors, where arithmetic is not the oracle: all agree.
- **Nano, dedicated:** `and`, `or`, `xor`, `and_c255` (a constant operand), a 3-nano chain, a REAL FORK feeding a nano, `add_then_xor`: each 16 items x **6 modes** -- plain, two random-stall seeds, heavy stall, and **two order-forcing skew modes (first input slow, last input slow) that force B-before-A and A-before-B arrivals deliberately** rather than by luck. All correct, in order.
- **Mutation controls on the `aload` glue, all caught:** B captured without waiting for A (a stale hold is read); A re-loaded when already loaded (the hold overwritten before B); the capture never clears `aload`.
- **Comparator, dedicated:** a hand-built relay -> comparator -> exit at thresholds 0, 5 and -5 over 12 probe values incl. INT_MIN/INT_MAX around each, 3 modes each; thresholds 0 and 5 also == the real VM; a zeroed-threshold mutant is caught.
All 14 suites pass: flex 51; generator 37; loops 9; addon 21; level 16; sequencer 20; branch 19; merge 17; netlist 12; compile 13; corpus 47; family equivalence 36; assembler 76; mul 38.

**A FINDING about the VM (a core-part cascade item; NOT patched):** at threshold -5 (0xFFFFFFFB) the flex hardware matches a true SIGNED compare on all 12 probe values, but the VM returns 0 for EVERY value. The VM declares `cmp_threshold: int = 0  # signed` but loads it raw -- `cell.cmp_threshold = cfg.get("threshold", 0)` -- and the ICM v3 `threshold` field is an UNSIGNED 32-bit field (bits 8-39), so a two's-complement negative threshold is read back as 4,294,967,291 and `signed(data) >= 4294967291` is false for every possible value. The RTL cells declare `reg signed` (flex: `reg signed [WIDTH-1:0] threshold`; sub: `reg signed [31:0] threshold`, both read, the sub one not tested), so the RTL agrees with the VM's own COMMENT about what the field means. The stock compiler only emits non-negative thresholds, so nothing in the corpus exercises it; recorded as a test that asserts the VM's behaviour (it must be revisited if the VM changes). VM catch-up item (#927).

## 948. ASIDE (Alan): "the nano logic shrinks to fit the current 18-bit target, not remaining at the original 32-bit?" MEASURED: the cells CAN shrink -- but the `--icm` path does not use it yet, the sub cells have no WIDTH parameter, and a much BIGGER saving turned up: the nano's topology is a runtime register, which costs ~28x more than a fixed one.

**Method:** `yosys synth_gowin` per cell, `chparam WIDTH` 32 vs 18; synthesis only, no place-and-route, no silicon. Reproducible: `python3 tools/measure_cell_width_v1.py`.

**1. Width: flex (v4sa) cells shrink; the ICM path does not use it.** Every flex cell carries a `WIDTH` parameter; almost every sub (v4s) cell does NOT (only the accumulator does), so the sub cells are hard-wired to 32 bits. And both ICM emitters (`flexsub_icm_generate_v1`, `flexsub_icm_flex_v1`) contain zero mentions of `WIDTH`: designs from `--icm` are 32-bit whatever the card's `native_width: 18` says. (Only the older step-1 chain assembler honours `-w` / the MAN width, #921.) Measured, 32 -> 18 bits [LUT1-4 / ALU / DFF]:
| flex cell | W=32 | W=18 |
|---|---|---|
| ram | 39 / 0 / 35 | 25 / 0 / 21 |
| **nano** | **1,088** / 0 / 76 | **626** / 0 / 48 |
| comparator | 28 / 32 / 35 | **86** / 18 / 21 |
| adder | 37 / 32 / 35 | 23 / 18 / 21 |
| mul (LUT) | 4,257 / 32 / 34 | **1,045** / 18 / 20 |
So the nano shrinks 42% in LUTs (37% in flops); the adder and relay roughly 40%; the LUT multiplier ~75% (it is quadratic in width). **An oddity, unexplained:** the comparator's LUT count goes UP at 18 bits (28 -> 86; LUTs + ALUs 60 -> 104) -- yosys maps the 18-bit signed compare differently; worth a look before relying on it.

**2. The bigger saving is not the width. The nano costs 1,088 LUTs -- about 34 per bit -- for what is one two-input gate per bit, because its topology is a REGISTER loaded at configuration, so synthesis cannot fold it and every bit carries a full 12-way selector.** A scratch copy with the topology pinned as a CONSTANT (what a fixed, generated design could use), for each of the 12 implemented topologies [LUT1-4 / DFF]: at W=32: pass A 6, pass B 5, NOT A/NOT B/NOR/AND/OR/NAND/XOR/XNOR **37-38**, const 0 4, const 1 5; at W=18: 4-24. So a fixed nano is **~38 LUTs at 32 bits (about 1 per bit) instead of 1,088, and ~24 instead of 626 at 18 bits** -- roughly 28x and 26x smaller, against 1.7x from the width alone; both together ~45x. (Gate names derived from the cell's own gate network: g0 = ~A, g1 = ~B, g2 = A&B, g3 = NAND, g4 = NOR, g5 = OR, g8 = XNOR, g9 = XOR. The register version is the true RECONFIGURABLE nano -- the architecture's point; the pinned version is only for a design that is fixed at generation time, i.e. what sub and the generated flex designs are, and the same logic as Alan's #939 ruling that mask/shift/invert become wiring once the variant is fixed.) The same question applies to the other configurable cells -- the comparator's threshold register, the adder's subtract-mode bit -- not measured here.

**What 18 bits would change, if the ICM path gained a width (not done):** the data nets, constants, thresholds and add-on maps all truncate to W bits; results wrap at 2^W; the sign bit is bit 17; the stock compare lowering's no-overflow domain (#931) shrinks accordingly; the add-on shift taps are defined on 32-bit lanes; and THE VM IS 32-BIT ONLY, so at 18 bits the oracle becomes arithmetic mod 2^18, not the VM (the VM width parameter is already on the #927 catch-up list). At 18 bits a `mul` could also use the MULT18X18 primitive exactly (the MAN now lists it, 0.25 block per instance = 48 instances on the Tang, versus 12 MULT36X36), so the multiplier ladder would change too.

**Not done:** nothing in the generators changed -- this entry is measurements and a tool. No width parameter on the `--icm` path; no pinned-topology nano; no comparator/adder-config measurements; the comparator anomaly is not investigated.

## 951. FLEX ICM GENERATION, STAGE 5: THE LEVEL SOURCES (accumulator, latch). Their pulse inputs have no handshake and can silently lose a snapshot, so the emitter gates every pulse by the cell's ready. Verified against the real VM.

Alan: "Continue" (the flex cores in order: level sources, then branch, merges, sequencer).

**What the flex cells actually do (read from `accumulator_cell_v4sa.v` / `latch_cell_v4sa.v`):** the pulse inputs (`inc_pulse`/`dec_pulse`; `set_in`/`clear_in`/`toggle_in`) are bare strobes with NO handshake; the internal total / state ALWAYS updates on a pulse, but the output snapshot (`out_buffer`) is captured only when the cell is NOT `pending`. A pulse that lands while the cell is pending is therefore COUNTED but its snapshot is silently LOST, so `data_out` goes stale. **The emitter's rule:** every pulse is gated by the cell's ready -- a pulse is `source valid & ack_out`, and the source is acknowledged at that same moment -- so every event is both counted and snapshotted and `data_out` always equals the true total. Several sources on one role OR together (one event, all acknowledged); a latch `set` also needs bit 0 of the arriving value (the value is consumed either way, as in the VM). **Level mode** (a continuous accumulator, any latch -- `is_level`, #938): valid is held high once armed (`ack_out | valid_out`), the cell's own `ack_in` is tied high so it never stalls, and consumers never acknowledge it -- no fork, no ack, like a constant. A level cell may itself be an output (its out valid is held high; the host's ack is ignored). **A pulse-mode accumulator** is an ordinary event source (fork, acks) but still pulse-gated. **Refused, as on sub:** a constant or level source into an accumulator's inc/dec or a latch's toggle (rate-dependent). `ASSEMBLY.json` lists `level_sources`.

**Verified (`tests/test_flexsub_flex_level_v1.py`, 37/37, new).** A level never "completes an item", so the observation is different from the stream tests: the level is SAMPLED EVERY CYCLE and the SEQUENCE OF DISTINCT VALUES it passes through is compared -- which exposes any dropped or duplicated event whatever the timing -- against the REAL VM's per-item totals/states:
- counter (nine increments of 3): [0, 3, 6, ... 27] == the VM, back-to-back and under random input gaps;
- **up/down with TWO sources** whose arrivals interleave differently in every mode (plain, two stall seeds, first-input-slow, last-input-slow): the final level (8 inc - 3 dec of 5 = 25) is right and every level visited is a reachable partial sum;
- **pulse mode**, both directions: the discrete events [30, 30, 30] / [-30, -30, -30] == the VM's, through random exit stalls;

**A problem the handshake creates that sub never had -- the SPURIOUS-EQUAL TRAP.** In sub a stream's valid is a one-cycle PULSE; in flex it is HELD until acknowledged. ## 954. FLEX ICM GENERATION, STAGE 7: THE MERGE. It CAN be done with the existing cells -- selection logic in front of an ordinary cell, no new cell -- and the WHOLE hand-built CORDIC now runs on flex, matching the real VM. Two limits stated plainly.

Alan: "check if it can be done, and if not we can add a merge core function for the flex system specifically ... it could be set to merge from two paths or just one, a selectable option giving greater flexibility overall."

**Answer: yes, it can be done without a new cell.** The planner's merge record is just a list of sources for a single-input consumer; a merge is selection logic IN FRONT of an ordinary cell, so the cells are unchanged. **The emitter glue is an ARBITER**, not an OR: grant ONE source, acknowledge ONLY the granted one, and rotate priority after every grant (a round-robin flag) so neither source can starve. **Why not simply OR them, as the VM does?** Under a handshake two sources can BOTH stay valid for as long as the cell is busy; when it frees up, a plain OR would consume both and FUSE two separate items into one corrupt value. (Constants in a merge stay refused by the planner: always valid, they would swamp the stream. Three or more sources are refused: the arbiter handles two.) A bug of my own on the way: my edit removing the blanket merge refusal also deleted the `levels` line `generate_flex` needs (a NameError); restored.

**Verified (`tests/test_flexsub_flex_merge_v1.py`, 16/16, new):**
- **THE WHOLE CORDIC on flex** -- 36 cells (24 relays, 8 adders, 4 branches, with 4 arbitrating merges and 12 constants) -- generated with no new cell: 12 starting angles (both signs, 0, +-1, beyond convergence) == the REAL VM in plain and two stall modes, ONE item in flight at a time, plus the independent anchor z0 = 50000 -> -404.
- hand-built two-source merges, 10 + 10 items x 5 modes (plain, two stalls, first-slow, last-slow): every item emerges exactly once, UNCORRUPTED, each source's own order kept; FAIRNESS (both sources always valid: the first 8 outputs are 4 from each);
- **mutation controls, all caught:** the plain OR (the VM's rule: fuse and acknowledge both); acknowledging both sources although only one is granted (an item consumed but lost); a priority that never rotates (the second source starves);
- refusals: a three-source merge; a merge including a constant.

**TWO LIMITS, stated plainly (both recorded as tests, not buried):**
1. **A semantic divergence from the VM.** Two items arriving in the SAME cycle: the VM ORs them into ONE value (0x0f0 | 0xf00 = 0xff0); flex SEQUENCES them: two outputs (0x0f0 and 0xf00). So a design that relies on the "free OR" to COMBINE two simultaneous halves into one word is NOT reproduced by the arbiter. Under a handshake that intent needs a different operation -- wait for BOTH sources, then OR (a join) -- which flex does not have yet.
2. **An arbiter cannot restore ORDER between two paths.** Fed 8 angles back-to-back through the cordic, NO value was ever corrupted or lost (the outputs are exactly the 8 correct results as a multiset, in all 4 modes), but in 1 of the 4 modes the outputs came out of order: item k can wait on one path while item k+1 overtakes on the other. So a merge is only well-defined when at most one item is in flight in the region -- true of loop-style designs like the cordic, never of the compiler's output (which has no merges). A merge CELL could not fix this either (it would need per-item tags).

**Stale assertions updated (not hidden):** the main flex suite (now 52) no longer says cordic or a two-source merge is refused; it now checks the cordic generates and a THREE-source merge is refused; the generator suite's "what flex refuses" example is now a sequencer (still refused), 37/37.

**Suites (final state):** flex_merge 16 (new); flex_branch 20; flex_level 37; flex 52; synthflag 20; mul 42; assembler 76; corpus 47; family equivalence 36; loops 9; addon 21; level 16; sequencer 20; branch 19; merge 17; generator 37; netlist 12; compile 13; plus the repo's MAN 14 and card-fit 28.

**DECISION for Alan, with the facts:** the merge CORE you proposed (a cell with a selectable mode) is not needed to make the cordic run -- the glue does it, and glue costs a few LUTs instead of a whole cell. Where a cell WOULD add something: (a) it would give the missing operation, a mode that WAITS for both sources and ORs them (the "combine" use of the free OR, divergence 1 above), and a pass-through single-path mode, selectable by configuration; (b) it would be the right form for a grid that is configured at run time rather than generated. ## 956. FLEX ICM GENERATION, STAGE 8: THE SEQUENCER -- the last ICM core the planner translates. Free-running, paced by the consumer's ack, exactly as Alan described. Plus a real defect fixed in `sequencer_cell_v4sa`.

Alan: the sequencer "originally just ran on the clock signal, or the ack signal advancing each tick, so technically it should stay the same, so with the pairing that would work -- the adder cell just sends it an ack signal, once it's cleared its internal sequence and the sequencer sees this and fires, switches to the next value and waits."

**What I found by reading and simulating the real cell BEFORE building (reported to Alan first):** `sequencer_cell_v4sa` is NOT ack-driven as we had assumed. It still advances only on an external `advance_in` pulse; the ack merely gates it (no advance while an offer is pending). It offers nothing at rest (the resting value is never offered) and the first value it offers is the SECOND one (`20 30 40 10 ...`), exactly like the sub cell (#937). **Alan's model is reproduced** by tying `advance_in` to the cell's own READY (armed & not pending): whenever the previous value has been taken the cell offers the next one and waits -- the VM's "advance when drained", paced entirely by the consumer's ack. The stored values are rotated one step (new[j] = V[(j-1) mod n]) so the sequence starts at VALUE_0 and wraps like the VM's.

**A REAL DEFECT in the cell, found by that probe and now fixed:** an UNCONFIGURED `sequencer_cell_v4sa` with `advance_in` high offered a spurious value (valid_out = 1). Its `advance_in` branch was gated by `pending` and `freeze_in` but NOT by `armed`; every other v4sa cell is armed-gated, the sub cell gates its output on armed (`valid_out_r <= armed && advance_in`), and the original v4 is armed-gated -- only this one lost the gate, presumably when the ack/pending discipline was added in #915, and its bench never tested the unconfigured case. **One-line fix** (`advance_in && armed`) with a new bench case; **verified the case really catches it**: the bench is ALL PASS on the fixed cell and FAILS exactly that case on the unfixed cell. (My first check wrongly concluded the case was "too weak": the bench's `label` argument is a 32-character field, my label was truncated and my own filter looked for a word that was cut off -- the bench itself was right. The label is now short enough to print.)

**The emitter/planner:** the sequencer is an INTERNAL source (not a host entry port: nothing feeds it, so it is excluded from the entry list and gets `advance_in = <cell>_rdy`); consumers use the usual edges, and fan-out the usual eager fork (advance only once every consumer has taken a value). The planner's refusal of a sequencer feeding a two-operand cell (a VM-self-pairing finding, #937) now applies to the SUB family only; on flex it is translated, and a sequencer feeding a MERGE is refused (which value the merge takes is ambiguous).

## 958. THE ICM `min_bit_width` HEADER FLAG, in the load and save functions of all three formats (icm-v3, icm-v4, icm-vix). Alan's rulings applied; the narrowing/padding that the loader and save will do is NOT built, and one question about how it should be written is open.

Alan's answers: (1) **the width minimum goes in the HEADER -- it has to be a transferable artifact**; (2) **the default stays 32 when it is not present** -- "the load and save mechanisms will deal with that side, to allow the icm to remain as open and cross targetable as possible"; (3) **the ICM loader and save function files are the points to target, then the VM side**, "where more things may change as we go".

**The points targeted:** `nano/icm_v3.py` (`IcmV3File`), `nano/icm_v4.py` (`IcmV4File`), `nano/icm_vix_v1.py` (`IcmVixFile`) -- each file class has its own `save`/`load`/`to_dict`/`record_hash` -- plus a new shared `nano/icm_width_v1.py` holding the rule once (validation; the 32 default; the hash suffix).
- **The field** `min_bit_width`: an integer 1-64 or absent; `bool`, strings, 0 and 65+ are refused (`IcmWidthError`, a `ValueError`); validated on construction and on load.
- **Where it lives:** ICM-VIX: inside `header`. The flat v3/v4 files have no header section but their top-level keys (`format_version`, `cell_type`, `name`, `description`, ...) already ARE their metadata, so it is a top-level key there.
- **Stored, not derived -- reconciling it with the VIX header's own rule.** The VIX header is deliberately DERIVED ("never hand-maintained", #734's lesson): `cores_used` and `cell_count` are recomputed from the data every time, and a stale or hand-edited value in a file is ignored. `min_bit_width` cannot be derived from the data, it is a user DECLARATION, so it is the one STORED header field; the other two remain derived exactly as before (tested: a file whose derived header was tampered with still loads, and `header()` recomputes).

**Nothing existing changes -- proved against the ORIGINAL code, not asserted.** I ran the same battery through the pristine `HEAD` modules and through the modified ones: the 3 VIX examples and v3/v4 files of 1, 3 and 8 cells; for each, `header()`, `to_dict()`, `record_hash()`, the flattened records, the SAVED FILE'S BYTES (sha256) and the hash after a reload: **9 of 9 identical**. (A first round-trip check of mine suggested the example files do not reproduce exactly; the pristine code shows the SAME differences -- the hand-authored examples store `cores_used` unsorted, omit `name`, and the v3 demo's stored hash never matched. Pre-existing, not mine; my check had been too strict, so I replaced it with the differential above.)

**The consumers.** The `--icm` generators (sub and flex) read the declared width (the flat-file wrapper `_FlatDoc` did not carry it, which my first trial caught -- fixed), **record it in `ASSEMBLY.json` (`min_bit_width`, `built_width`)**, ACCEPT a declared minimum up to 32 (they build 32-bit designs, which meets it) and REFUSE above 32 naming the declared width and why (e.g. 36). `flexsub_compile_v1.py --min-bit-width N` declares it where the design is produced (an invalid value is a clean error, rc 2, not a traceback). `docs/stripped-cell/ICM_VIX_FORMAT.md` documents the field.

**Verified (`tests/test_icm_min_bit_width_v1.py`, 43/43, new):** validation table; golden hashes and derived headers from the original code (3 VIX examples + v3 + v4); round trip through all three formats (saved in the right place, reloaded, same hash); the flag is covered by the hash (the same content without it hashes differently); a hand-edit 18 -> 36, DELETING the flag, and an invalid value in the file are all caught on load; the derived header fields stay derived; `flatten()` unaffected; the compile tool; both generators with no flag / 18 / 32 / 36; an ICM-VIX file with header 18 (generates) and 36 (refused). **Two vacuous assertions of mine were found on re-reading and replaced** ("covered by the integrity hash" ended in `if False else True`, always true): the real check passes, and breaking the hash on purpose to ignore the flag makes 10 checks fail -- so they bite. **NOT built -- what Alan said the loader and save will do, and the question it leaves.** The loader will truncate a design that does not need the full 32 bits down to the target's native width (18), the save will provide just those bits padded to 32, and where the design needs more the flex/nano cells are widened (to 36) before loading. (b) seems to serve "open and cross-targetable" better, but it is Alan's call. Related rules I would apply conservatively unless told otherwise: a constant, threshold or init value that does not fit the declared width as a signed number is REFUSED, never silently truncated.

**Not done:** the loader's narrowing and the save's padding; any width plumbing in the generators (they still build 32 bits); the per-merge mode in the ICM (still a command-line option -- the VIX header is not the place for a per-cell flag; a per-merge declaration needs a place in the cell records, a format change); the genuine `priority` arbiter; the VM side, which is next. Nothing has run on silicon.


## 959. RULING (Alan): the ICM stays STRICT and sign-extended; using a target's spare bits to hold sign data is a TARGET-SPECIFIC encoding, declared in the file when used -- not part of the ICM. Recorded; no code changed.

Alan, answering the open question of #958 (how a narrow design's negative values are written when padded to 32): "yes, and in the case of the Tang, as it has a native 18 and 36 there is space to hold the sign data, though this should be declared in the file when widths are above a certain level, i.e. not 8, not 16, not 32, allowing that data to be added, but this may cause confusion for other strict 8/16/32-bit systems where the sign is not stored, so this becomes a specific target item, not what the ICM was built for."

**How I read it (stated so it can be corrected):** (1) **the ICM itself is option (b)** -- values are plain numbers, **sign-extended** to the 32-bit field when a narrower design is saved, so the file is a lossless 32-bit ICM for ANY consumer, with or without reading the header; a narrow target reads `min_bit_width` and CHECKS that each value fits, refusing (never truncating) one that does not. (2) **Storing sign information in the spare bits of a non-strict width is a target-specific encoding**, defined and written by the target's own save and load and DECLARED in the file when it is used (a width other than 8, 16 or 32), because a strict 8/16/32-bit system does not store or expect it. **What it leaves, honestly:** (a) the loader's FIT CHECK (every value-bearing field fits the declared width as a signed number) is not built -- it has no consumer until a generator builds narrower than 32; it needs a list of the value-bearing fields (the record-level `preload_value`, the comparator `threshold`, the branch fixed values, the accumulator `threshold` and `step_amount`, the sequencer's unsigned 8-bit values) and I would build it with the first narrow build, not before; (b) the Tang's spare-bit encoding has no definition yet -- WHERE it is declared in the file (a clearly namespaced optional section that strict readers ignore, such as a `target_extensions` entry keyed by target, would fit the rule) and WHAT it holds are open, and I have NOT verified how many spare bits the Tang's memories or DSPs actually offer (the MAN records a native width of 18 and the DSP operand widths 18 and 36, read from yosys; nothing records the memory word layout).
**Next, as Alan said: the VM side**, where more is expected to change.

WHAT a cell is -- its ports, what each means, which faces it uses -- is the CORE's (fixed by its design: the branch has two inputs and per-outcome outputs, the merge core two inputs). ## 963. READ-ONLY FINDINGS: the three nano variants side by side (the step #962 set for this session). Nothing was changed.

Files read: `fpga/verilog/nano_gate_v4.v` (443 lines, standalone), `nano_gate_v4c.v` (375, carrier core), `sub/verilog/nano_cell_v4sa.v` (121, the flex nano, has a WIDTH parameter); `sub/verilog/nano_cell_v4s.v` (138, the sub nano) only counted, NOT read in detail.

**1. v4 and v4c differ in exactly ONE thing.** A code-only diff (comments and whitespace stripped) leaves 27 lines, and they are all one feature: v4 has the OUTPUT ADD-ON CHAIN (nibble-mask -> shift-lane -> invert, fed by a 20-bit `addon_config` held in the command latch, with its own `PROG_ID_ADDON_CONFIG = 7`) and drives its four outputs from the chain; v4c has none of it and drives its outputs straight from `out_buffer` (in the carrier system the add-ons live elsewhere). The core NOR network, the pattern compare, the data path and the command-word layout are otherwise identical. So v4c is v4 minus the add-on chain: "complementary" confirmed in the code.

**2. The core nano is BITWISE.** In all three the operation is a network of ten NOR gates (`g0`..`g9`) applied per bit to `input_val` and `second_val`, selected by a 10-bit topology word. No carries, no shifts, no rotates. Widening that part is mechanical (the operand wires become `[W-1:0]`); there is no W-bit arithmetic to define. This is why the flex nano (`v4sa`) already carries `[WIDTH-1:0]` throughout (16 of its 23 WIDTH references are declarations) and `v4`/`v4c`/`v4s` do not (zero WIDTH references; 17-21 hard-coded `[31:0]`).

**3. The one operation that depends on width: the pattern compare (v4, v4c only).** `cmp_gt = second_val > input_val`, `cmp_lt = second_val < input_val`, selecting `pattern_high/low/equal` (4-bit N/S/E/W routing patterns) for dynamic routing. It is UNSIGNED (no `signed` anywhere in either file), and the VM's `CACell._effective_routing` is also unsigned (`second_val > input_val`), so they agree. An unsigned compare at W bits needs no new definition, just wider operands. The flex nano (`v4sa`) has NO pattern compare at all (zero references), so the compare question does not arise for the family the 36-bit ruling is about.

**4. The width is tied to the command word in v4 and v4c.** `out_buffer = cmd_latch[127:96]`: the 32-bit data slot is the TOP slice of a fixed 128-bit command latch, and it is written only internally (from `computed_output` or `data_reg`, never through the program bus). All configuration fields sit below bit 96 (topology [9:0], ready [13], addon [33:14], masks [75:64], patterns [91:76], dynamic-route [94]), so widening the data slot to 36 changes the TOP of the word only (128 -> 132 bits, or the data moved to its own register); the configuration layout is untouched. The program bus is 32 bits (`prog_id` at [23:20], 20-bit `prog_word`) and carries no data, so it need not widen. NOT yet checked: whether anything outside these files (the carrier, the loader, `root_definition.json`) assumes the 128-bit word or 32-bit data slot.

**5. Add-ons.** The add-on modules are 32-bit lane definitions (as #961 found in the VM). So v4 at another width needs those redefined or disabled; v4c has none and is therefore the CLEAN one to widen first.

**What this means for the VM (`CACell`, refused at W != 32 today):** its NOR operations and unsigned compare would simply take the wider mask, matching items 2 and 3. NOT verified: that `CACell`'s output add-on handling matches v4 (the VM's `apply_addons` is the 32-lane one, refused at other widths), and I have not diffed `CACell`'s truth table against the RTL's topology decode at all.
**Proposed order, for Alan to confirm:** (1) widen the flex nano's already-parameterised cell and cross-check it against the VM at W=18/36 (cheapest, directly the 36-bit ruling); (2) parameterise `CACell` and `v4c`; (3) `v4` last, since its add-on chain needs a W-bit definition first. One question for Alan: should the 128-bit command word grow to 132 bits, or should the data slot move out of it?


## 964. READ-ONLY SURVEY for `FlexGrid` (Alan: "lets go"): how the VM is extended today, and what a flex mirror has to model. Nothing changed.

Alan's ruling (#963 discussion): flex is the only family where width and behaviour really differ, so a flex mirror is a SEPARATE VM variant (`FlexGrid`), leaving the std VM untouched; `CACell` (the standalone v4 model) stays alone.

**What exists (read today, in `unicell_super_automaton_v1.py` and `vix_carrier_automaton_v1.py`):**
1. **Subclass pattern:** `VixCarrierGrid(SuperGrid)` and `VixCarrierCell(SuperCell)`. The grid builds its cells through its own `from_record` and SKIPS the parent constructor (which is why #961's class-level width defaults of 32 were needed).
2. **Core behaviour is a MODULE-LEVEL registry** `_CORE_HANDLERS`, keyed by core name; `register_core_handler` RAISES on a duplicate name. So a flex grid cannot register different "adder" / "branch" behaviour there. Handlers are looked up at FOUR sites (deliver, offer_state, continuously_live, clear_valid), each `_CORE_HANDLERS.get(self.core)`.
3. **The nano is special-cased**, not registered: `if self.core == "nano"` delegates to `CACell` in several methods. A flex nano (hold/flow, bitwise, no pattern compare, already WIDTH-parameterised) would have to override those branches.
4. **The tick model is event-driven with per-direction arrivals:** each tick a cell's `deliver(arrivals_by_direction, injected)` may accept a SUBSET of the directions; refused ones are RETRIED next tick. So back-pressure already exists, and the direction an item came from is available to a handler.

**Proposed shape (not built):** (a) a tiny refactor of the shared file: the four lookups call `self._handler(name)`, which in the base class returns `_CORE_HANDLERS.get(name)` exactly as now (provable by the existing suite: 1539 tests); (b) `FlexCell(SuperCell)` with its OWN handler table for the cores whose flex behaviour differs, and an override for the nano branches; (c) `FlexGrid(SuperGrid)` that builds `FlexCell`s, takes the width, and is where the family is chosen at start-up (`vm flex -w36`).

**The important finding: a flex mirror has to model the GENERATOR's translation, not just the cells.** Flex behaviour comes from the cells PLUS what `flexsub_icm_generate_v1.plan(family="flex")` does to the ICM: it inserts merge cores (mode per merge), lowers the branch, assigns A/B roles for two-operand cells, turns a constant into an always-valid source, gates level-source pulses, and ties the sequencer's advance to its ready. So a ram -> adder chain in the VM and in flex differ not only in the cell but in the surrounding structure. FlexGrid should therefore take its structure from the same planner (or share its role and merge decisions) rather than re-deriving them, otherwise the two will drift.

**A useful reversal this makes possible:** until now the real VM was the oracle for the flex RTL (our flex suites compare iverilog runs to the VM). For FlexGrid the RTL becomes the oracle: the existing `run_level` harness and the generated designs can check FlexGrid cycle for cycle on the same ICM.

**Proposed order:** (1) the four-site refactor + an empty `FlexGrid` that must equal `SuperGrid` on the whole existing suite; (2) the flex nano (not `CACell`) with width; (3) role-based pairing for the adder and multiplier; (4) merge, in both modes; (5) sequencer free-running; (6) level sources, branch, constants; each step checked against the generated RTL. **NOT checked today:** the handlers' own code (`_deliver_adder` etc.), the planner's role assignment as an importable API, and `root_definition.json`'s coverage (still the open survey from #963's follow-up).

## 968. THE MASK WORD SCALES WITH THE WIDTH (Alan's ruling), replacing the fixed nibble: resolves the #967 mask_cell_v4sa finding.

**Ruling (Alan, 2026-10-06):** the mask word stays 8 bits at every width; each mask bit covers GROUP = ceil(WIDTH/8) data bits (1 bit up to W8, 2 up to W16, 3 up to W24, 4 up to W32, 5 up to W40). A single uniform rule, no extra masking layer; chosen over a "nibble up to 32, grow above" variant. Consequence, accepted: below 32 the same mask value means different data bits at different widths (W18: a mask bit = 3 bits, 6 groups). At W25..32 GROUP is 4 = the old nibble, so WIDTH=32 is unchanged. To be documented thoroughly in the user documentation.
**Changed:** `sub/verilog/mask_cell_v4sa.v` (GROUP/NIBBLES localparams; the generate loop uses GROUP); `tb_mask_cell_v4sa_width18.v` rewritten for the new rule (group 0 = bits 2:0, top group = bits 17:15, all 6 groups, mask bits with no group ignored; a mutant with GROUP forced to 4 is caught by it); `tb_mask_cell_v4sa.v` (W32) passes UNCHANGED; mirror `flex_addons()` in `nano/flex_grid_v1.py` uses the same rule; `sub/README.md` mask section updated.
**Proof:** `tests/vm/test_flex_grid_addons_v1.py` (24): the pinned-defect test is replaced by "every data bit has a mask bit and the real cell never drives x" at W = 4, 8, 9, 16, 17, 18, 24, 25, 32, 33, 36, 40 (all-ones mask clears everything; each single mask bit clears exactly its own group); the mask-vs-RTL and composed-chain tests now run at W36 with masking enabled (they had to exclude it before); a mutant mirror with a fixed 4-bit group fails 9 tests.
**Not re-measured:** the mask cell's LUT/DFF cost (the nibble design's figures in the #877 notes are for the old structure; at W32 the logic is identical, at W18 it differs). ## 969. FLEXGRID STEP 5: the flex MERGE (arbitrate and join-or) is mirrored and equals the generated RTL, including the whole CORDIC.

**What the flex family does that the std VM does not:** the std VM ORs same-tick arrivals at a multi-source input into ONE value. In flex the generator puts a merge core (merge_cell_v4sa) in front of the consumer: ARBITRATE grants one source at a time (A first, then round-robin via a flag that rotates after every grant, the loser stays pending and is served later); JOIN-OR waits until EVERY source is presenting and ORs them.
**Built (`nano/flex_grid_v1.py`):** `_flex_deliver_ram` registered as the flex handler for `ram` (single source = the std relay unchanged); `FlexGrid(records, width, merge_mode="arbitrate")` takes the generator's own spec (`parse_merge_modes`: 'arbitrate' | 'join-or' | 'cell=mode,default') and, per relay with several sources, records the operand order (A = the source that comes FIRST IN THE ICM RECORD LIST, which is what the generator does) and the mode. Uses the VM's existing partial-accept mechanism (as `priority` does): the loser is simply not accepted and is retried. Join-or accepts nothing until all sources are present, for any number of sources (OR is associative, so a tree of joins = a join of all). REFUSED with a reason: arbitrate of 3+ sources (a tree of round-robin cores whose grant order is not mirrored) and a merge into a comparator (not mirrored yet).
**Proof:** `tests/vm/test_flex_grid_merge_v1.py` (10), against designs GENERATED by `project_assemble_v1 -s flex` and run in iverilog: a same-cycle pair is SEQUENCED by arbitrate in the same order as the RTL while the std VM fuses it (both asserted); 8+8 streams (every item once, own order kept, both sources served early); join-or pairs OR'd in order EXACTLY equal to the RTL; a lone item waits and is never fused with a later one (8 X vs 5 Y -> 5 outputs); 3-source join-or equals the RTL; per-consumer mode spec; **the whole hand-built CORDIC (36 cells, 4 merges) in FlexGrid gives the generated RTL's z_output for 12 angles and the independent anchor -404**; a mirror falling back to the std relay is caught; three mutants of the handler (A/B priority swapped, flag never rotates, join-or not waiting) each fail the suite.
**Housekeeping:** the step-1 skeleton tests ("empty FlexGrid == SuperGrid") now run with the flex handler table cleared (it is no longer empty), and ignore the flex-only merge bookkeeping attributes; `tests/vm/flex_rtl_harness_v1.py` holds the generate-and-run helpers (copied from `tests/test_flexsub_flex_merge_v1.py`, which runs its checks at import).
**Not mirrored (stated):** exact tick counts (the VM is not cycle-accurate to the handshake family), the tree grant order of 3+ arbitrate sources, a merge into anything but a relay.
**Next:** sequencer free-running, level sources, branch lowering, constants.
