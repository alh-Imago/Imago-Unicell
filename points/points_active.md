## #1584 (28 Nov 2026) -- THE MULTIPLY UNIT: RTL (sc_sys_v23, MULU), library and host side, build files; tested in simulation, NOT built with Vivado, NOT run on a card

*Asked by Alan (28 Nov, 01:30):* "if we apply the changes now, i can run the builds over night, so the lib_mul32, add in the dsp side, as 1 per block, we now have a soft option, and remind me again on the in slice refinement". I reminded him of the refinement (operand stores answered inside the slice; only the product load waits for the slot) and built it that way; he has not said yes or no to it, so it can still be reversed (MULU=0 gives the v22 behaviour).
**RTL:** `sc_sys_v23.v` (v22 stays), parameter MULU (0 = nothing added, the window traps as in v22). With 1: a device window at data word index 2^(SHL+1) (byte 0x20000): store +0 = operand A, store +4 = operand B, load +8 = (A*B) mod 2^32; anything else in it traps (cause code 2; no new cause code). Per slice: operand registers, written straight from the finished store word (no slot wait); a product load is a shared-RAM-style read request flagged `rq_dev`, held 3 clocks after the last device store (`dv_stale`). Per block: one multiplier fed the operands of the slice whose slot comes 2 clocks later (`msel`), three register stages, so `mul_q` holds that slice's product when it captures (replaces `sdq` for a flagged read). The multiply is a plain 32x32 low-32 `*`: yosys maps it to 3 DSP48E1 (checked alone, 3). Whole-top synthesis in yosys (2 blocks, S=8): 7 DSP48E1 with MULU=1, 1 with MULU=0, i.e. +3 per block; the 1 that every Kintex build has is still unexplained (it is there with MULU=0 too). Resource numbers beyond DSP count were not looked at.
**Tests (iverilog, test_sys23.py + tb_sys23.v):** S=8 ULW 2 NU 2, S=4 ULW 2 NU 1, S=16 ULW 3 NU 2: 16 products (edge cases and random) correct at every fusion width alone and together, mixed with ordinary jobs and with the bad accesses (load from +0, store to +8, word +12), which trap with cause 2; the real library routine `jobio/lib_mul_unit.s` called with a jump gives the right products; with MULU=0 all multiply programs trap (cause 2) and the ordinary programs (sum100, fib, crc32, softmul_gcd) still pass. Clock figures from those runs are not multiply costs (they include task start-up); the cost is to be measured on the card.
**Host side:** `jobio/lib_mul.s` (software shift and add, #1582) and `jobio/lib_mul_unit.s` (unit); `jobio_ext_v1.py` links the unit version when the build's `mul_units` > 0 and the software version otherwise, writes the count into job header word 7, and installs `jobiss_v2.py` (the interpreter with a model of the unit). **Change from the plan in #1580/#1581:** the choice is made at link time from the build's `mul_units`, not by a run-time test of word 7 (that test would have cost one shared-RAM access per multiply: 207 clocks at lw 0, 32 at lw 5); the header word is still written, for information. On the host interpreter vmul32l runs 599 instructions instead of 9,519 (40 words, multiplier 0xFFFFFFFF), results equal; test_jobio_ext_v1.py. `score_store_v2.py` adds `mul_units` to the build entry (0 when the manifest has none; 1 for a name with line letter m and no manifest); score_shell_v11 and scwin_v22 use it (their tests pass).
**Build files:** `fpga/sc_block_v7.v`, `fpga/sc_top_k7_v19.v` (parameter MULU), `make_manifest_v3.py` (fields mul_units, mul_unit_dsp_blocks; with MULU 0 identical to v2 apart from those two fields), `k7/make_mb_v14.py` (6th argument; with 0 it writes the same files as make_mb_v13.py apart from the comment line, checked) and `k7/stage_mb_v13.sh`. A build with the unit is named `hm<NB>s<S>u<W>n<NU>i<IMEM>` (fits the name pattern of score_store). `batches/mul_unit_cost.score` and `mul_unit_cost_calc_v1.py` are written for the card measurement. How to build and test: s-core/MUL_UNIT_BUILD_v1.md.

**Estimate (not a measurement; assumes the 10 loop instructions around the multiply cost the average clocks per instruction):** a loop word is about 1,355 clocks (lw 0) and 130 (lw 4), so the multiply by the unit is about 890 clocks (lw 0) and 117 (lw 4) and the software multiply about 30,350 and 2,917: roughly 34 times and 25 times for the multiply alone. The unit's multiply is the call, the lui, the three device accesses, a register move and the return: 7 instructions, which at 135.5 clocks each is about 950, close to the 890 above; so **the wait for the unit's slot is small and the cost is the instruction count around it**. The estimates of #1581 (472 and 48 clocks per multiply) were therefore too low for this library routine (the refinement removes the store waits but not the extra instructions). Inline use (no jal / ret, base address kept in a register) would need about 3 instructions; not built.
