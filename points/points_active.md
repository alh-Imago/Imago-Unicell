Modes from `merge_cell_v4sa.v`: A only, B only (the other input is never accepted), arbitrate (one at a time; the loser gets priority next time, the first tie goes to A), join (waits for both, outputs A OR B bit by bit, takes both). ## #1044 -- TEACHING MANUAL PART 6: REMEMBERING, LATCH AND SEQUENCER (Alan's direction)

## 1068. Division as a runtime loop in the VM: repeated subtraction works and is tiny, but it is slow and narrow -- the 32-step unrolled design stays the general answer (Alan/Claude, 2026-10-12)

Alan asked for the loop version of division ("or a multiply loop as a side trick"). Built and measured in the VM only; no RTL, no hardware.

**Built:** #518's shape in the VM -- three cells: SUB (accumulator, step = divisor), BR (branch cell, held reference A-B, "continue" routed to SUB and to Q), Q (accumulator, step 1, the quotient). 3 cells instead of ~23,000. Quotient = Q, remainder = A - SUB. Test: `tests/vm/test_division_loop_v1.py` (5 tests pass).

**Harness steps, stated plainly:** (1) A-B is worked out outside and set as BR's held reference on the cell directly (as #518 did with a host-precomputed constant); a formula would need a subtract cell and a sequenced first arrival to do this inside the design -- not built. (2) SUB's freeze input is driven each tick: unfrozen for the first tick, then frozen unless BR is holding a continue.

**Measured:** 157 cases (150 random with A up to 3000, B 1..255, plus edge cases) all equal Python's quotient and remainder. Without the freeze gate the quotient is exactly one too many and the remainder is short by B -- the same race #518 found in RTL (a stale value is offered twice), now reproduced in the VM. The startup window matters: unfrozen for one tick works; two ticks fails every case with quotient 1 (found by testing, not predicted). Speed: 2 VM ticks per unit of quotient, so time grows with the answer (quotient 53 took 106 ticks).

**Limits found (all real):** the accumulator step is 8 bits (`& 0xFF`) and its threshold 16 bits, so the divisor must be 1..255 here; the number of passes equals the quotient, which for a 32-bit dividend can be 2^32 passes; divide by zero NEVER halts (checked: the counter keeps climbing), so a loop version needs an explicit guard to match the front end's "x/0 = all ones". Bit-serial long division (32 passes always) needs three circulating words plus a counter (merge + branch cells per variable); that dataflow loop is still not built.

**The multiply question:** not wrong, but it does not replace the loop. A multiply-based divide needs a reciprocal (Newton iteration, which is itself a loop) and the high half of a product, then a correction step; it is the right tool for a CONSTANT divisor (reciprocal worked out at compile time) and is NOT built or measured here. ## 1077. K (quotient bits per clock) becomes a design-time setting of the divider, at one fixed place in the record (Alan/Claude, 2026-10-12)

The change follows that:
- **ICM record:** new div field `steps` at bits 18-23 (0 = not set, the family's own default). `root_definition.json` and the tile's optional params list it. Read at generation time, not by a running cell.
- **Flex:** the generator builds each div cell with `.STEPS(K)` (and refuses K above the built width, e.g. K=16 with `-w 8`). **Sub:** refuses K other than 32 with the reason (a looped divider needs a latency and throughput model in the planner, not built). **VM:** ignores it (timing is data-driven). **Capability check:** `steps` on a non-div core, or outside 1..32, is a problem on every target.
- **v4/v4c carrier (both files) and the two shells:** new build-time parameter `DIV_STEPS` / `STEPS` (default 1), passed to the core. It is per build, so every carrier of a grid is alike; it is not an ICM-programmed value there.
- **LaTeX:** `compile_latex(div_steps=K)` and `--div-steps K` set it on every division cell. W was already settable at assembly (flex `-w`); K was not until now.

**Checks:** `tests/vm/test_div_steps_field_v1.py` (11 tests: bit position and round trip; LaTeX sets it and validates; VM unchanged; capability messages; flex RTL built at K = 1, 4, 13, 32 agrees with the formula; width refusal; sub refuses 4 and accepts 32; CLI) and 6 new carrier tests (v1 and v1d at K = 1, 4, 32: the testbench prints the core's own STEPS and the carrier divides correctly). Mutations checked: flex emitter always writing `.STEPS(1)` (caught, 3 fail), sub refusal removed (caught), carrier not passing `DIV_STEPS` (caught, 2 fail). The existing carrier and hold/corner tests pass (35).

**Not done:** the full `quick_check --changed` run was not completed (interrupted); a K below the built maximum chosen live (skipping steps) is possible but not built; the sub looped forms; a LaTeX design on the carrier grid (Alan's own test later). No area or Fmax claim is made; see the #1072 sweep for measured sizes.

## 1078. The arithmetic plan library, first plan: Horner polynomial (Alan/Claude, 2026-10-12)

Alan asked for library plans (a base pattern and a rule for joining copies to grow it) so the compiler places a known shape instead of rebuilding extended maths from single operations; polynomials first. Built:
- **`nano/arith_plan_library_v1.py`** (new): a `Plan` (name, base pattern, ports, operation-count formula, `emit`) and the `horner` plan: base stage `acc' = acc * x + c`, one copy per degree, out of one stage into the acc port of the next. The plan writes its stages through the front end's own emitter, so the compiler, placer and cells are the ordinary ones; the plan fixes the shape. Identities: a zero coefficient drops its add, a leading 1 drops the first multiply.
- **Front end:** `_poly_of` recognises a one-variable polynomial (sum, difference, product, whole power, negation; expanded mod 2^32, degree up to 64). `compile_latex(polynomial="auto")` (default) builds the formula directly and with the plan and keeps the one with fewer cells (a tie keeps the direct form); `"horner"` / `"direct"` force; CLI flag `--polynomial auto|horner|direct`. A polynomial inside a bigger formula (e.g. divided by z) is placed as the plan too.
- **Measured (cells, direct / Horner):** `3x^2+2x+1` 44 / 26; `x^7` 61 / 38; `2x^5-3x^3+x+9` 75 / 50; `x^4+x^3+x^2+x+1` 76 / 44; `(x+1)^3` 23 / 32 (direct kept); `x^2`, `x^3` unchanged (8, 14). A dense polynomial is exactly **12 cells per degree + 2** (degrees 1 to 8 checked). Operation counts mislead: I first chose by operation count, found Horner has MORE multiplies for `x^7` (6 against 4) yet fewer cells, and switched the choice to compiled cell counts. Why fan-out and relays cost so much was not investigated.
- **Checks:** `tests/vm/test_arith_plan_horner_v1.py` (17 tests: operation formula equals what is emitted; recogniser expansion; 25 random polynomials with wrap-around against Python; linear cell count; VM agreement with the direct form; auto keeps the smaller; option validation; a polynomial inside a division; generated flex RTL and generated sub RTL both match the formula over 8 values). Mutation checks, all caught: coefficient off by one, identity rule changed, product truncated to 16 bits in the recogniser, auto always taking Horner. The 110 existing LaTeX tests still pass under the new default.

**Not done:** square and cube as their own plans (they compile to the same cells now, no gain found); dot product / matrix-vector (multiply-accumulate chain or add tree); fixed-range sums; run-time sums (needs the loop ring); the plan as a stored ICM block placed by name (this plan is a generator, not a stored file); cardinal (v4/v4c) cells. docs listed in `docs/build_manual.py`: `sub/README.md` updated.

## 1079. Fixed-range \sum and \prod, chain plans, dot products (Alan/Claude, 2026-10-12)

Next stage of the plan library after Horner (#1078). `\sum_{i=a}^{b} body` and `\prod_{i=a}^{b} body` with whole-number bounds (at most 64 terms) are parsed and written out as a chain; the library gains `sum_chain` and `product_chain` (base `acc' = acc + term` / `acc * term`, n-1 operations). The index may stand alone, be a subscript (`a_i` becomes the variable `a_k`) or an exponent (`x^i`). The body is the next multiplicative term (brackets for a sum of terms); the index is local (an `i` outside is an ordinary variable). A run-time range, an empty range, more than 64 terms, a multi-digit bound without braces, and a malformed range are refused with a reason. A polynomial produced by a sum (`\sum_{i=0}^{4} x^i`) is recognised and goes through the Horner choice of #1078 (44 cells). Dot product is `\sum_{i=1}^{n} a_i b_i`.

**Measured (compiled cells, routed_x):** chain of adds over plain variables: exactly 6 cells per term (n = 2..9: 8, 14, ..., 50). A balanced tree of adds is much worse (4 terms 29 against 20; 8 terms 101 against 44; 16 terms 288 against 92) -- I did not investigate why; the chain is the shape. Dot product, n = 2..9: 29, 53, 89, 137, 188, 260, 326, 413 cells, increments 24, 36, 48, 51, 72, 66, 87 -- NOT linear; at 8 terms 296 of 326 cells are `ram` relay cells (plus 15 priority, 8 mul, 7 adder). The order of the operations in the IR makes no difference (three orders tried, identical counts). The cost is the general placer routing 2n inputs. Even `a*b + c` is 15 cells (priority cells and relay delay lines around the mul). A pre-laid-out multiply-add stage joined N times (inputs, mul, add, one relay to carry the running total, about 5 cells per stage by my sketch -- NOT built or measured) would be linear; that is the "stored block with a join rule" route and it needs the tile-placement machinery (priority cell protocol, relay timing) driven by hand.

**Checks:** `tests/vm/test_latex_sum_prod_v1.py` (14 tests): values against Python incl. nested sums and brackets; random values with wrap-around; 8 malformed-range refusals; index locality; chain plans emit exactly the IR the front end writes; sum chain exactly 6n-4 cells and the tree larger. Mutations caught: range off by one, subscript off by one, product treated as sum. The 110 existing LaTeX tests and the 17 Horner tests pass. VM check only for the new tests (no RTL run of a dot product).

**Not done:** matrices and matrix-vector (the front end has a single output; several outputs needs a design decision); the pre-laid-out MAC block; run-time sums (loop ring); RTL runs of sums; cardinal cells.

## 1080. The stored multiply-accumulate block: a pre-laid-out stage joined N times (Alan/Claude, 2026-10-12)

Alan asked for the stored-block route after #1079 showed the dot product growing faster than linearly. New module `nano/arith_blocks_v1.py`: `mac_chain` writes the cells and positions of a multiply-accumulate chain directly. One stage = A and B input cells, a priority cell, the multiplier, a priority cell, the adder, one wire cell; stage pitch 3 rows, 5 columns wide (a layout diagram is in the module docstring). Cells and masks are the ones the compiler itself writes for `a*b + c` (I read them off a compiled design first: a relay "ram" cell is a wire segment, and every two-operand cell has a priority cell in front). Stage 0 has no add (its product runs down three wire cells); the last add is `main.r`. Joining rule: stage k+1 starts three rows below stage k and takes the running total from the wire cell above its second priority cell.

**Measured:** n terms = exactly 7n - 1 cells (n = 2 to 10 checked; 16 terms 111, 32 terms 223) against 29 / 53 / 89 / 326 for 2 / 3 / 4 / 8 terms from the general placer. It worked on the first run (no layout debugging); results match the general placer's and Python's on random words including 0, 1 and all ones.
**Front end:** `compile_latex(blocks="auto")` (default; `--blocks off` on the command line): a formula that is exactly a dot product (a sum of two or more products of two variables, every variable used once) goes straight to the block and the general placer is NOT run for it (at 16 terms it had been taking minutes). The compile result's dag / icm / rewrites fields come from a two-term sibling compile and describe that, not this design; only records, injections and the result cell are used. Input cells are named as the compiler names them (`main.dynq_<mul>_a/_b`) so the IR-based tools still find them. Anything else (`a b + c d + e`, a repeated variable, a coefficient, a subtraction, one term) is unchanged.
**Checks:** `tests/vm/test_arith_block_mac_v1.py` (18 tests): cell count formula, unique squares and names; VM against Python and the general placer; which formulas use it; option validated; generated flex RTL and generated sub RTL (3 terms, 8 value sets incl. 0 and all ones) match. Mutations caught: adder wired from the wrong face, wire cell pointing east, B input injected at the wrong square, cell-count formula off by one. The 141 existing LaTeX / plan tests pass.

**Not done / limits:** the largest term count checked on the VM is 32 (the check takes about a minute); RTL only at 3 terms; throughput with items fed closely together on the block is not measured; the stage is fixed (a cardinal / carrier grid version is not built); block versions of the other plans (Horner stage as a block would likely also shrink 12 cells per stage; not tried).

## 1081. The ramp pipe: Alan's feed pipe for matrices, large form (Alan/Claude, 2026-10-12)

Alan's design for the matrix side: a feed pipe runs north to south; at the head of each calc point is a split (a ram cell with two outputs); a start value such as 1 goes in, the first split gives its calc point the 1 and the pipe carries on, an adder adds the step (1), the next split gets 2, and so on; because of the pipe delay the results come out in order. The alternative (small) form feeds the value through a loop that adds its iteration each time, the calc point loading each new number; "two possible ways, one large, one small, essentially the same job". Built the large form: `arith_blocks_v1.ramp_pipe(n, step)`: per stage a split, a tap (ram cell standing in for the calc point), the step constant, a priority cell and the adder (5 cells; the last stage 2), n taps = 5n - 3 cells, column 4 the pipe. Worked on the first run in the VM (1 to 10 step 1; step 5 from 100; wrap-around at 2^32; step 0; step 2^31) and as generated flex RTL, where each tap becomes its own output and five start values streamed through give start + k*step at tap k, in order. `tests/vm/test_arith_block_ramp_v1.py` (22 tests); mutations caught: last adder with no downstream, step constant off by one, cell-count formula. The generator accepts several exit cells as several outputs (flex); the LaTeX front end does not.

**Not done / limits:** the small (looped) form (needs the loop ring, prior art #638 / #649 / #518); the taps are plain ram cells, not yet connected to calc points (for a matrix: one multiply-accumulate chain per row); sub RTL not run; throughput with closely spaced start values not measured beyond the streamed test; no LaTeX syntax for a matrix or for several outputs yet. Open question for Alan: what the calc points compute for a matrix, and how the matrix is written on the LaTeX side.

## 1082. Matrices on the LaTeX side: a rule and a size, applied to a vector (Alan/Claude, 2026-10-12)

Alan agreed the notation: a rule for the entries plus a size, `A_{ij} = i j` for 4 by 4, and `A x` for the product; the writing guide and the reduction advisory go into the teaching-manual update at the end (see "For the teaching manual" below). Built:
- **`arith_blocks_v1.matvec`**: y = A x for a constant m-by-n matrix and a run-time vector. m multiply-accumulate chains side by side (3 columns each, the #1080 stage with a constant cell in place of the second input); each x_j runs along one feed line (row 3j) that splits into every chain (a ram cell with two outputs: down into the stage, on east) and CROSSES each chain's running total through a `cross` tile (N-to-S the total, W-to-E the feed line). Outputs are the last adders `main.y1 .. main.ym`. - **`compile_matrix_latex(rule, rows, cols, vector="x")`** and CLI `--matrix RxC [--vector x]`: parses `A_{ij} = body` (also `A_{i,j}`; any matrix name, any two different index letters), body is an ordinary formula in the two letters only (a third variable is refused with the reason: entries are worked out at build time and become constants); entries count from 1 and wrap modulo 2^32; sizes 1..16 rows, 2..16 columns; vector name one letter. A `MatrixResult` has `.run`, `.reference`, `.cells`, `.save`. Checked on the VM against plain Python (3 corner vectors and random ones) before it is returned.
- **Finding:** the #1081 ramp pipe is NOT needed for constant entries: a constant cell is one cell, a pipe tap is five. The pipe or a counter pays only for entries that depend on a run-time value (not supported yet). Alan's counter shortcut was checked against the code: the accumulator counts per arriving pulse (not per clock) with a fixed 0..255 step (reprogrammable through the programming channel on the cardinal cell, not data-driven); I read the VM and the cardinal RTL, not the flex / sub versions.

**Checks:** `tests/vm/test_latex_matrix_v1.py` (16 tests): cell-count formula and unique squares for 7 sizes; entries for sum, product, product of squares, subtraction with wrap, division, remainder, both subscript spellings; VM against Python on 4 rules; 8 refusals with reasons; CLI; 2x3 as generated flex RTL (two outputs, five vectors incl. 0 and all ones); 1x3 as generated sub RTL. **Not done / limits:** entries depending on run-time values (needs the ramp pipe or a counter feeding the entries, or the looped small form); matrix times matrix; an explicit matrix written out as `\begin{pmatrix}..\end{pmatrix}`; one column (n = 1); several-output sub RTL (the sub bench reads one output, so the 2-output case is checked on flex only); throughput of closely spaced vectors not measured; the manual and CLI help were updated only in sub/README.md.

## 1083. Matrices made flexible: run-time entries, chaining, matrix times matrix by streaming (Alan/Claude, 2026-10-12)

Alan: the matrix side will need run-time versions; a design may use the result of another design as its input; matrix times matrix means passing the products on to further matrices, which grows very large, so it may have to become a loop; the matrix function needs a high degree of flexibility from the start. Built the flexibility into `matvec` now:
- **Run-time entries:** `matvec(entry_names=...)` puts an input cell where the constant cell was (same cell count). LaTeX: `A_{ij}` with no rule; inputs are named `A_1_1`, `A_1_2`, ... (and counted in `args`).
- **Chaining (a design using another design's results):** `matvec_chain(layers, x)` stacks the blocks: the next block's splits listen on the face the previous block's result adders send to, and every second block is reflected about the diagonal (rows <-> columns, faces n<->w, s<->e) so the 3-square pitch of the results meets the 3-square pitch of the inputs. No wire cells between blocks; no overlaps (checked on every chain). 2 layers 89 cells, 3 layers 133, 4 layers tested. LaTeX: `compile_matrix_latex(..., then=[(rule, rows, cols), ...])`, CLI `--then "B_{ij} = i + j @ 3x2"`; dimension, name-clash and vector-name checks; mixes constant and run-time matrices.
- **Matrix times matrix:** by STREAMING -- the n columns of B go one after another through ONE block of A (the design is dataflow, so a longer stream only takes longer). Checked as generated flex RTL: four random columns through a 2x3 block, output streams = the columns of C. A spatial copy per column would be n blocks (16x16: about 32,000 cells against about 2,000 for the one block; computed from the cell-count formula, not built). This answers "very large indeed" for the constant-A case without a loop ring; it does not remove the cost when the matrix entries themselves are large run-time data fed per column.
- Result object generalised: `MatrixResult.layers`, `.args` (x first, then run-time entries), `.reference` applies layers in turn.

**Checks:** `tests/vm/test_latex_matrix_v1.py` now 24 tests: run-time matrix against Python; three chain shapes (const-const, const-runtime-const, four layers ending in one row) on the VM incl. no two cells on one square; refusals (dimension mismatch, repeated name, vector name as a matrix name, a middle result of one value, a rule using a third variable now points to the run-time form); matrix-times-matrix streaming on flex RTL; a two-layer chain on flex RTL (two outputs) and a chain ending in one row on sub RTL; CLI `--then` and run-time matrix. Mutations caught: next block placed one column off, reflection not swapping faces, run-time entry injected one square off, reference reversed. All earlier matrix, LaTeX, plan and block tests pass.

**Not done / limits:** the looped small form (needs the loop ring: one MAC reused over time; for matrices much larger than 16 by 16 or when the block itself will not fit); streaming of consecutive items was checked on flex RTL only (VM injects one item; the sub bench reads one output); run-time-dependent rule entries (a rule using a third variable) are still refused; matrix written out with numbers; a layer of one row feeding another is refused because a block needs two columns; throughput limits for closely spaced items not measured.
