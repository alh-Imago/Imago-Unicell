Modes from `merge_cell_v4sa.v`: A only, B only (the other input is never accepted), arbitrate (one at a time; the loser gets priority next time, the first tie goes to A), join (waits for both, outputs A OR B bit by bit, takes both). ## #1044 -- TEACHING MANUAL PART 6: REMEMBERING, LATCH AND SEQUENCER (Alan's direction)

## 1068. Division as a runtime loop in the VM: repeated subtraction works and is tiny, but it is slow and narrow -- the 32-step unrolled design stays the general answer (Alan/Claude, 2026-10-12)

Alan asked for the loop version of division ("or a multiply loop as a side trick"). Built and measured in the VM only; no RTL, no hardware.

**Built:** #518's shape in the VM -- three cells: SUB (accumulator, step = divisor), BR (branch cell, held reference A-B, "continue" routed to SUB and to Q), Q (accumulator, step 1, the quotient). 3 cells instead of ~23,000. Quotient = Q, remainder = A - SUB. Test: `tests/vm/test_division_loop_v1.py` (5 tests pass).

**Harness steps, stated plainly:** (1) A-B is worked out outside and set as BR's held reference on the cell directly (as #518 did with a host-precomputed constant); a formula would need a subtract cell and a sequenced first arrival to do this inside the design -- not built. (2) SUB's freeze input is driven each tick: unfrozen for the first tick, then frozen unless BR is holding a continue.

**Measured:** 157 cases (150 random with A up to 3000, B 1..255, plus edge cases) all equal Python's quotient and remainder. Without the freeze gate the quotient is exactly one too many and the remainder is short by B -- the same race #518 found in RTL (a stale value is offered twice), now reproduced in the VM. The startup window matters: unfrozen for one tick works; two ticks fails every case with quotient 1 (found by testing, not predicted). Speed: 2 VM ticks per unit of quotient, so time grows with the answer (quotient 53 took 106 ticks).

**Limits found (all real):** the accumulator step is 8 bits (`& 0xFF`) and its threshold 16 bits, so the divisor must be 1..255 here; the number of passes equals the quotient, which for a 32-bit dividend can be 2^32 passes; divide by zero NEVER halts (checked: the counter keeps climbing), so a loop version needs an explicit guard to match the front end's "x/0 = all ones". Bit-serial long division (32 passes always) needs three circulating words plus a counter (merge + branch cells per variable); that dataflow loop is still not built.

**The multiply question:** not wrong, but it does not replace the loop. A multiply-based divide needs a reciprocal (Newton iteration, which is itself a loop) and the high half of a product, then a correction step; it is the right tool for a CONSTANT divisor (reciprocal worked out at compile time) and is NOT built or measured here. ## 1077. K (quotient bits per clock) becomes a design-time setting of the divider, at one fixed place in the record (Alan/Claude, 2026-10-12)

## 1078. The arithmetic plan library, first plan: Horner polynomial (Alan/Claude, 2026-10-12)

## 1079. Fixed-range \sum and \prod, chain plans, dot products (Alan/Claude, 2026-10-12)

Next stage of the plan library after Horner (#1078). `\sum_{i=a}^{b} body` and `\prod_{i=a}^{b} body` with whole-number bounds (at most 64 terms) are parsed and written out as a chain; the library gains `sum_chain` and `product_chain` (base `acc' = acc + term` / `acc * term`, n-1 operations). The index may stand alone, be a subscript (`a_i` becomes the variable `a_k`) or an exponent (`x^i`). The body is the next multiplicative term (brackets for a sum of terms); the index is local (an `i` outside is an ordinary variable). A run-time range, an empty range, more than 64 terms, a multi-digit bound without braces, and a malformed range are refused with a reason. A polynomial produced by a sum (`\sum_{i=0}^{4} x^i`) is recognised and goes through the Horner choice of #1078 (44 cells). Dot product is `\sum_{i=1}^{n} a_i b_i`.

**Measured (compiled cells, routed_x):** chain of adds over plain variables: exactly 6 cells per term (n = 2..9: 8, 14, ..., 50). A balanced tree of adds is much worse (4 terms 29 against 20; 8 terms 101 against 44; 16 terms 288 against 92) -- I did not investigate why; the chain is the shape. Dot product, n = 2..9: 29, 53, 89, 137, 188, 260, 326, 413 cells, increments 24, 36, 48, 51, 72, 66, 87 -- NOT linear; at 8 terms 296 of 326 cells are `ram` relay cells (plus 15 priority, 8 mul, 7 adder). The order of the operations in the IR makes no difference (three orders tried, identical counts). The cost is the general placer routing 2n inputs. Even `a*b + c` is 15 cells (priority cells and relay delay lines around the mul). A pre-laid-out multiply-add stage joined N times (inputs, mul, add, one relay to carry the running total, about 5 cells per stage by my sketch -- NOT built or measured) would be linear; that is the "stored block with a join rule" route and it needs the tile-placement machinery (priority cell protocol, relay timing) driven by hand.

**Checks:** `tests/vm/test_latex_sum_prod_v1.py` (14 tests): values against Python incl. nested sums and brackets; random values with wrap-around; 8 malformed-range refusals; index locality; chain plans emit exactly the IR the front end writes; sum chain exactly 6n-4 cells and the tree larger. Mutations caught: range off by one, subscript off by one, product treated as sum. The 110 existing LaTeX tests and the 17 Horner tests pass. VM check only for the new tests (no RTL run of a dot product).

**Not done:** matrices and matrix-vector (the front end has a single output; several outputs needs a design decision); the pre-laid-out MAC block; run-time sums (loop ring); RTL runs of sums; cardinal cells.

## 1080. The stored multiply-accumulate block: a pre-laid-out stage joined N times (Alan/Claude, 2026-10-12)

## 1081. The ramp pipe: Alan's feed pipe for matrices, large form (Alan/Claude, 2026-10-12)

The crossing pair costs 2 clocks over the sub block's own latency. Negative control: without the one-in-flight gate (a word admitted while one is held and the sink stalls) words are lost, so the gate is real.

*Honest scope.* One word in flight, so a long sub block runs at 1 word per (its latency + 3): the bridge gives up the sub family's one-result-per-clock pipelining (a credit/queue version could restore it; not built). Tested against flex cells only; the nano (stepped) side is not done. Synthesis cost and clock speed of the bridge not measured (two registers and a flag per side; it adds no cells). No compare/check cell is wired in yet: the held word is available at the flex side for any flex cell (comparator, branch) to use.

## #1116 (12 Oct 2026) -- RING CONTROL ON THE STANDARD LINE: a counter, a branch and a join-gate IN the ring (VM and VIXeN carrier RTL)

*Alan (22:19, 22:44).* The standard line (carrier and standalone nano) needs "a simple counter ... along with a compare or branching system ... as long as it's part of the ring itself", because the next cell only takes its word if it acks the previous one. Then, on seeing the first layout: "the branch only sends data on values, it does not redirect the entire system".

*His point is right and the design follows from it.* A branch decides per datum and stays in no mode: each value it compares is emitted and routed once. So the branch cannot steer the ring. What stops the ring is a JOIN adder (the gate, on the ring's return path): a word passes only together with a token, and a word with no token simply waits (ack discipline), which holds the whole ring. The branch only hands out the per-lap tokens.

*Build* (`nano/looped_cordic_v1.py`, `build_doc(..., ring_laps=N)`; every cell an existing standard cell): the fork cell fb4 sends each word onward and to an accumulator (+1 per word); the count goes by two relays to the branch; a preloaded ram offers the reference once and so becomes the branch's held reference; LOW (count < ref) emits token 0 to a token relay and on to the gate; EQUAL emits 1 to the `ring_stopped` ram; HIGH emits nothing. `ring_release` is a host word into the token relay (a token beside the branch's own): the held word goes one lap, the count is then above the reference, so it stops again.

*Findings on the way (all measured).* (1) The accumulator offers its running total again and again, and starts with two zero offers; a first layout let those become the branch's reference and the ring stopped at once (0 laps). (2) A flowing ram ORs simultaneous arrivals and acks both, so a host release sharing a ram with the count was swallowed (the count 6 OR 0 = 6); the release has its own token relay. (3) The stop comes RING_OFFSET = 4 words after the reference value (two start-up zeros + two relay hops of the count path), so the reference is N-4 and N must be at least 5 (`MIN_RING_LAPS`); a smaller N is refused with that reason.

*Measured.* VM (SuperGrid, join adders): N = 5, 6, 9 -> exactly N entry arrivals, values equal the model, quiet afterwards, `ring_stopped` set; every release gives exactly one more lap, repeatedly, values still on the model. VIXeN carrier RTL (iverilog, `tools/carrier_grid_v3.py`, a clone of v2 that adds the accumulator to the cores the grid generator can configure): N = 5, 6, 9 stop at exactly N with model values; two releases (a re-commit of the release ram with word 0) give laps 7 and 8 (8255, -2032) and nothing else.

*Honest scope.* Proven in the VM and on the carrier grid (VIXeN). NOT done: the standalone nano (the same cells exist as nano_gate cores, but no standalone shell was built or run); no Fmax or area figure (no nextpnr here); N >= 5 only; the count offset is calibrated, not designed away (a pulse-mode accumulator with a threshold might give a cleaner counter; not tried); the release is a host write of any word below the reference value. Only the looped CORDIC carries the control; the ICM/assembler flags for the std line are not added yet.

*Tests.* tests/vm/test_std_ring_v1.py: 11 pass (VM 6, carrier RTL 4 + refusal); looped CORDIC, carrier grid and VIXeN system suites still pass (25 together).

### #1130 (13 Oct) -- A SERIAL PROBE: MEASURE THE LINE TO THE PC BY ITSELF (CRC-32 FRAMES)

*Alan, 08:48.* The serial line is the only contact with the card and is vital for confirming a save/load cycle on something more complex than the CORDIC, captured mid-flight; it must not be able to corrupt the data unnoticed.

*What is wrong with the present readout.* The report line carries a rotate-and-XOR checksum (`sig=`), which is weak, and a silent line (0 bytes) cannot be told from a design failure except by the LEDs (#1129). The transmitter itself (`board_uart_tx`, 8N1, idle high, 234 clocks per bit at 27 MHz) reads correctly; I found no fault in it by inspection, and no explanation yet for the silent runs.

*What was built.* `tools/board_serial_probe_v1.py` -> `fpga/board_serial_probe/`: two bitstreams with no cells (788 / 809 LUT4, timing met) that send for ever the framed line `UCP seq=XXXX d=W0..W7 crc=CCCCCCCC` (16-bit sequence, eight mixed 32-bit words, standard CRC-32 of the text). `serial_probe_fast` sends frames back to back (hardest for the PC side), `serial_probe_gap` leaves ~10 ms. `run_probe.sh` loads each ONCE (no reload on silence: a reload hides a dropout) and `check_probe.py` reports frames valid / corrupt, missed frames (sequence gaps) and, for corrupt frames, how many bytes differ from the frame that should have arrived; verdict CLEAN / DEGRADED / SILENT.

*Measured here.* In simulation the first two frames the Verilog sends are byte-for-byte the frames the host computes (two independent implementations of the mix and the CRC). `tests/vm/test_serial_probe_v1.py` (4 tests): a clean capture is CLEAN; one flipped bit = one corrupt frame with one differing byte; two lost frames are counted as 2 missed; a dropped byte corrupts a frame. Not yet run on the card.

*What it will and will not tell us.* It separates the serial path from any design: if the probe is CLEAN on a run where a design was silent, the line is fine and the design's own printing is suspect; if the probe itself drops or corrupts bytes, the line is the cause and its rate and kind (loss versus bit errors) are measured. For a save/load check the next step, once the line's quality is known, is to send the captured state in the same kind of CRC-framed form with a repeat, so corruption is detected and the frame is simply taken again.

### #1145 (13 Oct) -- IN-FLIGHT CAPTURE AND RESTORE ON THE FLEX LOOPED CORDIC, STAGE 1: A SCAN CHAIN, PROVEN IN SIMULATION (not yet on the card, no serial framing yet)

*Why.* Freezing the looped CORDIC mid-flight (#1096-#1101) holds the state but cannot read or write it: the cells have no path to their dynamic registers, so a save only worked at cuts where everything sat in the one closing register. To carry a part-way computation to a fresh card the state inside the cells has to be reachable.

*What was built (all new files; no proven file edited).* `tools/flex_scan_net_v1.py` clones each flex cell (ram, adder, merge, branch; `sub/verilog/<kind>_cell_v4sa.v`) into `<kind>_cell_v4sa_scan.v` with `scan_en/scan_in/scan_out`: the dynamic registers form one shift register, and a `scan_en` branch sits between `cfg_valid` and the normal branch (priority rst > cfg_valid > scan_en > normal). It joins the clones into one chain in `icm_open_flex_fz_scan.v` and writes `SCAN_MAP.json` (cell order, register widths, offsets). On the looped CORDIC: 48 cells in the chain, **1905 bits** (ram 31 cells, adder 9, branch 4, merge 4); the 13 constant cells are left out. `sub/verilog/looped_cordic_stop_wrapper_v3.v` (v2 untouched) adds `scan_hold` (freeze the grid and ignore it), `scan_en` (shift, implies hold) and `load_has` (load the closing register as empty or full). Recirculating (scan_in = scan_out for 1905 clocks) reads the state without changing it; restoring = reset, the same configuration pulse, load the closing word, shift the stream in.

*Test* (`tools/flex_scan_check_v1.py`, `tests/vm/test_flex_scan_v1.py`, iverilog). Card A runs from the start value and stops itself by freeze after k1 results; its chain is read out by recirculating; fresh card B gets the configuration, the closing word and the stream; both are released together. They must deliver the same next 6 results, with the same spacing in clocks, equal to the Python model (`nano/looped_cordic_v1.py`). Swept: freeze lag 0-31 x feed delay 0-4 x k1 3,4,5 = **480 trials: all 480 identical to the model, 99 distinct captured states** (30 with the word in the closing register, 450 with it inside the grid). Separately a chain-integrity test (six patterns incl. random, all ones, all zeros) shifts a known stream into a frozen fresh grid and reads it back: all six equal. Deliberate breaks, each caught: zeros shifted in instead of the stream; closing word not restored; one stream bit flipped per trial (one trial in 20 changed the results, as expected since most bits are not live); one chain link cut. pytest: 5 passed.

*Scope, stated plainly.* Simulation only. Seven register kinds never held a non-zero value in any captured state (adder carry_buffer and pending_c, branch has_loaded_1/2 and held1/held2, ram have): this workload does not use them, so their *function* after restore is not exercised here; their *place in the chain* is, by the pattern test. Constant cells are assumed stateless in the sense that matters; the 480 results agree with that, but it is an observation, not a proof for other designs. The scan clones were checked against the original cells only through these workloads, not by formal equivalence. Timing: B is released within a cycle of A, and the spacing between results matches. The step counter and stop latch are not in the chain; the host re-arms the counter with the steps remaining. Cost not yet measured (synthesis comes with the card kit).

### #1146 (13 Oct) -- IN-FLIGHT CAPTURE AND RESTORE, STAGE 2: THE CRC-CHECKED SERIAL PROTOCOL, ON THE REAL DESIGN IN SIMULATION WITH DAMAGE ON THE WIRE (not yet on the card)

*Built* (new files only). `tools/board_scan_v1.py` generates the card top: the scan-chain grid (#1145), wrapper v3, a 256-byte image memory, a staging buffer, CRC-32 (the probe's crc8 function), UART. Image = 240 bytes of scan stream (1905 bits + 15 zero pad bits) + closing word (4) + flag (1) + step count (2) + zeros, carried as 8 chunks of 32 bytes. Card to host: one text line per chunk, `UCS lcordic ses=SSSS seq=N of=8 d=<64 hex> crc=CCCCCCCC`, CRC-32 over session, seq, 8 and the data. Host to card: binary `W` + session, seq, 8, 32 data bytes, CRC (big-endian); the card stages the chunk, checks the CRC, and only a good chunk reaches the image memory, then answers `K seq mask` (`E` for a bad CRC, `T` after a timeout when a byte went missing). Commands: X C L G Q as before, plus S (capture, session +1), D n (dump chunk), W, M (mask), Z, A (apply: needs all 8 chunks, holds the grid, loads the closing word, shifts the stream in, step offset = image steps). `tools/scan_host_v1.py` is the PC side: it accepts a dumped chunk only if design name, session, sequence and CRC are all right; takes every capture twice and requires identical images; reads a restore back (captures the restored card and compares with what it sent); retries a bounded number of times, then raises ScanError. It talks to a link with send/read/drain, so the same code will run on the serial port (a Python reader opened before the load, #1141) and on the simulated card (`SimCard`: the real Verilog in iverilog driven byte by byte through a live pipe). `FaultLink` damages traffic on purpose.

*Result* (`tools/scan_flow_check_v1.py`, `tests/vm/test_scan_serial_v1.py`: 4 passed). Card A runs the looped CORDIC and freezes itself part-way (word inside the grid); the host captures it twice; a separate fresh simulation, card B, is reset, configured, loaded with the image through checked chunks, applied, read back, and released together with A; at the next stop the two cards' complete images are identical, the flags and word agree, and the word equals the Python model. Clean runs at three different cuts (lag 0 / dly 0 / k1 3; lag 7 / dly 1 / k1 4; lag 20 / dly 0 / k1 5) passed. With damage on the wire, each ended identical to the undamaged run after retries: a bit flipped in a dumped data line, in a dumped CRC, a byte lost from a dumped line, a byte repeated; a bit flipped in a written chunk's data, in its CRC, in its sequence byte, a byte lost (the card timed out and said `T`), a byte repeated, the card's `K` reply damaged; and one run with three different damages. Retry counts matched the injections (for example one write retry for one damaged write). Damage on every attempt does not get through: persistent write damage stops with "write chunk 0: no 'K' after 5 tries (last reply E)", persistent dump damage with "no valid line ... after 5 tries". A card deliberately built without the chunk CRC check accepted a flipped chunk, and the read-back raised "READ-BACK DIFFERS after restore: 1 bytes (first at 111)", so the second line of defence works on its own.

*Scope, stated plainly.* Simulation only: 8 clocks per bit, card timeout 3000 clocks (the card will use 2^21), not the real 115200 baud, no pin timing. The real serial path has not been used for this protocol yet; the reply-gap lesson (#1099) is carried over (first reply byte waits 12 bit times). Damage was injected at chosen places, not at random, and each case once. Three cuts of one workload (the looped CORDIC), with the seven never-used register kinds of #1145 still never exercised. Chunk mask and image survive a soft reset by design; a stale mask from an earlier restore is cleared by the host with `Z` at the start of each restore. LUT/FF cost of the scan chain and the controller is not measured yet. Dumps and writes are about 113 and 41 bytes per chunk, so a full image is about 2 x 8 x 113 bytes per verified capture; at 115200 baud that is roughly 3 s per verified capture (estimate from byte counts, not measured).

### #1159 (13 Oct) -- VM LEG: A SAVED MID-FLIGHT STATE MOVES BETWEEN THE CARD AND THE VM (FlexGrid), BOTH WAYS (cross-reference #1151-#1158)

`tools/vm_state_bridge_v1.py` (new; with `to-vm` / `from-vm` commands and tests/vm/test_vm_state_bridge_v1.py). Card/simulator state file -> VM: every live register is written into the VM cell of the same name (names are `c_` + cell id with `.` -> `_`); VM -> state file: refused, naming the cell, if the VM holds something the card's registers cannot express exactly. The loop (each result fed back into the inputs) is done by a small driver in the bridge, as the card's wrapper does.
**Four differences between the VM and the card that a real mid-flight state exposed (all handled in the bridge, none by changing the VM or the card):**
1. *Divider.* The VM computes its answer up front and counts `div_busy` down; the card divides one bit per step. A card state part-way through a division is finished with the divider's own step rule (replica of `div_cell_v4sa.v`), and the VM's busy counter is set to the steps remaining.
2. *Join cells (adder / mul / div).* The card fires when BOTH operand cells are presenting; the VM takes operands one at a time. A state with both waiting is fired in the bridge (that is what the card's next clock does).
3. *Priority cells.* The flex assembler eliminates them (`eliminated_priority_cells`); the VM keeps them and, in strict mode with the constant and the product both waiting, served the constant twice (first restore gave 24690 instead of 49981: caught only because the saved state has both words waiting at once, which a normal one-shot VM run never has). The bridge puts the priority cell in front of each join into sequence mode, operand A's face then B's (roles read from ASSEMBLY.json `adder_roles`, now stored in design.json as `joins`).
4. *Constants.* The card builds a constant as a fixed ram that offers its word forever; the compiled record is a flowing ram preloaded once, so the VM ran dry after 3 rounds of the loop (hang in round 4). The bridge marks those cells fixed (`constants` in design.json).
*Measured:* the REAL card state of #1154 (cut 3:3:0, the multiplier holding 65327^2) in the VM: 8 results [49981, 59060, 19989, 25408, 396, 38119, 11289, 15521] = model, and 25408 = the card's own answer at step 7. 14 simulated-card cuts (steps 3..6, lags 0..50; one with a join about to fire; nine with the divider 9..32 steps from done): all continue in the VM to the model's next 5 results. VM -> state file -> simulated card: the VM after 3 results + 10 ticks (closing word 65327, multiplier mid-calculation) restored into the simulator, ran to step 7: 25408 = model PASS. 3 new tests pass (15 s).
*Refused honestly (VM -> card):* one operand arrived in a join (the card has no register for half a join), a VM division still counting (the card would need half-way registers the VM does not have), a word held in a VM priority cell, carry / wide / remainder words (not mapped yet). Also not mapped card -> VM: carry (`pending_c`), high word (`pending_hi`), remainder word (`pending_r`) -- the code raises rather than guess.
*Scope.* One design (the LaTeX line). Ticks are not clocks: the VM continues to the right WORDS, not to the same cycle-by-cycle state; the cut-by-cut equality of full register state that the card tests check is not claimed here. Only the first step after the cut is a restored state; later steps run on the VM's own loop. Not run against Alan's VIXeN engine. The VM-made state file `images/vm_after_3_results_10_ticks.state.json` is restored on the real card by Alan next (not yet run on the card).
