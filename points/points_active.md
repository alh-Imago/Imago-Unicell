## #1243 (19 Oct 2026) -- FREEZE-AND-READ KIT FOR THE KINTEX (`fpga/kintex7_tests/k7_freeze`): the card freezes the Tang tree ITSELF at a programmed clock count, and the PC reads every cell's visible state over JTAG. Simulated and synthesised; not yet built through nextpnr, not run on the card

*Alan's idea (19 Oct), first small version.* `tools/kintex_freeze_pack_v1.py` builds the kit. The Tang `std_tree4` grid (13 cells) is cloned as `std_tree4_frz` (generated from the Tang grid file; the cell files are unchanged copies): every cell's `freeze_in` is joined to one freeze line (the Tang grid ties them to 0) and each cell's visible state is brought out. A small driver replays the Tang top's own 24-step load schedule (copied from `board_top_std_tree4.sv`) and, on a host command, restarts the run and **freezes the grid itself at clock count T** (Alan's rule of #1098: the card stops itself; the host link is slow). One BSCANE2 USER1 register of 1024 bits carries the snapshot out and the command in, in the same scan (command applied at Update-DR only if its valid bit is set, so a scan of zeros is a pure read). Snapshot: header (magic 'FRZ1', run count, flags, result signature, last result, T in force) and, for each of the 13 cells, the word on its output (out_buffer for an adder), its four fire (pending-acknowledge) bits, status_data_valid and status_a_arrived. Host side: OpenOCD scripts `freeze_read.sh`, `freeze_at.sh T`, `freeze_release.sh`, `freeze_sweep.sh START STOP STEP` (-> `sweep.csv`, one row per cell per count) and `decode_freeze.py`.
*Checked in simulation (iverilog; BSCANE2 modelled in the testbench; two copies of the design, A commanded over the modelled scan, B free-running with its cell state recorded at every count):* the automatic first run delivers 6 results with signature 7FEF5298 and last word 7FFFFEAA, the same as the Tang line (#1237); freezing at 24 counts (including counts at and just after load events, 45-57 and 345-357, and near the result times, 1500, 1560, 1561) gives a snapshot equal to B's state at **the same count T** (one offset, d=0, holds at every T; at idle counts every offset matches, so only the busy counts discriminate); two reads of a frozen grid are identical; releasing the freeze finishes the run with the same 6 results and the same signature as the free copy; a plain rerun (a reset without freeze) gives the same signature. *Synthesis:* yosys `synth_xilinx -flatten -abc9 -arch xc7` accepts the design with no error or warning (LUT6 770, LUT5 193, LUT4 120, CARRY4 53, FDRE 1658, one BSCANE2); that is a synthesis check only (no placement, no timing).
*Found while building (a sim-only trap, fixed):* a plain-Verilog `always @*` block with a `case` does not evaluate at time zero in iverilog, so the load schedule stayed unknown and no load fired; the schedule is now a function (also fine for yosys).
*NOT checked:* nextpnr-xilinx place and route with this size of register (1024 flops on the JTAG clock); the real Update-DR behaviour of the BSCANE2 UPDATE pin (I edge-detect it on TCK, the common practice, but have not seen it on this chip); the reset and restart of the grid on the card (in simulation a rerun gives the same results; the RAM cells' stored words across a reset are covered only by that same-signature result); OpenOCD's actual `drscan` output for 32 fields (the decoder expects 32 words of 8 hex digits after "SNAP <T>").
*What it does NOT show.* Only the cells' visible state. The waiting operand (a_reg), the configuration and masks, and the RAM cells' stored words are inside the cells and are not brought out; that needs a debug port on a cloned cell (a v4f; the cell files are not touched in this kit). The Arria 10 and Tang boards are not involved.
*Next, in order (Alan):* copy `k7_freeze` into demo-projects, `make`, `make program JTAG_LINK="-c ft232"`, check the LEDs (yellow heartbeat, green = first run done, red off), then `freeze_read.sh`, then `freeze_at.sh 346`, then `freeze_release.sh`, then the sweep.

### #1268 (19 Oct 2026) -- CORDIC multi-word streams: why the VM delivers only the first word (finding, not a fix)

*Question (Alan, 19 Oct: "look at the VM ... may need to hold the initial values as it passes").* Why does the VM deliver only the first word of a stream through `cordic_z_convergence` while the card delivers all of them (#1267)?

*Measured (VM, this session).* (1) Both `SuperGrid` and `FlexGrid`, after a 6-tick settle, give 2736 for the first word and nothing for later ones (80 ticks each, words 10, 1, 2, 50000 fed one after another on one grid). (2) Trace of stage 0 on the VM: the zero source (`s0.zero_source`, a ram with preload 0, `fixed_mode` 0 in the ICM) is valid at tick 0 and not valid after the settle: it sent its 0 ONCE to the branch as the reference and is then empty. Each stage's constants sit in the adders' A operand. The second word reaches `s0.merge` (register = 1, 40 ticks later) but goes no further: the branch has no fresh reference to compare with. So the answer to "does it need to hold the initial values as it passes" is yes, for the zero references: the VM spends them on the first word. (3) The hardware does not: the generated Verilog (`icm_cordic_z_convergence_flex.sv`) builds every preloaded, unfed ram (constants and the four zero sources, 12 cells) as `ram_cell_v4sa` with `.cfg_fixed_mode(1'b1)`, commented `// CONSTANT`: a fixed-mode ram offers its value continuously and is never drained (generator rule, `flexsub_icm_flex_v1.py` header: "a ram with preload_value or fixed_mode is a FIXED-MODE ram"). So the generator and the VM read the same ICM cell (preload, `fixed_mode` 0) differently: the generator as a constant that is always offered, the VM as a one-shot. This is the likely reason for the word-count difference; it is consistent with every number measured, but the multi-word VM answer was not made to match the card.

*Tried and not working.* Marking those 12 rams `fixed_mode` 1 in the VM's copy of the records (so the VM treats them as continuous constants) makes the VM flood: the exit shows 7125, 6911, 5404 and 4294964570 over and over (hundreds of words, never the CORDIC answers), because the VM's continuous constant re-fires the adders every tick, where the hardware's handshake lets an adder take the held constant as one operand and wait for z. So a correct fix is a real FlexGrid change (a held constant that is read as an operand, not re-sent as a word), not a flag. NOT done: no VM file was changed (FlexGrid and SuperGrid are proven; a change would be a new version, `flex_grid_v2`, with its own tests and a full run of the VM suites).

*Standing result.* Single words: VM = card = independent CORDIC (#1267). Streams: card gives the correct single-input answer for every word; VM gives only the first. Which model of a preloaded `fixed_mode`-0 ram is the intended one for the VM is a design decision for Alan.
