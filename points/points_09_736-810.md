2. A single relay cell can't sequence two separate values -- `ram`'s

4. A `fixed_mode` ram cell continuously re-offering the same constant

   re-offering every tick can get captured twice (as both real
   operands) before the dynamic operand ever arrives. Real fix:
   flowing-mode (`fixed_mode=0`) `ram` with a real `preload_value`
   instead -- offers exactly once, matching what a true constant
   source actually needs.
5. `VixCarrierGrid` has a real, genuine gap: its own `__init__`

   `super().__init__()` at all, so the real freeze/preload/unfreeze

   real `__init__` side by side. This design uses no VIX-specific
   core, so switching to the base `SuperGrid` was the correct, honest
   choice -- but the real gap in `VixCarrierGrid` itself is recorded
   as its own, separate, genuine finding, not silently routed around
   for good.

## 796. Alan's direction, verbatim in substance: operand ordering is essential only in certain cases, that must be noted on the compiler's scan pass (which selects the appropriate ingestion), and the ordering guarantee is needed to keep flow and output correct.

**1. ## 798. PORTS: `icmp` (all six predicates), `select`, `ashr` into the new library-driven path -- built by COMPOSING existing library ops, no new hardware. Also: a leaf-placement fix in the dispatcher, a precisely-bounded inherited overflow limit surfaced as `caveats`, and a documented placement limit that fails loudly. 54 tests in the ports file, 964 pass. (Alan/Claude)

Continues Alan's "port each function and test". The frontend pipeline was restructured from 1:1 rewrites to **check -> expand (1:N) -> rewrite (1:1) -> scan -> compile**, with a lineage map so a library op can always be traced to the source `%name` it came from and the scan report survives expansion. All 52 pre-existing frontend tests passed unchanged through the restructure. Argument bindings are now derived from the FINAL DAG (a dynamic `DagOperand` carries its argument name in `ref_name`), so they cannot go stale through any expansion.

**1. `icmp`.** Old shape was `diff -> comparator(threshold)`; new path expresses it as two library entries: `sub` (which inherits `#796`'s ordering guarantee) plus a new one-operand entry `cmp_ge` (the comparator; `LibraryEntry` gained `param_builder` and `needs_capture` -- the comparator's own output IS the 0/1 result, no capture cell). `sge`/`sgt`: A-B; `slt`/`sle`: B-A (the old table, `#611`); `eq` = `XOR(diff>=0, diff>=1)`; `ne` = `xor(eq, 1)` (a bitwise XNOR would flip all 32 bits, `#668`). Verified through the VM against a signed Python model: every predicate exact on the non-overflowing domain (64 pairs each incl. small negatives), through `select` and as a returned `i1`. **`eq`/`ne` are exact for EVERY pair including extremes** (diff==0 is sign-agnostic). **The four ordered predicates are wrong EXACTLY when their 32-bit difference overflows** -- measured, not assumed: 16 of 16 overflow pairs wrong, and every wrong pair is an overflow. This is the old frontend's own `#711` limit, inherited faithfully and now bounded exactly; pinned as a documented negative test (asserts both directions; flip if a sign-aware compare is ever built) and surfaced on every affected compile as `DagFrontendResult.caveats`, so it is never silent. Unsigned predicates and literal-vs-literal are refused. Cross-checked against the old frontend's own model for the four ordered predicates it accepts; it REFUSES eq/ne feeding a select (`#668`'s restriction), so the new path is more general there.

**2. `ashr`.** Old realization was a ~9x sign-magnitude composition (`#702`/`#703`) because the shift addon has no sign extension. New: `ashr(x,k) = lshr(x,k) | shl(0 - lshr(x,31), 32-k)` -- five ordinary library ops, no branch, no correction stage; `k=0` is a copy. **Verified exact for every k in 0..31 across 10 edge values (320 cases), 0 mismatches**; refused for variable or out-of-range amounts. Mutation-checked: a `30-k` fill and a missing negate are both caught; a `31-k` mutant SURVIVED and is an EQUIVALENT mutant (the extra bit it sets is one `lo` already sets from the sign), not a test gap -- confirmed by reasoning, then by the non-equivalent mutants failing.

**3. `select`.** `m = 0 - c` (0/1 -> 0/0xFFFFFFFF), `nm = m xor 0xFFFFFFFF`, `(t & m) | (f & nm)` -- and/or/xor/sub only. Drops every old restriction (final instruction only, condition adjacent). Works for literal arms, argument arms, two dynamic arms, `abs`, `max`, min/max clamps against a literal.

**4. THE PLACEMENT FINDING.** `select` first collided on most shapes (`IcmVixFormatError`, position collision). Root cause: `_grow_convergence` put every leaf (argument/literal) frontier at a far-away `leaf_counter*100` origin, so a leaf converging with a nearby computed value put the target at the midpoint and made the partner's route ~90 cells long, crossing other structure. **Fix kept:** when exactly ONE operand is a leaf and the other a known frontier, give the leaf a virtual position OFFSET 8 rows north of its partner (target lands 4 cells east of the partner, distinct faces, short routes). Both-leaf and both-ref convergence untouched; the full pre-existing suite passed unchanged; cell counts dropped substantially (e.g. 155 -> 78). **A first attempt (co-locating the leaf ON the partner) made things WORSE** -- a degenerate tie in `choose_two_way_orientation` put the leaf's source cell on the partner's route -- and was reverted at once after reading the orientation helper. **What remains unsolved:** two independently COMPUTED values that must merge (a `select` with two computed arms; a chain of `select`s). `manhattan_route` is explicitly "purely geometric" (its own docstring), and the dispatcher relies on growth locality. I tried an obstacle-avoiding BFS fallback: with a big enough search box the routes ARE found, but the dispatcher's straight-line `_pad` growth doesn't consult occupancy, so later pads run into the wandering routes -- making growth occupancy-aware is global placement, a separate architectural piece, not a mid-port patch. **BFS fallback fully reverted** (router file byte-identical to HEAD). Instead the frontend converts the collision into a `place`-stage diagnostic naming the cause -- LOUD and precise, never a raw exception, never a wrong answer -- and two documented negative tests pin it (flip them if occupancy-aware placement is built).

Cleared every `__pycache__`, reran: 964 passed. **Lesson for any future mutation testing here: clear `__pycache__` (or `PYTHONDONTWRITEBYTECODE=1`) between mutate and restore.** (The failure was diagnosed as a hypothesis first and confirmed by the cache clear, not assumed.)

**REAL, HONEST SCOPE.** Not built: occupancy-aware placement (the blocker for general `select`, chained selects, and any merge of two independent computed chains); the tightening pass (still never invoked -- layouts are loose, e.g. `abs` is 386 cells); a sign-aware ordered compare (would remove the `#711` limit at the cost of more cells); unsigned predicates; unnamed temporaries (`%0`); loops/control flow (the one old-frontend capability not yet ported); program-nexus segmentation; opcode escalation; the I/O work. ## 799. NUMBERED / UNNAMED SSA VALUES (`%0`, `%2`, ...) NOW SUPPORTED -- and a dispatcher bug the work exposed: fan-out from a nano-gate result wrote the wrong output field. 8 new tests, 971 pass. (Alan/Claude)

Continuing after `#798`. Real clang output is full of unnamed temporaries, and `#795` refused them; this was the largest self-contained practical limit on the frontend that needed no design decision.

**1. What llvmlite actually prints (probed, not assumed).** An unnamed argument prints `i32 %0`; an unnamed result prints `%2 = add ...`; a REFERENCE to an unnamed result prints as the whole defining instruction (no type prefix); literals print `i32 5`. The unnamed entry block consumes a number, so with one unnamed argument instruction results start at `%2` -- confirmed when my first probe input failed to parse (`'%1' defined with type 'label'`). This is why the extractor parses the PRINTED text rather than counting.

**2. Implementation.** `_source_operand(op, label)` recognises a literal only by matching the whole text against `i32 <int>` (never a last-token parse -- `#795`'s trap), an unnamed result by its `%N =` prefix, an unnamed argument by `<type> %N`. Unnamed values get the identifier `v<N>`, uniquified against every real name in the function (`%v0` real + `%0` unnamed -> `v0` and `v0_`), so the mapping is stable and collision-free. `ret` of a numbered value works. Verified through the VM: an unnamed argument and results; mixed named/numbered values and arguments; numbered values through `icmp`/`select`/`ashr` expansions; the collision case. `#795`'s test that REFUSED unnamed values was flipped, keeping its purpose: `sub 100, %0` where `%0 = x+5` must equal `100-(x+5)` for every x -- a misparse would give a constant 95, so it cannot pass by accident.

**3. A REAL DISPATCHER BUG, found by accident.** The numbered-values test fanned a `select`'s result (an `or` on a `nano_gate`) out to two consumers and the VM rejected the cell: `core='nano' core_config has unknown field(s) ['downstream_mask']`. `_claim_branch_start` wrote `downstream_mask` onto ANY producer, but a nano gate's output field is `routing_mask`. No earlier test had ever fanned out from a gate result (and/or/xor, or `select`'s merge). Fix: new `_out_field(core)` reads the field from the tile registry (unique per core: only `nano` differs; `branch` has none and REFUSES rather than guessing). Direct regression test covers and/or/xor gate results with two consumers; mutation-checked (with `__pycache__` cleared, per `#798`'s lesson): reverting to the hardcoded field fails it.

**HONEST SCOPE.** Numbered values only where llvmlite prints one of the three forms above; anything else is still a precise diagnostic. Still not built: loops (see below), occupancy-aware placement, exact ordered compare, unsigned predicates, program-nexus segmentation, escalation, I/O.

**LOOPS -- investigated, deliberately NOT ported, needs Alan's decision.** The old frontend's loop support (`_compile_single_counting_loop`) is a very narrow shape: entry block containing only a `br`, ONE loop block of exactly `phi`/`add`/`icmp`/conditional `br`, one exit block -- realized with hardware loop-ring tiles and a HOST-DRIVEN per-round protocol (its own docstring: "this fabric has no real command core wired in yet to do this from within itself"). The VIX library has no loop tiles. So this is not a straightforward port of an opcode: it is a choice between (a) porting the hardware loop tiles into the VIX library (bounded, self-timed, but needs the round protocol/command core), or (b) compile-time UNROLLING of loops with a known trip count into straight-line DAG (far more general -- arbitrary bodies -- and reuses everything built here, but cell count grows with trip count and the no-occupancy-placement limit will bite on bodies with merges). Alan's earlier point stands (`#370`): branching means every outcome needs its own physical cells, so branch-heavy control flow stays genuinely limited. Recommendation recorded for discussion, not decided.

## 800. PLACEMENT AS A VIRTUAL-SPACE STAGE, LOWERED TO CELLS ONLY AT THE END -- a layout + global router with free endpoint cardinality, tightening by spacing search, and folding with per-band orientation flips. The three shapes no growth placement could handle now compile and are correct. `nano/vix_virtual_layout_v1.py`; 16 new tests; whole verified frontend corpus re-run under it; 989 pass. (Alan/Claude)

**Alan's design (2026-09-21), in his words as recorded:** while a design is being created it sits in a virtual space, not yet lowered to a card or an ICM, and that is where to optimise; once cells are built their in/out faces are fixed, which naturally forces a linear, simple chain -- so the optimiser must be able to CHANGE THE CARDINALITY of each route's endpoints while virtual. The fold/tighten passes then have somewhere to work; a design bound for a bounded card must be folded to fit, which is why the cardinal outs must be re-chosen as it folds, then tightened. (Also: loops go by compile-time UNROLLING, option (b) -- decided, not yet built.)

**Why this succeeds where `#798`'s BFS fallback failed.** That router ran DURING growth, when faces were already fixed and the layout incomplete (later straight `_pad` growth ran into its routes). A router that runs AFTER placement, seeing every node and obstacle, choosing the face at both ends of every route, is sound.

**What was built (all plain Python objects until the last stage; no `HierCell` exists before lowering):** (1) graph -- `DagInstr`s to leaf / unary / binary nodes and edges; (2) layout -- depth = column, row = barycentre; (3) route -- sequential BFS over the whole occupancy map, MULTI-SOURCE / MULTI-TARGET so the router picks both faces (cardinality is a RESULT of routing); (4) tighten -- search for the smallest spacing that routes; (5) lower -- build cells with the chosen faces. Same return contract as `compile_dag()`, so a frontend swaps placers: `compile_llvm_via_dag(src, placer="growth"|"routed"|"auto")` (default `auto`: growth first, routed only if growth cannot place; `IMAGO_PLACER` overrides), plus `fold_width=` / `spacing=` (either forces the routed placer). `DagFrontendResult.placer` records which one ran.

**Every binary op goes through a priority cell** (PRIORITY when commutative, SEQUENCER when not), never a bare race between two routes -- the growth placer's real+constant "plain chain" leans on its own geometry for timing, and a router changes route lengths freely, so correctness must not depend on them. Costs one priority cell per binary op; layouts still came out smaller (diamond 42 -> 25 cells, proof case 14 = 14).

**THE DIAGNOSIS THAT MATTERED.** First attempts failed on `select` at EVERY spacing -- scale-invariant, so not congestion. Rendering the layout showed why: constant/argument leaves placed west-and-below their consumer made long L-shaped stubs that acted as vertical walls cutting the design into strips. Fix: operation nodes on a slot pitch of 3, leaves directly NORTH / SOUTH of their consumer in the same column (short vertical stubs into free faces), plus seeded layout jitter across attempts. After that: `select` with two computed arms, chained selects, and computed arms + computed condition all compile and verify.

**A mechanism I built, measured, and REMOVED.** A keep-out ring around nodes (routes may touch a node's neighbourhood only if it is one of their endpoints) was added on the theory that it protects pin access and keeps relays from running alongside a `nano_gate` (which accepts from any wired neighbour). Mutation-testing it showed NO test noticed its removal; measuring it over eight programs showed identical success and layouts equal or larger without it (arms+cond 166 vs 122 cells). The hazard reasoning was also wrong -- a relay only offers to its own next cell, so adjacency cannot feed a gate. Removed; the rationale is kept in the module docstring so it is not re-added on a hunch. The gate-feeding INVARIANT (only a route's last relay or the gate's own priority cell may point at a gate) is still tested on every layout.

**Verified.** The proof case, diamond, `select` shapes A/B/F/I, and the ENTIRE existing frontend corpus (~100 programs -- every shift amount, all six icmp predicates, ashr for every k, numbered values, chains, fan-outs) re-run under `IMAGO_PLACER=routed`: all pass; the only two that failed were the documented growth-limit negatives, which now compile. (Those two were split: growth's own limit stays PINNED by forcing `placer="growth"`; the default now compiles and verifies them -- flipped exactly as `#798` said.) Mutation-checked with bytecode writing disabled (`#798`'s lesson): dropping the fold orientation flip and swapping the sequencer's face order are both caught.

**FOLDING.** `fold_width=N` wraps the layered columns into stacked bands in a snake; a shape's own orientation flips on alternate bands (priority->op points east in even bands, WEST in odd ones) -- Alan's "cardinal outs adjusted as it folds". Tested: flat layouts have every pair pointing `e`, folded ones have both `e` and `w`; results stay correct; a 10-op chain folded to width 4 is narrower and taller. Measured limits, pinned as tests: chain and diamond fold to 2 columns per band, but the branching `select` needs >= 4 (2 and 3 refuse loudly).

**HONEST LIMITS / DEVIATIONS FROM THE DESCRIPTION.** (a) I fold at LAYOUT time (columns wrap into bands, then route), not as a post-pass over an already-built linear chain of cells -- equivalent in what it can express (faces are still re-chosen because none exist yet), but Alan's original wording was a pass over a built chain; a genuine post-pass over an existing HierCell array is not implemented. (b) Tightening is a spacing search, not incremental compaction of a built layout. (c) No crossover cell exists, so a non-planar program CANNOT be routed on a plane: it fails loudly with a `place` diagnostic (tested with a K3,3-minor program). (d) A value may have at most 3 consumers on the router (3 free output faces; growth allows 4). (e) Routing is a sequential heuristic (shortest first, then seeded reorderings, then more spacing), not an optimum -- the Composer scope already records that this class is NP-hard, which is why a human fallback exists. (f) No bounded-canvas FIT check yet: `fold_width` bounds the width you ask for, but nothing yet computes the width a given card needs (Tang Nano 20K: 20,736 cells) or tests that a design fits. (g) The whole-corpus oracle test re-runs the frontend tests in a subprocess (+12 s); full suite is now ~65 s.

**Real queue:** (1) loops by UNROLLING (decided); (2) a bounded-card fit check driving `fold_width`; (3) a true post-pass fold/tighten over a built cell array if wanted; (4) sign-aware ordered compare + unsigned predicates now that merges of many independent values are placeable; (5) program-nexus segmentation, escalation, I/O.

## 801. LOOPS BY COMPILE-TIME UNROLLING (Alan's option (b)), plus two measured improvements it forced: `auto` now keeps the SMALLER layout, and the simulation tick budget comes from measurement. 17 new tests, 1006 pass. (Alan/Claude)

**Decision (Alan, 2026-09-21):** loops go by unrolling -- "a more general approach is overall better." (The alternative, hardware loop-ring tiles with the host-driven round protocol, is NOT ported.)

**What was built (`llvm_dag_frontend_v1.py`, extractor stage; nothing downstream changed).** The supported shape is entry -> loop -> exit: entry (any plain instructions, then `br label %loop`), one NAMED self-looping block (phis, a body of any supported instructions, `br i1 %c, label %loop, label %exit` in either target order), and an exit block (post-loop instructions, optional LCSSA phis, `ret`). The loop block is INTERPRETED iteration by iteration with an environment mapping each source value to a literal, an alias, or the per-iteration name of a freshly emitted instruction (`accnext__it3`). Compile-time-known values -- the induction variable -- constant-fold away (`_fold`: add/sub/mul/and/or/xor, shifts, all ten `icmp` predicates, `select` with a literal condition); the exit condition MUST fold to a constant or the trip count is not known and the loop is refused. Everything data-dependent is emitted as ordinary instructions for the existing pipeline (expansion, scan, placement). Two-phase phi update so swap-style carried values (a,b = b,a+b) are right. `phi`/`br` are parsed from llvmlite's PRINTED text (its operand storage order for `br` is a known quirk); unnamed values inside loops are supported.

**Generalizes the old frontend's loop** (exactly four instructions: phi, add, icmp, br; one carried variable): arbitrary bodies, several carried values, code before and after the loop, exit phis, and -- a nice consequence -- the induction variable feeds a SHIFT AMOUNT as a literal, so `shl %y, %i` inside a loop compiles although a variable shift amount is otherwise refused. Verified through the VM against independent Python loops: accumulator (5x), x^6, a two-phi Fibonacci-style loop (8 iterations), a descending loop with a negative step, reversed branch targets, entry/exit code with a post-loop phi, an IV-driven shift sum, a data-dependent `select` running maximum inside the loop, numbered values, and a 32-iteration loop. **The induction variable leaves no cells at all:** 5 iterations of `acc += x` compile to exactly 5 adds. Mutation-checked (bytecode writing off): swapped phi selection, inverted exit polarity, and a wrong `add` fold are each caught.

**WHAT UNROLLING CANNOT DO -- stated plainly, because it is the trade Alan chose.** (1) Trip count must be known at compile time: a data-dependent exit is REFUSED (tested). (2) Cell count grows linearly with trip count: capped at 64 iterations / 600 instructions, beyond which it refuses and names the cap. (3) A loop whose result depends only on the induction variable (the old frontend's `return %inext`) is refused: the result would be a compile-time constant, not a computed cell -- so the old hardware-loop behaviour is NOT reproduced. (4) Only the entry/loop/exit shape: nested loops, loops with separate header/body/latch blocks, and multi-exit loops are refused with a precise reason. (5) Nothing here is a runtime loop; a real hardware loop remains separate, unbuilt work.

**Two measured improvements the loops forced.** (a) **`auto` placer now compiles with BOTH and keeps the smaller layout (ties -> growth).** Found because a 5-iteration shift loop simulated slowly: compile time was 0.0 s, simulation dominated, and growth spaces independent leaves 100 rows apart -- 739 cells under growth vs 140 routed (simulates 20x faster). My earlier assumption that growth is "compact for what it handles" was wrong once a program has many independent leaves; recorded, and tested. (b) **The default simulation tick budget** was `6 x cells`, chosen without measuring. Measured across 10 program/placer pairs: a result settles in at most ~1.05 x its cell count (most under 0.6x), because a value moves about one cell per tick along a critical path no longer than the design. ## 802. THE NANO GATE HAS NO INPUT GATING -- measured, and a lowering audit added; then i1 <-> i32 CONVERSIONS AND i1 LOGIC (`zext`, `sext`, `trunc`, `and`/`or`/`xor`/`select` on i1). 18 tests + 2 audit tests; 1024 pass. (Alan/Claude)

**Alan's question:** the nano has no cardinal awareness on its input -- it accepts from any neighbour -- so if that is not handled in the core or shell, could it be an issue? And if a neighbouring cell does not route to it, is it a problem at all?

**Answer, with evidence (not assumed).** (1) Semantics confirmed in the docs: nano has NO `upstream_mask`; it consumes an arrival from ANY physically wired neighbour; its one per-incoming-direction field, `cardinal_edge`, only CLASSIFIES an arrival as consume (0) or relay (1, pure pass-through to `out_buffer`) -- it does not gate, and a same-cycle disagreement latches `error_frozen`. (2) Measured on a routed `xor(x,12)` with a stray value-holding cell placed beside the gate: pointing AWAY -> result identical (12 / 9 / 104); pointing AT the gate -> silently wrong (255 / 250 / 155). So a neighbour that does not offer toward the gate is completely harmless; one that does is silently corrupting. (3) Audited every nano gate in both placers' layouts over a corpus: routed = 21 gates, every one has exactly ONE offering neighbour (its priority cell); growth = 16 gates, one or two (the designed chain + constant inputs). No stray feeder exists in current output. **So it is not a problem today -- the risk is a stale or dangling output face, most plausibly after a cell is re-oriented during a FOLD (Alan's own requirement).** Not adopted: tagging non-input faces relay in `cardinal_edge` -- a relay arrival also corrupts `out_buffer`, and the mismatch latch only fires on same-cycle disagreement, so it is not a reliable guard.

**Guard built:** `vix_virtual_layout_v1.audit_gate_feeders()` requires EXACTLY ONE offering neighbour per gate and that it is a `pri_` cell; called at the end of routed lowering, so a bad reorientation fails LOUDLY (`RouteFailure`) instead of corrupting. Two tests: the stray-neighbour experiment kept as a regression documenting the semantics (away = untouched, at = wrong), and an audit test (clean on every routed corpus layout; catches a constructed stray; passes a harmless one). The growth placer is NOT audited (its plain-chain gates legitimately have two feeders).

**i1 slice (the target Alan chose: 'start there').** Scope decision: i1 <-> i32 ONLY -- an i1 is a canonical 0/1 in a 32-bit cell, so everything maps onto existing ops: `zext i1->i32` = a new one-cell internal `copy` library entry (a `ram_flowing` pass-through, like `cmp_ge` not an LLVM opcode); `sext i1->i32` = `0 - c` (the mask `select` already uses); `trunc i32->i1` = `and x, 1`. i1 `and`/`or`/`xor` use the same nano gates; `xor i1 %c, true` is NOT; `select` accepts i1 arms; `i1 true/false` literals are read. Verified through the VM: zext of a comparison, counting how many conditions hold (sum of zexts), sext masks, trunc -> select, a range check via i1 `and`, i1 `or`/NOT/xor, `select` with i1 arms, a returned i1, and a `zext` inside an unrolled loop.

**A real bug the composition test found:** the loop unroller (`#801`) rebuilds each `SourceInstr` and dropped the new `from_type` field, so a `zext` in a loop lost its source type. One-line fix; would not have been found by any single-feature test.

**Refused, precisely:** narrow/wide integer types (`i8`/`i16`/`i64`) -- the diagnostic names the reason: they need a real SUB-WORD type system (re-masking after every op, sign extension for signed compares), a separate piece deliberately not bolted on; `zext` of anything that is not an i1 producer (an i1 ARGUMENT is not accepted -- nothing guarantees it is 0/1); conversions of literals. Mutation-checked (bytecode off): a `trunc` keeping 2 bits and a `sext` behaving as `zext` are both caught.

**REAL, HONEST SCOPE.** i8/i16/i64, `sdiv`/`udiv`/`srem`, memory (alloca/load/store), calls and multi-function modules remain refused. **Next in the agreed order: if/else via `phi`** (acyclic control flow by if-conversion).

## 803. IF/ELSE VIA `phi` -- ACYCLIC CONTROL FLOW BY IF-CONVERSION -- plus three things it forced: cheaper `select` forms, a measured router search schedule, and the keep-out ring back as a fallback mode. 15 control-flow tests; 1037 pass. (Alan/Claude)

The second item of the slice Alan chose ("start there"): if/else via `phi`, after i1 logic (`#802`).

**Approach.** Every supported op is PURE (no memory, no division, nothing that can trap), so IF-CONVERSION is sound: every block's instructions execute unconditionally (speculation), a `phi` becomes a `select` chain over its incoming EDGE conditions, and several `ret`s become a select chain over block-execution conditions. Implemented as `_multi_block` (build the CFG from llvmlite's PRINTED `br`/`phi` text, DFS cycle check: a back edge routes to the loop unroller of `#801`, otherwise to `_if_convert`) and `_if_convert` (reverse-post-order walk). Handles diamonds, triangles, nested ifs, chains of diamonds, phis of computed values, several early `ret`s, branching on i1 logic, and plain chains of blocks (which are just straight-line code -- the old 'control flow is not supported' refusals for 2-block and 4-block chains were flipped).

**Conditions are SYMBOLIC until used.** First version emitted `and`/`or`/`xor` gates eagerly, and a nested if produced `(c1 and c2) or (c1 and not c2)` -- redundant logic for what is just `c1`. Conditions are now tuples (`L`iteral, `V`ariable, `N`ot, `A`nd, `O`r) with the standard identities (double negation, absorption, `X or (X and Y) = X`, `(X and C) or (X and not C) = X`, `C or not C = 1`) applied BEFORE any gate is materialised, and materialisation is memoised. A plain diamond costs exactly one select; the nested if's join collapses to `c1` (7 source instructions, what a person would write). Edge and block conditions are LAZY thunks, so unused conditions emit nothing.

**A wrong turn, diagnosed.** The nested if kept being refused by the router. The if-converted source was already optimal and the final DAG had fan-out <= 2, so the fault was not the front end. Measurements: a layout existed but only at spacing 12 with 3,926 cells (useless); 24 of 240 sampled (spacing, seed) layouts routed at small spacing; and my diagnostic probe used a DIFFERENT jitter schedule from the real search, so it was not reproducing what `compile_dag_routed` did -- the discrepancy itself was the clue. Success probability is ~10% per layout under a gentle jitter (`1 + attempt//8`) and worse under the stronger one that was in place (`1 + attempt//4`). Fixed the schedule (and 16 attempts per spacing): the nested if now compiles in 0.1 s, 222 cells, 0 mismatches.

**Two front-end changes that made graphs cheaper and routable.** (a) `select` with BOTH arms literal (the common `phi [1,..],[2,..]` shape) is no longer the 5-op mask/complement diamond: `(1,0)` is a `copy` of the condition, `(0,1)` is `xor c, 1`, otherwise a 3-op CHAIN `f xor ((t xor f) and (0-c))` (2 ops when `f == 0`). (b) With exactly ONE literal arm it is a TREE (no sub-value used twice): `f xor ((t xor f) and (0-c))` or `t xor ((f xor t) and (c-1))` -- `c-1` is already the complemented mask. Chains and trees route trivially. A real slip caught in passing: the first fast path tested `t.kind == 'literal'` but by that stage operands are `DagOperand`s whose constant kind is `'const'` -- the fast path never fired and the diagnostic pointed at the router. One-line fix; found because the instruction list still showed the 5-op form.

**The keep-out ring is BACK, as an alternate search mode.** `#800` removed it (no benefit on simple programs; layouts equal-or-larger). It returns ONLY as an odd-attempt fallback, because denser graphs fail with 'no free output or input face' (pin starvation), which is what it prevents; the un-ringed attempt still runs first, so the size cost is not paid where it is not needed. NOT independently shown to be what fixed the nested case -- the schedule fix did; recorded so this is not over-claimed.

**Mutation-checked (bytecode off):** inverted phi edge polarity, a false-edge that is not negated, and a wrong boolean-simplifier AND-rule are each caught. **Tests that pinned the old behaviour were flipped or corrected:** 2-block and 4-block chains (now valid straight-line code); the clamp-chain shape that pinned 'growth cannot place this' became placeable by growth once `select` got cheaper -- a genuine improvement, so growth's limit is now pinned by the computed-arms shape only; a loop with a branching body (5 blocks) is refused precisely; one assertion of mine looked in the `why` field instead of `problem`.

**KNOWN LIMIT, pinned as a documented negative test:** a THREE-way early return with two computed arms (a dense select chain). 576 layouts (96 attempts x 6 spacings) ALL failed to route -- a real limit of the heuristic router (or non-planarity), NOT a search-budget problem. Refused loudly with a `place` diagnostic; the same shape with cheap arms compiles. Flip the test if the router improves.

**REAL, HONEST SCOPE.** Speculation means both arms always run: sound only for pure ops (division is refused, tested). NOT built: loops with branching bodies and nested loops (refused precisely); i8/i16/i64; memory; calls; `switch`; a router that handles dense select chains; a sign-aware ordered compare. Everything is VM-verified only -- none of it has been through Quartus or hardware.

**Real queue:** (1) bounded-card fit check driving `fold_width`; (2) sign-aware ordered compare + unsigned predicates; (3) a stronger router (rip-up-and-reroute / long-edge lane reservation) for dense select chains; (4) sub-word integer types; (5) `switch`, memory, calls; (6) scope items 3, 4, 6.

## 805. A STRONGER ROUTER -- NEGOTIATED CONGESTION (PATHFINDER) RIP-UP-AND-REROUTE. The 3-way early return (planar, but unroutable by the greedy router across 576 layouts) now compiles; narrow folds of branching designs now work, at a measured cost. `_route_all_pathfinder()` in `nano/vix_virtual_layout_v1.py`. 1060 tests pass. (Alan/Claude)

Alan: "start on the stronger routing, that may become a bone of contention, so let's get that sorted first." Motivated by `#804`'s correction: the 3-way return's dataflow graph is PLANAR, so a solution exists and the greedy router's search was the weakness.

**Why greedy fails, and the fix.** The greedy router commits each edge once, so an early edge can wall off a later one and the whole layout is lost. `_route_all_pathfinder` routes every edge with overlaps ALLOWED at a cost, then iteratively rips up and re-routes every edge that shares a cell at a rising present-congestion penalty (x1.5 per iteration) while contested cells accumulate a HISTORY cost, until no cell is shared. It is multi-source / multi-target Dijkstra (the router still chooses both faces), with a local search window around the endpoints first and the whole grid only if that fails. Same result fields as the greedy router, so `_lower` is unchanged.

**Measured (per-layout success over 40 (spacing, seed) layouts; greedy -> negotiation):** nested if 20% -> 38%; select with two computed arms 12% -> 40%; arms+cond 22% -> 52%; **3-way early return 0% -> 12%** (its first successes). Cost: roughly 10x slower per layout (0.5 s -> ~5-12 s per 40 layouts).

**Diagnosis before tuning.** Failures were NOT 'no path' -- they were 1-5 cells stuck in a dispute after 40 iterations, while EVERY success converged by iteration 9-12. So negotiation converges fast or never: iterations capped at 25 (fail quickly), and the budget spent on trying MORE LAYOUTS instead. And success was identical at every spacing (1 in 10 each) while varying by seed, which exposed a flaw in my own search: it re-used seeds 0..N at every spacing, re-trying the same node ORDERINGS. What decides success is the ordering a seed produces, not the room. Fixed: a different seed per spacing. The two together took the 3-way return from refused to compiled (299 cells, 0 mismatches, 0.7 s).

**Integration.** Stage two of each routed attempt: if the greedy pass fails, negotiate on the SAME layout. Budget: at most 30 failed negotiations per compile, and it switches itself off after 4 failures with >= 6 still-contested cells (many contested cells is the signature of a genuine crossing). Verified: the K3,3-minor program (truly non-planar, `#800`) is STILL refused, in ~2 s -- negotiation does not 'find' a planar embedding that does not exist.

**Two documented limitations FLIPPED, as their own docstrings said to:** the 3-way early return (`#803`) and folding a branching design below 4 columns per band (`#800`). A layout that compiles proves nothing, so both were checked in the VM. **The narrow-fold cost is real and is now recorded, not hidden:** the branching select folds correctly to 2 columns per band but at 774 cells (extent 212x11, 9 s to compile), 365 cells at 3 columns, 205 at 4 -- narrower folds force longer routes. A test asserts that trend.

**Tests (4 new + 2 flipped):** on the SAME layout greedy fails and negotiation succeeds (found by search, asserted to exist); a negotiated routing never shares a cell or crosses a node (checked directly on every routed edge); greedy alone cannot place the 3-way return but the default can; the non-planar case is still refused. Mutation-checked (bytecode off): tolerating two routes in one cell, letting routes cross nodes, and switching the stage off by default are each caught.

**HONEST LIMITS.** Success is still not universal per layout (12-52%), so the search still depends on trying several layouts; a genuinely better fix would ALSO reorder nodes (a crossing-minimising layout), not only re-route them. Negotiation cannot fix a placement that forces a real crossing. Compile time for hard designs is now seconds, not milliseconds. Routes are still a tree-free one-path-per-edge model (no shared prefixes for fan-out). VM-verified only.

## 806. THE FIT MODEL'S UNITS CORRECTED -- the budget is INSTANTIATED array positions at a MEASURED per-position ALM cost, not used cells at ~103 ALM. Supersedes the unit choices in `#804`. 9 new tests, 1069 pass. (Alan/Claude)

## 807. THE BRAM/DSP FIXED STRUCTURES AS A MODEL: the dispatch tree, the gather tree, and the sentinel at a chain's head and tail -- built from the project's own proven RTL and design entries, and checked against HARDWARE-PROVEN values. `nano/fixed_structures_v1.py`; 26 new tests, 1095 pass. **Alan's brief.** Fixed structures are used on the BRAM side -- the dispatch and gather tree mechanisms, whose DEPTH VARIES with how many feeds are needed -- and a sentinel design sits at the head and tail of the chain; the shapes are known maps, so the library may need additions. **What I read before building (the ledger archive `points/points_03_191-297.md`, the RTL, `docs/shapes/`).** `#258` (a mux/combiner node has THREE usable faces -- one of four is consumed by the RAM-facing connection -- so a real tree is needed; the routing ID is a 2-bit level count + three 2-bit slots: max 3 levels x 3-way = 27 destinations), `#263` (policy: the BRAM/DSP interface is a fixed, bounded, deliberately NON-PORTABLE addon unit; the rest of the fabric stays uniform), `mux_cell_v1.v` (the exact decode), `tb_mux_tree2_v1.v` / `tb_combiner_tree2_v1.v` (the proven bytes), `sentinel_bram_automaton_v1.py` (the sentinel port), and the known map `docs/shapes/top_sentinel_gather_shared_bram_v3.shape.json` (roles: `programmable_substrate` = the compiled chains; `connection_point` = the address counters, SENTINELS, collector and BRAM controller attached at a chain's boundary ports).

**The depth rule (implemented, `build_tree` / `levels_for`).** ceil(log3 n) levels, 0 for a single feed (no tree: count 0), an error beyond 27 with the reason. k nodes give 2k+1 faces (each non-root node consumes one parent face and adds three), so n feeds need ceil((n-1)/2) nodes: 5 -> 2 (the proven #271 tree), 9 -> 4, 27 -> 13. The builder turns the SHALLOWEST unused face into a child, preferring the highest face code, which reproduces the proven topology exactly (root: leaf, leaf, child; child: leaf, leaf, leaf).

**The routing byte (RTL, `mux_cell_v1.v`).** [7:6] count, [5:4] slot1, [3:2] slot2, [1:0] slot3; a node reads the slot INDEXED BY THE CURRENT COUNT and forwards the byte with only count decremented, so the root reads slot L and the last node slot 1. `dispatch_id`, `mux_decode` (walks the tree as the RTL does), and `gather_stamp` (the write-side rule -- innermost node starts at 1, each parent increments and writes into the NEW count's slot -- implemented independently, not by reusing dispatch_id).

**VERIFIED AGAINST SILICON-PROVEN VALUES.** The mux-tree testbench (#271) writes 0x40, 0x50, 0x88, 0x98, 0xA8 for its five leaves; the combiner-tree testbench (#272) expects 0x40, 0x50, 0x88, 0x98. The module reproduces all of them; the read-side and write-side rules agree for every destination of every tree size 1..27; decode reaches every destination; bytes are unique and fit 8 bits. ## 808. PLACING THE BRAM/DSP TREES AND TESTING THE FIT -- with the bus-width adaptation Alan asked for. **Alan's brief.** Place the trees and test the fit. The caveat: the design was built around the Arria 10's 40-bit word (8 routing + 32 data); other cards differ, so it must adapt -- even with a store-and-shift stage; e.g. a bus of only 16 bits would give 8 data bits, but that is likely a smaller card, so only one chain. **Reading of the numbers, stated:** "49" = the 40-bit M20K word; "26 ... 8 bits data, the other i bits routing" = a 16-bit bus (8 routing + 8 data), the only reading where 8 data bits follows. The width is a PARAMETER and 16, 26 and 40 are all tested.

**1. Bus-width adaptation (`BusSpec`, `BusPlan`).** Routing bits depend on the feed count: a single chain needs NONE (no tree, count 0), so the whole word is data; a tree costs the 8-bit field as built (`fixed_routing_field=False` models a proposed 2 + 2 x levels parameterisation). Data bits = width - routing; `beats = ceil(32 / data bits)`; more than one beat means a STORE-AND-SHIFT stage to assemble a value on the read side and disassemble it on the write side. Verified: 40 bit, 5 feeds -> 8+32, 1 beat (the proven build); **16 bit, 5 feeds -> 8 data bits, 4 beats** (Alan's example); 26 bit -> 18 data, 2 beats; **one chain -> the whole word is data at any width** (16 bit: 2 beats); a word too narrow for its routing is refused. NOT built, and said so in every plan note: the RTL as built always splits {8 routing, 32 data}, so a one-chain variant and a parameterised splitter/mux/combiner do not exist, and neither does the store-and-shift stage.

**2. THE 2D EMBEDDING LIMIT -- the decisive finding.** The routing byte rides DEDICATED per-direction wires between ADJACENT mux nodes (`mux_cell_v1`'s `routing_in_<dir>` / `routing_out`), so a parent and child must be UNIT NEIGHBOURS -- a relay in between would carry the 32-bit data but not the routing byte. Two nodes' faces can then point at the same neighbouring cell and a face that points at a node cell can offer nothing. Searched EXHAUSTIVELY over every tree shape (1, 8 and 473 shapes): **levels 1/2/3 offer 3/7/13 leaves in 2D, not the abstract 3/9/27.** The 2-bit count could address 27 feeds; the GEOMETRY caps a 2D build at 13. This is Alan's earlier 2D-vs-3D point, quantified: the format reserves the third axis (the nano's `routing_mask`/`cardinal_edge` are 6-bit slots, 4 wired) but it is not built. `embed_tree(n)` picks the fewest levels, then fewest nodes, then children on the highest face codes; beyond 13 it refuses with the reason. The embedded 5-feed tree reproduces the HARDWARE-PROVEN bytes 0x40/0x50/0x88/0x98/0xA8 exactly (a first version picked a mirror-image tie and did not -- caught, fixed with the tie-break), and decode/adjacency/no-overlap/distinct-leaf-cells are checked for every n = 1..13.

**3. Placement (`place_stream`).** The BRAM interface is one rigid macro: controller at the origin, splitter north of it, dispatch tree beyond, combiner root south of it, gather tree beyond -- **a floor plan I chose (the RTL has the connections, not a placement); stated as an assumption.** N rigid copies of a compiled chain sit in a column; each chain connects to a dispatch leaf pin and a gather leaf pin by ordinary relay ROUTES found by the negotiated-congestion router (extended so an edge may be restricted to specific pins). The mux/combiner/splitter/controller are not VIX cores, so they are recorded as `SetPieceCell`s (position, faces, `face_for_slotN` codes) that occupy array positions; everything else -- the chains and every relay -- is a real ICM. **Because the chains are identical, which pin feeds which chain is arbitrary:** two hand-made pairings (by destination number, by pin position) both failed to route, so each chain may use ANY leaf pin and the router negotiates it; the result is read back as the host's mapping tables (dispatch id -> chain -> gather stamp), checked to be permutations.

**Verified, on the real VM.** 1, 2 and 3 chains: structurally clean (no overlap, contiguous routes, adjacent tree nodes, tree decode), and values injected where the dispatch tree would offer them travel the placed route, the replicated chain and the output route and are read where the gather tree would receive them: results correct, sentinels safe_to_intervene, and NO value leaked onto another destination's output. One chain places no tree at all (controller + splitter only).

THE FIT.** A `target=` binds the BRAM controller to a real BRAM site from the Mustang MAN (the layout is translated so it lands on one that keeps everything inside the grid) and reports used cells, the instantiated array, budget and the bus (`n data bits/beat, m beat(s)`). A REAL ROUTER BUG THIS EXPOSED.** The present-congestion factor grew x1.5 per iteration with no cap and the search used 1e18 as 'infinity'; after ~120 iterations every cell looked unreachable and the router reported 'no path exists even ignoring congestion' for a reachable pin -- a fake hard blockage that sent me down a wrong path for two rounds. Also added STALL DETECTION (stop after 40 iterations without reducing contested cells) as the default -- but measured that successful stream placements need 42-117 iterations and look stalled at 1 contested cell for a long time, so stream placement uses the full 150-iteration budget without it.

## 810. THE COUNTER MECHANISM WITH FEEDBACK, at protocol level -- credit-gated counters, backpressure from a stalled chain, the priority cell versus a fixed-order scan, then the shared single port. `nano/counter_feedback_v1.py`; 21 tests; 1171 pass. Grounded on the REAL VM: a priority cell serves the live source when the other never offers; a sequencer passes nothing. (Alan/Claude)

**Alan's brief (2026-09-21).** The counters need some degree of feedback, which limits the chain options (probably to 2) but gives flexibility and a degree of control over stalled chains, and lets RAM requests avoid stalling THEMSELVES on a loaded chain -- backpressure stalls any call to a stalled chain until it clears, via the ACK side. Start there (two-port), then the single (shared) version. And the priority cell must be used, or one part can stall and stop the whole chain.

**What the real RTL does (`top_sentinel_gather_shared_bram_v3.v`, read before modelling).** Each chain has its own address counter (block-partitioned). The collector scans chains round-robin; its ready is asserted only for the ACTIVE chain and only once that chain's own capture is `fresh`, and the scan advances on THAT chain's ack. The collector's ack (`collect_pulse`) ALSO PACES THE NEXT FEED -- that is the feedback loop, roughly one item in flight per chain -- and a scan that waits on the active chain's ack is exactly where head-of-line blocking lives.

**GROUNDED ON THE REAL VM CELL.** Two sources into a priority cell; the 'stalled part' A never offers. PRIORITY mode (0) passes B (222); SEQUENCER mode (2, fixed order waiting for A) passes NOTHING (0, invalid). With both offering, the two agree. So Alan's claim holds on the actual cell semantics: a fixed-order merge lets one stalled part stop everything; the priority cell does not.

**The model.** Per chain: an address counter, a leaf buffer, `latency` rounds per item, an output buffer, and a SENTINEL (feed at the head, collect at the tail). FEEDBACK = the sentinel's credit (in flight < window) AND the leaf buffer's room AND the chain's READY (the ack side): a chain that is not accepting must not be asked. Read arbiter `scan` (WAITS on the current chain) or `priority` (serve whoever is ready, losers wait pending); the same choice on the write-side gather. `ports=2` (independent read and write ports) then `ports=1` (ONE shared port, write priority, a blocked read queued).

**MEASURED -- chain 0 blocked from round 4 to 69, chain 1 healthy (2 chains x 6 items).**
| feedback | read arbiter | healthy chain finishes | tree blocked | sentinel errors |
| ON | priority | round ~30 | 0 | 0 |
| ON | scan | after the stall (~round 80) -- progress 0 during it; the scan waited 69 rounds | 0 | 0 |
| OFF | either | late | 62 rounds (an item for the full chain sits IN the tree and blocks EVERY read) | 2 (overflow latched) |
So: the priority cell removes the head-of-line block; feedback stops requests stalling themselves and keeps the free-running counter inside its window (which the sentinel otherwise latches); and BOTH are needed. Also verified: a larger credit window puts more items in flight and finishes sooner; the stalled chain's own counter stops at its credit limit (backpressure); an input-side stall is isolated by priority and starves the scan; the write-side gather needs the priority cell too; a stall that never clears only ever holds up its own chain under priority; results are correct, in order per chain, and BRAM output is densely packed. **Single shared port:** completes correctly, 5 reads deferred behind writes, 30 rounds vs 20 for two ports (the cost of sharing), and a stalled chain is still isolated under priority and not under scan.

**TWO MODEL GAPS FOUND WHILE BUILDING (both fixed, both mine).** (1) In single-port mode a DEFERRED read chose its target by priority rules whatever the arbiter was, so a 'scan' arbiter silently stopped blocking; the arbiter now picks the target first and the port decides whether it issues now or is queued. (2) The first feedback covered credit and buffer room only, so a chain refusing input still looked eligible and its item stuck in the tree; the chain's READY (the ack side Alan named) is now part of it. The first failing test also showed a poor metric: I had used an arbitrary progress window, so results now use `finished_round` (when a chain had collected ALL its items).

**MUTATION-CHECKED (bytecode off):** removing the credit check, ignoring buffer room, ignoring the ready signal, making the scan non-blocking, and starving the sentinel of feeds are each caught. **NOT caught, and honest about why:** dropping the queued read on the shared port. In this model the counter only advances on an actual issue, so a deferred read is simply retried -- the mutation is EQUIVALENT here. The RTL hazard `shared_bram_arbiter` guards against (a single-cycle command pulse silently lost inside the splitter) cannot occur at this abstraction, so this model does NOT show the queue prevents loss; the test's claim was corrected to say so.

**HONEST LIMITS.** (1) **"Probably 2 chains" is Alan's estimate and is NOT derived** -- the model runs any N (1-4 tested) and I have not identified what physically fixes it; a face budget at the interface cell is a guess, not checked. It needs Alan's reasoning. (2) Protocol-level, rounds not clock cycles; the chains are abstract (a function and a latency), NOT the placed layouts of `stream_layout_v1`. (3) Not connected to the placed layout: the FORWARD routes there are ordinary relay chains whose per-hop offer/ack already carries backpressure, but the credit side-channel (sentinel diff -> counter) and the counters themselves are NOT placed or routed. (4) The host stall/refill lifecycle and the open empty/full status signal (#257) are not modelled. (5) No counter, sentinel or arbiter RTL simulated. (6) DSP unchanged; VM mirror still not on the LLVM path or a CLI.

**Real queue:** (1) work out with Alan what limits the counter mechanism to ~2 chains, and whether the credit side-channel is what costs the faces; (2) place the counters and the feedback path in `stream_layout_v1` and route the credit/ack lines; (3) model the host stall/refill and the empty/full signal; (4) a two-chain layout on the real VM using a priority cell at each merge; (5) DSP-wrapper lowering + the six DSP ops; (6) wire the VM mirror into the LLVM path and a CLI; (7) store-and-shift; (8) floating point; (9) scope items 3, 4, 6.
