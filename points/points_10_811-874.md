## 811. WHY THE COUNTER FEEDBACK LIMITS THE CHAINS TO TWO -- a planarity result, confirmed on the real router; and the way out: ONE credit-return link instead of a feedback line per chain. 17 new tests, 1188 pass. (Alan/Claude)

**Alan's point (2026-09-21).** If the feedback channel sits in the centre and feeds up to the RAM address counter, how do extra chains reach it? It doesn't fit: once the lines come out they must wrap around to reach the second point, so there is no crossing available. This answers the open item from `#810`, where "probably 2 chains" was Alan's estimate that I could not derive.

**IT IS A PLANARITY THEOREM.** Each chain needs a line to the dispatch side, the gather side AND the feedback channel. Three separate hubs each joined to every chain is the complete bipartite graph K(3,n): planar for n <= 2, NON-planar from n = 3 (K(3,3) is a minor). Checked with `networkx.check_planarity`: two hubs (dispatch + gather) are planar for EVERY n -- which is why 9 chains routed in `#809`; adding a per-chain FEEDBACK hub is planar only for n = 1, 2; and two hubs plus ONE credit-return link G-D are planar for every n. Contracting a connected blob to a vertex preserves non-planarity, so it holds whatever shape the trees take.

**CONFIRMED ON THE REAL ROUTER (`place_stream(..., ports=2, feedback=...)`).** Per-chain feedback (a shared counter block west of the read macro, every chain's tail joined to it): 1 and 2 chains route; 3, 4, 5, 6, 8, 9 all FAIL -- exactly the planarity limit. Alan's mechanism, stated plainly: an interior chain's line would have to cross the output routes of the chains between it and the top or bottom, so only the topmost and bottommost chain can escape without a crossing.

**THE WAY OUT: one credit-return link, keyed by the ID the gather tree already stamps.** Credit-release information (the sentinel's collect) is available at the WRITE controller, which stamps the source chain's ID on every result -- so the feedback can be a SINGLE channel from the write side to the counters carrying that ID, decoded at the counters (inside the read blob, so it adds no hub). This is the counter-as-free-ID idea of `#257`. Routed FIRST, round the perimeter (up from the write controller, over the top of every node, down the far side to the counter), with the rest negotiating around it: **1-6 and 8 chains route; 7 and 9 do not** -- the perimeter path is never blocked; the remaining routes are already at the router's density edge there (no-feedback took 0.4 s at 7) and the link's vertical run tips it over. A router-capacity limit, pinned as a documented negative test, NOT a planarity one.

**WHAT THE SHARED LINK COSTS (protocol model, `credit_link=d`).** Two chains, no stall, rounds to finish: window 1 / buffers 1: per-chain 20, shared link delay 2 -> 30, delay 5 -> 45; window 3 / buffers 3: 15 / 15 / 17; window 6: 15 / 15 / 15. So it costs BUFFER DEPTH to cover the return latency, not correctness; a stalled chain is still isolated under priority with the shared link. **A CORRECTION to what I first said:** I described the serial channel as costing throughput because credits return 'one at a time'. That is not binding: there is one write per round, so at most one credit is ever generated per round and the channel cannot fall behind -- lifting it is an EQUIVALENT mutation (checked). The real cost is only the return DELAY.

**TWO MISTAKES CAUGHT ALONG THE WAY.** (1) A router that negotiates could not route the single long link (it must circle everything; negotiation is a poor fit for one net that spans the whole structure) -- hard reachability was checked first (it WAS reachable in every case), which showed it was contention, not enclosure; the standard remedy (route the long net first, round the outside, let the rest route around it) is what worked. (2) My first perimeter path stopped one cell SHORT of the counter -- caught by the test asserting the link ends adjacent to it, fixed.

**Router change:** `_Edge.path_fixed` -- a pre-routed net is an obstacle and is not re-routed by the negotiation. **Mutation-checked (bytecode off):** never routing the per-chain edges, routing the link through the middle, letting the router re-route the fixed link, and ignoring the return delay are each caught. NOT caught (equivalent): lifting the one-credit-per-round serialisation.

**HONEST LIMITS.** (1) The feedback lines are NOT functionally modelled on the grid: the credit route ends at a counter set-piece with no consumer, so a per-chain feedback line tapping a chain's result cell would eventually back-pressure it on the VM; the layouts are checked for routing, adjacency and overlap, and the forward path still runs on the VM only for the credit-return variant (its source is the write controller, not an ICM cell). (2) The counter block is a modelling choice (a column of counter cells, or one cell, west of the read macro); real adjacency of the address counters to the controller is not modelled. (3) The credit link is keyed by the gather STAMP; the ID -> per-chain-credit DECODE at the read side is not built or placed. (4) Head-side ready/ack rides the forward relay routes (per-hop offer/ack) and is not separately routed. (5) The 3D axis would lift the per-chain limit (K(3,3) embeds with a layer change) -- not built. (6) 7 and 9 chains with a credit link do not route.

**Real queue:** (1) place and decode the ID -> per-chain credit structure at the read side; (2) model the host stall/refill and the empty/full signal; (3) a denser router for 7, 9-13 chains; (4) the shared-port (one bus) case with this feedback; (5) DSP-wrapper lowering + the six DSP ops; (6) wire the VM mirror into the LLVM path and a CLI; (7) store-and-shift; (8) floating point; (9) scope items 3, 4, 6.

## 812. THE ADDRESS SUPPLY AND ITS CONTROL: BRAM read latency 1-3, and "the feed's out, here's the next address" as an ACK-driven advance -- the counter model and the feedback model both need it. Protocol model extended; 15 new tests, 1203 pass. (Alan/Claude)

**Alan's message (2026-09-21).** In the feedback design the counter becomes a simple RAM (or similar) that just passes data through to the BRAM controller; it must be controlled by the results out, because the BRAM side can take a few extra cycles to produce (1-3 in the original docs). Either the counter model (simpler) or the feedback model: both need a control mechanism that says 'the feed's out, here's the next address'.

**WHAT THE EXISTING DESIGN ALREADY SAYS (read before building).** `bram_controller_v1.v`: a single-stage synchronous read; `cmd_valid` is a ONE-CYCLE pulse and `rdata_valid` pulses exactly one cycle after it. `#243`: BRAM reads are not single-cycle -- 1-2 cycles -- and the latency must be ABSORBED, not assumed. `#256`: `addr_counter_v1.v`'s `advance_en` is driven by the memory cell's own genuine ACK, never a fixed cycle count. `#284`/`#285`: the real Quartus fix doubled the latency from 1 to 2 cycles (`bram_controller_v2.v`, registered read address) and the whole system re-ran with IDENTICAL timestamps -- zero change outside the memory core -- because every consumer waited on the real valid signal. Steady state (`#257` era): 2-cycle latency, 1-cycle throughput, the counter having already advanced and the next read already in flight. Alan's '1 to 3' is presumably the end-to-end figure with the interface around the core; the model accepts 0-3 and I have not verified 3 from the RTL.

**WHAT WAS BUILT (`counter_feedback_v1.run`).** `bram_latency` (0-3): data appears that many rounds after the command. The read interface holds `outstanding` reads (default 1: the splitter latches one). `advance='ack'`: the next address is released only when the interface has a free slot -- the feed is out. `advance='fixed'`: a counter that ASSUMES the latency and pulses a command every `fixed_period` rounds regardless; a command arriving while the interface is busy is LOST (the single-cycle-pulse hazard `shared_bram_arbiter_v1.v` documents) and the counter has already moved on, so that item is a hole. `addr_source='counter'` supplies sequential addresses, `'ram'` a stored arbitrary sequence read THROUGH the BRAM (`addresses`, `bram`); a counter refuses a non-sequential sequence. Credit and leaf-buffer room now count reads still in the BRAM pipeline.

**MEASURED (one chain, 8 items).** Ack-driven: rounds 11 / 19 / 27 at latency 1 / 2 / 3, ZERO lost reads and correct results at every latency. A counter tuned for a 1-cycle BRAM (one command per round): correct at latency 1, then LOSES reads at latency 2 -- silent data loss, not a deadlock: the `#284` doubling reproduced. A fixed period of 2 works at latency 1 and 2 but loses 4 of 8 items at latency 3. Ack order verified: the next address is released the round the previous data comes out; the latency is honoured exactly. Throughput vs reads held in the interface (rounds): latency 2: 19 (1) -> 12 (2); latency 3: 27 (1) -> 16 (2) -> 13 (3) -- holding at least `latency` reads restores about one item per round. An address RAM and a counter have IDENTICAL timing and issue order; only the address sequence differs, and the RAM is the flexible one.

**THE TRADE-OFF THIS MAKES VISIBLE.** The COUNTER model with ack advance taken from the BRAM interface alone (the feed-out ack, local to the read macro) needs NO line from the chains back to the counters, so it has no K(3,n) planarity problem (`#811`) -- but with no chain feedback a stalled chain's item sits in the dispatch path and blocks every read (`#810`: tree blocked 62 rounds, healthy chain starved, sentinel overflow). The FEEDBACK model isolates a stalled chain (the healthy chain finishes early with priority arbitration) and costs the credit-return link, which one shared channel keyed by the gather stamp keeps planar (`#811`), paying buffer depth for the return delay. So: counter model = simpler and planar for any chain count, no isolation; feedback model = isolation, one return link. **My reading of 'controlled by the results out':** both styles use the feed-out ack for the ADDRESS release (local); only the feedback model adds the results-collected credit. If Alan meant the RESULT (post-chain) should itself release the next address, that is the feedback model's credit path.

**MUTATION-CHECKED (bytecode off):** issuing into a busy interface in ack mode, never losing a command into a busy interface, accepting non-sequential addresses on a counter, and an off-by-one BRAM latency are each caught. The credit gating and the leaf-room gating each count reads still in the BRAM, and each ALONE is masked by the other (overlapping guards -- removing either one is an equivalent mutation); removing BOTH is caught by a test I added after the first run showed a gap: a STALLED chain with reads in flight must not have its credit ignore them, or the delivery path blocks and the sentinel latches overflow.

**HONEST LIMITS.** (1) Protocol-level, rounds not cycles; no counter/RAM/controller RTL simulated. (2) The placed layout still names the address supply a 'counter' set-piece and does not model it passing data through to the controller. (3) The 1-3 cycle range is Alan's recollection; the RTL shows 1 (v1) and 2 (v2). (4) The interface's `outstanding` depth is a parameter -- what the real splitter/controller pair can hold in flight is not derived here. (5) The shared-port (one bus) variant with this latency is not separately explored (single-port still runs; the old queued-read path is unchanged). (6) Host stall/refill and the empty/full signal still not modelled.

**Real queue:** (1) place and decode the ID -> per-chain credit at the read side; (2) rename/model the address supply as a RAM cell passing through to the controller in `stream_layout_v1`; (3) host stall/refill + the empty/full signal; (4) a denser router for 7, 9-13 chains; (5) the shared-port case with feedback and latency; (6) DSP-wrapper lowering + the six DSP ops; (7) wire the VM mirror into the LLVM path and a CLI; (8) store-and-shift; (9) floating point; (10) scope items 3, 4, 6.

It also says feed-in on two buses GIVES UP stall isolation unless that link is paid for.

## 814. THE PRIORITY CELL ON THE SINGLE BUS (measured on the real cell: only its WEIGHTED mode is fair, and the weight field is 2 bits), AND THE DSP CHAIN AS A BLACK BOX THAT MUST BE MONITORED AT BOTH ENDS. `nano/shared_bus_v1.py`, `nano/dsp_blackbox_v1.py`; 39 new tests, 1259 pass. Alan's two questions from #813 are answered. (Alan/Claude)

**Alan's message (2026-09-21).** (1) 'Feed in' is the data coming from the BRAM; 'feed out' is the RETURN values. (2) A side thought: for the single-bus units place a PRIORITY CELL instead, so both chain ends are kept moving at the rate of the RAM. (3) The DSP side, from the original doc, varied from 0 (or 1) to OVER 8 per link in the DSP chain, so a programmed chain takes a varied time depending on its functions and how many are linked; so BOTH the feed in and the return to the DSP must be MONITORED, or collisions could occur internally, away from the UniCell substrate, where we have no control.

**#813's TWO QUESTIONS, RESOLVED.** Feed in = BRAM data arriving at the chain (= my 'delivered'); feed out = the return values (= my 'result_out'): the mapping holds. For DSP, 'feed out' is the RETURN from the chain -- because the links inside a hard cascade have no ack we can see, so #813's per-link 'stage_out' is not observable there; only the two ends are, which is exactly why both are monitored.

**THE PRIORITY CELL, MEASURED ON THE REAL VM (both ends always ready).** STRICT mode (0): one end gets EVERY slot and the other gets NONE -- 199 of 199 -- at equal ranks (the fixed N>S tie-break) and at unequal ranks. So a priority cell in its default mode does NOT keep both ends moving. But `scheduling_mode=1` is WEIGHTED round-robin (Surplus Round Robin): equal weights alternate ABABAB..., 3:1 gives exactly 75%/25% (AAABAAAB...), 1:3 the mirror; an end that offers only occasionally is served whenever it does. **So the side thought holds, with one condition: the cell must be in mode 1.** The `shared_bram_arbiter_v1.v` policy (WRITE priority, a blocked read queued) is strict: it starves the feed-in end whenever returns saturate (0 of 300 served in the model); strict read priority starves the return end. A weighted priority cell serves both ends at the rate of the RAM (150/150, waits <= 1; the RAM is never idle).

**THE ROUND-ROBIN, REPLICATED EXACTLY.** Read from `unicell_super_automaton_v1.py` (#730): every side's credit gains its weight at each arbitration; the highest credit wins (ties N>S>E>W); the winner pays the total weight of the CANDIDATES, floored at 0. The replica reproduces the real cell's sequences EXACTLY for every weight pair 1-3 x 1-3 (9 weighted) and 7 strict rank pairs -- 16 configurations, each ~160 items. **A HARDWARE TRAP FOUND BY A MISMATCH:** the first comparison used weights 5:2 and 1:7 and DIFFERED -- the cell's rank/weight field is 2 BITS and the real cell MASKS larger values SILENTLY (`& 0x3`): a weight of 5 behaves as 1, 7 as 3, with no error. Confirmed on the VM (5:2 == 1:2; 1:7 == 1:3). So the largest achievable share ratio is 3:1, and the replica REFUSES anything above 3.

**THE DSP BLACK BOX (`dsp_blackbox_v1`).** Links have latencies from 0 upward (total = their sum, at least 1); inside there is NO backpressure -- what is fed advances every round and emerges that many rounds later. Two hazards nothing inside can prevent: a RETURN collision (a result emerges while the return side is full: overwritten) and a FEED collision (a target fed inside the initiation interval `ii` of the programmed function: corrupted). The MONITOR sits at the two ends the substrate CAN see -- a feed-in count and a return count, like the sentinel -- and feeds only when (in flight + results still held) < return_slots (a place to land it is guaranteed) and `ii` rounds have passed. It never needs the latency. **MEASURED:** (a) variable latency ALONE is NOT the hazard -- an unmonitored feeder into a return side that keeps pace collides with nothing even for a 27-round chain; (b) a return side that STALLS: unmonitored 1 of 12 returned, 11 collisions; monitored 12 of 12, none; (c) a return side SLOWER than the feed: unmonitored collisions; monitored none; (d) an initiation interval of 4: unmonitored 11 feed collisions; monitored none; (e) the monitored rate follows LITTLE'S LAW without ever knowing the latency (rounds for 40 items on links [0,1,8,2]: 441 / 222 / 114 at 1 / 2 / 4 return slots vs ~440 / 220 / 110), in flight never above the slots; (f) any of 50 random latency profiles (0 to 12 per link), slot counts, stall windows and intervals: zero collisions, all returned in order.

**MUTATION-CHECKED (bytecode off), WITH TWO SURVIVORS FIXED.** Caught: the winner never paying, the tie-break reversed, strict scoring inverted, the 2-bit bound not enforced, write_priority inverted; the DSP monitor ignoring free return slots, ignoring results still HELD, a full return side never overwriting, total latency = slowest link instead of the sum. **D2 survived and was a REAL BUG IN MY MODEL:** the feed-collision hazard was only checked for the UNMONITORED feeder, so a monitor that ignored the initiation interval was never penalised. A hazard is physical, so it now applies to every feed whoever issued it. **B1 survived** (the winner pays ALL sides' weight, not just the candidates'): invisible under saturation because with two saturating ends the sums coincide -- it only shows when one end is ABSENT, which the replica-vs-VM comparison never exercised. Now pinned by a scripted sequence worked out BY HAND from the cell's source (an absent side still gains its weight; a lone candidate pays only its own weight). **That test is derived from the source, NOT measured on the VM** -- the absent-side credit accumulation (a side that was away is owed a burst when it returns) is replicated but its long-idle behaviour was never separately measured.

**HONEST LIMITS.** (1) The DSP latency profile (0/1 to over 8 per link), the initiation interval and both hazards are MODELLED from Alan's description; I have NOT checked them against a real DSP cascade or the Quartus IP, and `dsp_arith_wrapper_v1.v` holds ONE operation at a time (`computing`), so this multi-item pipeline is the CHAIN case Alan describes, not the single wrapper. (2) The shared-bus model is standalone: `counter_feedback_v1`'s single-port path still uses WRITE priority and does not use a weighted priority cell; `stream_layout_v1` does not place a priority cell at the shared controller. (3) Rounds, not clock cycles; one queued offer per end. (4) The replica is verified on the VM only under saturation. (5) Which weights to choose (the read/write share) is not derived; 1:1 is the natural default.

**Real queue:** (1) put the weighted priority cell into `counter_feedback_v1`'s single-port path and compare it with the write-priority arbiter there; (2) place the priority cell at the shared controller in `stream_layout_v1` (one bus) and count its cost; (3) wire the DSP monitor to the address-supply control (return slots as credits) and the elastic-pipeline model; (4) get the real DSP latency/ii figures (the original doc; Quartus IP) into the black box; (5) place and decode ID -> per-chain credit at the read side; (6) host stall/refill + the empty/full signal; (7) the address supply as a RAM cell passing through to the controller in the layout; (8) a denser router for 7, 9-13 chains; (9) DSP-wrapper lowering; (10) VM mirror into the LLVM path and a CLI; (11) store-and-shift; (12) floating point; (13) scope items 3, 4, 6.

## 815. THE ARRIA 10 DSP CHAIN'S REAL TOPOLOGY: a fixed 27-block chain, programmed once, tapped in and out anywhere -- but ONE feed per chain regardless of span. Per-block latency made a CARD PROPERTY in the MAN file, deliberately left loose. `nano/dsp_chain_v1.py` + `card_fit_v1.dsp_chain_from_man`; 20 new tests, 1279 pass. (Alan/Claude)

The Arria 10 chains are odd: many units (~1.6k) but chained blocks limited to 27; the extra fun part is you can enter at any point and leave at any point, so you could program known sequences at set points and just use those -- but you can only feed ONE value per chain, no matter how much of it you use.

**GROUNDED -- this was already anticipated.** `#25`/`#26` (2026-07-09, Arria 10 handbook 683461 sec 3.3.5 p46): chain length 27 is a SPINE CLOCK REGION limit -- spatial/placement, not arithmetic -- and DSP latency/legal chain lengths/block coordinates are explicitly named CARD properties belonging in the MAN file, not model properties. `#33` already separates control (fabric) from data (BRAM), consistent with treating a chain as an addressable resource with taps.

**MAN file (`docs/man/mustang-f100-a10.man.json`).** Added `device.dsp.chain`: `max_length: 27`, the spine-region reason, `total_blocks` (1687, already present), and `latency_per_block_cycles: null` with a note that this is card-dependent and deliberately unset. `card_fit_v1.dsp_chain_from_man(man)` reads it into `DspChainCard`; a MAN file with NO chain entry is REFUSED (not silently treated as unbounded).

**The chain model (`dsp_chain_v1.DspChain`).** Programmed ONCE with a fixed sequence of block operations; `.tap(entry, exit)` reads any contiguous sub-sequence without touching the programming -- verified for the whole chain, a single block at either end, and every out-of-range or backwards request refused. `.feed(entry, exit)` CLAIMS the chain; **the exclusivity rule Alan named is enforced exactly as stated: feeding one tap makes the WHOLE chain busy for every OTHER tap, disjoint or identical, regardless of span** -- feeding all 27 blocks and feeding one block cost the same busy state. `.release()` frees it for a new tap anywhere. `ChainPool` makes the consequence operational: parallel DSP work needs MORE CHAINS, not more taps on one; a pool of N chains allows exactly N concurrent feeds and refuses the (N+1)th by name.

**Loose, on purpose.** `ChainSegment.links(latency_per_block)` turns a tap into the exact `links` list `dsp_blackbox_v1.run_dsp` (`#814`) already consumes -- so the feed-in/return monitor built for the DSP black box applies unchanged to whichever segment of whichever chain is in use, verified directly (a 6-block tap fed into the #814 monitor: 8/8 returned, correct). **What it does.** `Assembler` accumulates `plan.beats` narrow chunks, in order, into the original `plan.word_bits`-wide value -- a classic serial shift-in (SIPO) accumulator: each new chunk shifts what has already arrived toward the HIGH end and ORs the new chunk into the freed LOW bits, so the FIRST chunk received ends up most significant. `disassemble()` is the exact inverse, splitting a value from the high end down so feeding its own output back through `Assembler`, in order, always reconstructs the original value -- proven directly, not just documented as intended.

Checked directly: `0xFFFFFFFF` through the 26-bit-bus plan gives a first chunk whose top 4 bits are genuinely zero, and a second chunk that is an untouched, full 18-bit low slice.

**Verified.** The exact `#808` worked example (0xDEADBEEF, 26-bit bus, 5 feeds, 2 beats) round-trips exactly. ## 843. **A citation correction made and recorded honestly, not quietly fixed.** Mid-discussion, Claude asserted the drain/checkpoint pattern below was already proven precedent from "hybrid-DSP design work" ("freeze -> system quiesces -> hard blocks settle -> save cell states"). This entry rests on that honest footing: a real, referenced, UNBUILT concept, not a proven mechanism being reused.

**The throughline, in order of how it was reasoned out:**

1. **Static-vs-reconfigure, the real architectural fork.** For fp32 ADD's normalize stage (shift-on-overflow) and, by the same reasoning, its alignment stage (`#840`'s barrel-shift gap): a static branch-and-pad structure (branch routes to one of two pre-computed paths, RAM cells pad the shorter path to equal hop count, `#544`) gives full pipeline throughput, back-to-back values with no gap. A `v1d`-style live command-cell reconfigure is cheaper in cells but pays a REAL, PIPELINE-WIDE pause every time it fires, because freeze is not per-cell -- it stalls the whole substrate while it happens. Settled: for anything meant to be a real, reusable, streaming tile, static wins on architectural grounds alone, independent of the actual depth/cell-count numbers (still unmeasured). `v1d`-style reconfigure is the right tool for genuinely rare/occasional retuning, not for gating a per-value decision inside a stream.

2. **The real, deeper insight Alan named directly: live addon reconfiguration doesn't just retune an operation, it can change what a chain fundamentally DOES, in place, with no rebuild** -- a step beyond ordinary per-field PROG_ID reconfiguration (which still leaves an adder "an adder"). Genuine power, with the honest, already-established cost (1) above.

3. **Section-wide broadcast reconfigure -- amortizing the pause across many cells at once, not just one.** A line of command cells, each in programmer mode, each independently wired 1:1 to its own target, each carrying its OWN relay payload (not necessarily identical). If all of them trigger on the SAME cycle rather than merely close together, the pipeline pays one pause window regardless of how wide the section being touched is. The real, still-open mechanism question: what makes them start on the identical cycle, by construction rather than by luck? Trigger mode's own real "watches a shared signal, direction-agnostic, OR-combined" design is the natural answer -- if every command cell in the line watches the SAME broadcast signal, they cross idle->active together by construction. Points directly at `#835`/`#836`'s own paired-cell/command-bus idea as the natural carrier for that shared trigger, rather than inventing a second broadcast mechanism alongside it.

4. **The real hazard this raised, and Alan's own resolution: drain before you reconfigure, so nothing is ever caught mid-flight across the boundary.** A genuine two-branch pattern: Branch A live and processing while Branch B is reconfigured off to the side (safe regardless of B's state, since B isn't in A's data path yet); A's output feeds a checkpoint (RAM); the newly-reconfigured B takes over, fed FROM that checkpoint; A becomes the next branch available to reconfigure, and the cycle repeats -- a genuine ping-pong, not a one-shot swap. The real, still-open piece: knowing when a drain is genuinely complete, not just paused -- naturally answered by SOME real drain-completion signal, and `#257`'s own empty/full concept is the obvious real fit for that role, but (per the correction above) it is UNBUILT -- a real design gap to close, not a mechanism to assume already works.

5. **The genuinely elegant closing piece, Alan's own: overlap the reconfigure with the flow, rather than pausing FOR it.** The same drain-complete signal that hands a checkpoint to the branch taking over ALSO fires the trigger that starts reconfiguring the branch that just emptied -- one signal, two jobs, for free. By the time fresh data has finished flowing through the branch that's live, the branch that drained has already finished becoming something new. The reconfigure latency hides behind the handoff instead of sitting in the critical path.

6. **A genuinely different USE MODE this whole pattern opens, not just a latency optimization: iterative folding.** Rather than laying out every stage of a multi-stage algorithm as separate, permanent hardware, fold the WHOLE algorithm through a small, fixed footprint of cells, one stage at a time, self-triggering its own reconfiguration between passes via the mechanism above. Real, compact area-for-time trading -- a genuine answer to doing a lot of computation on a small board (the Tang Nano's own real constraint), not requiring every stage to exist in silicon simultaneously.

**Alan's own closing framing, worth preserving verbatim rather than paraphrased, since it names what this whole session's worth of design exploration actually is:** this kind of investigation -- reasoned out on the VM side, no hardware required, nothing at risk -- is exactly what this project's own architecture is FOR: "a safe playground of computation built in logic, performed by physics."

**Real, honest status: nothing built, not even a design-note file.** This entry exists to make sure the reasoning survives to next session in the ledger itself, not just in chat history. No RTL, no VM code, no cell counts, no tick counts -- every real number this design needs (branch depth, RAM padding count, actual reconfigure-cycle cost, whether trigger mode's shared-signal watch genuinely synchronizes to the same cycle) is still unmeasured.

## 873. A DESIGN OBSERVATION, NOT BUILT -- Alan's proposal to simplify the command cell and sequencer while nothing is on silicon yet. Logged with what I verified about the current cells and a recommended path, so it survives the session reset. (Alan/Claude, 2026-09-28)

**The proposal, as I read it (confirm before building).** (1) A command cell that ACCEPTS A START COMMAND FROM ANY DIRECTION, then RUNS by sending an ack to a set direction -- the run phase is "ack the word source in the configured direction, one word per ack, relay to the target, stop on the End word", after which the cell goes idle and the store simply holds. **Why it looks right (evidence from `#868`-`#872`, not opinion).** It would remove: the freeze-the-head trick and the SECOND command cell it needs; the fan-out from the store head to both cells, and the race that forced it (`#870`: the final word had to reach the trigger cell in the SAME tick as the programmer or the next round's word leaks; a delayed copy does not work); the arm/disarm gotcha (`armed` never auto-clears and `cfg` always arms, `#863`/`#869`); and the nine-cell serialized word chain plus long relay paths that existed purely for placement. Halting becomes inherent to the handshake -- the cell stops acking, the store holds -- rather than a race to freeze something in time. **Two catches, verified against the current code before writing this:**
- **The sequencer has NO capture side today.** `CELL_CHEATSHEET.md`: arity 0, "`ack_out` is permanently tied low on every direction", a config-fixed cyclic list of up to 4 real 8-BIT values advancing only when the current offer is acked (VM: `seq_value_0..3` masked `& 0xFF`). "Record any data from any direction" makes it a different cell (arity 0 -> has an input). Full 32-bit values x 4 = 128 bits of config, more than the widest config any core has today (`ram`, 80 bits), so it likely means fewer values or loading through the incremental reprogram channel (as `ram`'s init halves already are). The existing `nano` hold+reemit (`#382`) already converts "any arrival" into one held full-width value; a sequencer would generalise that to several.
- **"Start from any direction" while refusing other words needs per-direction ack AND match-aware selection.** The RTL selects the first ARRIVED direction in N>S>E>W order (`watch_sel_x`, acking only the selected one). In an idle-refuses-non-Start mode a refused word arriving on N would mask a Start on E and DEADLOCK, so idle selection must filter by pattern match (four small 4-bit comparators). And the VM acks EVERY arrival delivered in a tick (the documented gap, `#868`), so a VM prototype would silently consume the store's offered word whenever a Start coincided with one. Per-direction ack in the VM is a PREREQUISITE, not a nice-to-have.
